# 仓库功能图

仓库把人维护的功能清单放在根目录 `repo-map/features.json`。清单只写功能、目的、理由出处、入口、根功能的独立子仓登记和外部依赖名字；外部依赖名字由人在根功能声明，谁用到从代码和文档推导。文件归属、行数、依赖、标记与页面都从 Git 跟踪文件推导。

画图和更新图（新建或修改 `features.json`、重新发布现状图）都照 `xy-cleanup` 走：画完接着清扫变过的功能、找能删的地方，不只交一张图。第一次画图还没有认可记录，变过的就是全部功能。

## 功能清单

每个功能对象必须恰有以下通用字段：

| 字段 | 用途 |
|---|---|
| `id` | 全树唯一的稳定标识；小写字母开头，只含小写字母、数字和连字符。 |
| `title` | 给人看的功能名，非空。 |
| `what` | 一句话说明要什么，非空。 |
| `why` | 功能为什么需要，以及理由出处。 |
| `directory` | 对应目录的仓内相对路径；仓库根写 `""`；不对应目录写 `null`。 |
| `entries` | 仓内相对文件路径，或以 `/` 结尾的目录路径；目录入口包含其下所有跟踪文件。 |
| `children` | 子功能数组。 |

根功能还必须有 `subrepositories` 字段，记录另有功能图的独立子仓目录；没有时写 `[]`。`subrepositories` 是仓内相对目录路径数组：路径非空、不以 `/` 开头或结尾、不含 `\`，且不能有空段、`.` 段或 `..` 段。重复路径不报错，比对时按集合处理。子功能不能有 `subrepositories`。

根功能还必须有 `external_dependencies` 字段，列出仓外依赖的名字；没有时写 `[]`。名字必须是非空字符串，首尾没有空白且不含换行。重复名字不报错。子功能不能有 `external_dependencies`。

`why` 必须恰有 `text`、`source`、`quote`、`from` 四个字段：

| `source` | `quote` | `from` |
|---|---|---|
| `原话` | 用户说过的话或用户规范的逐字原文，非空。 | 原话或规范的明确来历。 |
| `确认` | 空字符串。 | 用户确认回答的来历。 |
| `起草` | 空字符串。 | 空字符串。 |

`text` 是非空理由。`check` 校验格式，但不能判断引文是否真由用户说过；新增或改动清单时，由审查者对照 `from` 指向的原件逐条核对。`起草` 表示用户尚未确认，页面会显眼标出「等你拍板」。

一个最小清单如下：

```json
{
  "id": "sample",
  "title": "示例仓库",
  "what": "说明仓库提供什么。",
  "why": {
    "text": "需要一个可校验的功能清单。",
    "source": "起草",
    "quote": "",
    "from": ""
  },
  "directory": "",
  "subrepositories": [],
  "external_dependencies": [],
  "entries": [],
  "children": []
}
```

清单必须满足以下约束：

- 根功能的 `directory` 是 `""`，每个功能 id 唯一。
- 每个非空 `directory` 下至少有一个 Git 跟踪文件；目录只能对应一个功能，子目录功能必须位于最近的祖先目录功能之内。
- 每个 `entries` 路径存在，且处于该功能最近的目录功能之内；不能落在另一个目录功能之内。目录入口必须以 `/` 结尾。
- 没有子功能的目录功能使用 `entries: []`。目录本身已经登记了它的全部跟踪文件。
- 每个外部依赖名字至少在一份 Git 跟踪的代码或文档中被整词提到，且不能与仓内目录功能的目录名相同。
- gitlink 和未被忽略目录里的嵌套 Git 仓仍会报「还不支持子仓」。被忽略规则直接点名的嵌套 Git 仓必须登记在根功能的 `subrepositories`；漏登记会列出路径并报错。登记的路径在当前检出中存在、却不是被忽略规则直接点名的嵌套 Git 仓时也会报错；路径不存在时不报错。登记且符合条件的子仓不进入功能图。被忽略的目录不再向内查找，因为那里通常是工作树和依赖缓存。
- 符号链接、含 NUL 字节或路径上已归为「其他」的文件先归为「其他」；其余普通文本文件使用已知但暂不支持统计的代码后缀时，检查会报错并列出文件。

## 文件、行数与依赖

只处理 `git ls-files` 返回的文件。每个文件恰好归一个功能。

| 分类 | 判定与计数 |
|---|---|
| 测试 | 代码后缀的文件位于 `tests`、`test`、`benches`、`test_data`、`testdata`、`fixtures` 目录中，或文件名为 `test_*.py`、`*_test.py`、`*_test.rs`、`conftest.py`；所有非空行都计为测试。 |
| 代码 | 已支持的代码后缀，以及 `.html`；依照语言规则区分代码、文档字符串与注释。HTML 中完全位于 `<!-- -->` 注释里的行计为注释。 |
| 文档 | `.md`、`.rst`，且不在测试目录中；所有非空行都计为文档。 |
| 其他 | 符号链接、含 NUL 字节的文件，以及其余文件（包括 `third_party`、`vendor`、`node_modules` 下的文件），行数为零。 |

路径上已归为「其他」的文件不读内容。读取代码、测试或文档时不跟随符号链接；发现 NUL 字节后将文件归为「其他」。其余内容按 UTF-8 解码，无效字节以替换字符解码后照常计数和推导依赖。Git 跟踪文件读不出来时，检查会报错并指出文件路径。

代码后缀由 `repo_map_lib/constants.py` 维护。已知但不支持统计的语言后缀会列出文件并使检查失败。

文件归属按以下顺序决定：

1. 文件先归到它所在的最深目录功能。
2. 该目录功能没有子功能时，文件归它。
3. 有子功能时，显式列在 `entries` 的文件归登记它的功能；祖先和子孙同时登记时，以子孙为准。
4. 其余非测试文件从入口沿 Python `import` 依赖向下查找，只在同一目录功能内走；遇到无亲缘关系的功能入口就停止。
5. 多个功能共同登记或查找到一个文件时，文件归它们最近的共同上级，标为「共用」。
6. 仍没有归属的文件归目录功能，标为「整体」。目录里有这类代码或测试时，目录功能会显示「没归到功能的代码或测试」。
7. 未登记的测试文件先看它直接导入、且和测试文件属于同一目录功能的代码。文件名对应的被测文件只在当前候选里查找；同目录功能没有导入代码时，再看它导入的其他目录功能里的代码，归这些代码所归的功能。涉及多个功能时归最近共同上级，标为「共用」。仓内代码一处都没导入时，测试才归自己所在的目录功能并标为「整体」。

Python `import` 通过 AST 解析；模块名只在仓内恰好匹配一个 `.py` 文件时成立。相对导入按当前文件目录解析。测试代码的 import 只用于判定测试归属。

代码与文档中的路径提及、其他目录功能名提及，会生成 `mention` 关系。文件路径提及只匹配带 `/` 的路径，且匹配处两侧不能紧邻字母、数字、下划线、点、连字符或斜杠；目录名提及按整词匹配。外部依赖也按目录名的整词边界匹配，名字声明在根功能，谁用到只看文件直接归属的功能，不向上汇总。来源文件所属的目录功能是目标所属目录功能的祖先时，不论路径提及还是目录名提及，都不生成关系；上级目录的介绍文件提到下级功能是在说明组成部分。提及只供页面显示，不改变文件归属。功能之间出现 `import` 和 `mention` 两种关系时，保存为 `import`。只有彼此不是祖先或子孙的功能才显示相互依赖。

## 推导结果

`map-data.json` 顶层恰有 `root`、`features`、`markers` 三个字段。`features` 以功能 id 为键，每个功能提供：

- `title`、`directory_name`、`parent`、`children`、`what`、`why`。根功能的 `directory_name` 使用 `git worktree list --porcelain -z` 中主检出的目录名，所以从 linked worktree 出图也显示仓库名。
- `lines.own` 与 `lines.total`，分别是直接归属和包含所有子功能的代码、文档、注释、测试行数。
- `files.registered`、`files.reached`、`files.directory`、`files.shared`、`files.whole`，按归属原因列出直接文件。
- `uses`，列出用到的功能和关系类型 `import` 或 `mention`。
- `external_uses`，列出从代码和文档推导出的外部依赖名字，排序、去重；没有时为 `[]`。
- `markers`，列出「等你拍板」「还没实现」「没归到功能的代码或测试」。

`markers` 提供三种标记的数量。没有目录、没有子功能、没有入口的功能会标「还没实现」。目录功能有子功能，且有代码文件或测试文件的行数落在「整体」时，会标「没归到功能的代码或测试」。功能比文件粒度更细时可以没有行数；页面显示「—」。

## 命令

所有参数都要显式给出；`--repo` 必须是仓根绝对路径。参数错误退出码为 `2`；功能清单或仓库检查有错误退出码为 `1`；检查通过时，即使有标记也退出码为 `0`。

```sh
python3 <xy-repo-map目录>/repo_map.py check \
  --repo <仓根绝对路径>

python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> \
  --out <不存在或为空的输出目录>

python3 <xy-repo-map目录>/repo_map.py render-workspace \
  --repo <主仓根绝对路径> \
  --out <不存在或为空的输出目录>

python3 <xy-repo-map目录>/repo_map.py publish \
  --out <render 输出目录> \
  --as <当前|清扫前|清扫后>
```

`check` 校验清单、子仓、支持的后缀、文件归属、行数、依赖和标记。

`render` 先完成同样的校验，再读取 `repo_map_lib/templates/feature-tree.html`，嵌入数据后写 `index.html` 和 `map-data.json`；模板路径登记在「出图」功能的 `entries` 中。页面是可离线打开的单页，只画手机友好的功能树，不显示实现文件；页头显示根功能的名字、「要什么」和「为什么」及其出处，点击根功能名打开详情；树从根功能的子功能开始。功能行和详情面板的「用到」都列出外部依赖并标为「外部」；外部依赖使用不可点击的元素。默认显示根下面两层；行数条长度表示占父功能的比例，条内按代码、测试、文档、注释分段。筛选「等你拍板」时，显示带标记的功能及其各级上级，不显示其他功能和「没细分到子功能的部分」。页面内嵌的功能数据与 `map-data.json` 相同，但不含 `files`。输出目录必须不存在或为空。

`render-workspace` 先用 `build_map` 分别检查主仓和每个登记子仓；主仓必须登记至少一个子仓，登记的子仓必须在当前检出中、是 Git 仓根并有自己的有效 `repo-map/features.json`。检查失败退出 `1`，错误会指出子仓和原因；子仓缺少清单时提示先为它起草只有根功能的清单，子仓未在当前检出时提示到子仓所在的检出里运行。参数错误仍退出 `2`。主仓根保持不变，子仓根按登记顺序接在它的子功能末尾；子仓功能 id 加上登记路径前缀，`parent`、`children`、`uses` 和 `files` 中的路径同步改写。子仓自己的行数和标记保持不变；主仓根的 `lines.total` 与顶层标记计数加上各子仓的计数。子仓不会递归组合它登记的其他仓。

组合时，每个功能的外部依赖名字只在声明该名字的仓以外查找目录名恰好匹配的功能。主仓根用主检出目录名作为目录名，子仓根用登记路径最后一段，其他目录功能用目录最后一段。唯一匹配时，将名字从 `external_uses` 移到指向该功能的 `uses`，关系类型为 `mention`；已有同目标 `import` 时保留 `import`。如果源和目标互为祖先或子孙，则只移出外部依赖，不加关系。找不到或匹配多个目录功能时，该名字继续作为不可点击的外部依赖显示。功能行的「用到」按钮显示目标的完整功能名（标题和目录名），详情面板也显示完整功能名。`check` 和 `render` 仍只检查或生成当前仓自己的图；`publish` 行为不变。

`publish` 要求目录内同时有 `index.html` 与 `map-data.json`，并从 `map-data.json` 生成站点名，不接受手写站点名。根功能 `directory_name` 加 `-map` 是单仓的固定站点名；若功能 id 中有 `/`，则加 `-overview-map` 作为组合图固定站点名。`--as 当前` 每次覆盖固定站点；`--as 清扫前` 和 `--as 清扫后` 分别追加发布当天本地日期及 `-before`、`-after`，保留清扫快照。map-data 无法读取、缺少根功能或根功能没有 `directory_name` 时参数检查失败，退出 `2`。把命令输出的链接交给用户。

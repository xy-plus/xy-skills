# 仓库功能图

每个仓库的图放在仓根 `repo-map/`，用于看清功能分层、文件归属和功能之间的关系。仓图是维护中的模型，正式出图前必须通过 `check`。

## 格式约定

- `likec4.config.json` 只写根节点名，例如 `{"name":"quant_engine"}`。
- `kinds.c4` 只定义 `node` 和 `repo` 两种元素类型，内容必须与 `repo_map.py` 内的标准文本完全一致。`specification` 只放在这里。
- `approvals.txt` 由 `record` 追加，不手工维护。
- 其他 `.c4` 文件写节点、描述、链接和关系，可按功能拆分，避免单文件超过仓库长度限制。生成的网站不放进仓库。
- 每个元素都要有一句非空描述。根节点必须是唯一顶层 `node`，其 id 与配置名相同。
- 节点可以嵌套。功能结构只包含节点 id、类型、标题、描述、上级和关系的起点、终点、标题。不能在元素或关系上添加 `technology`、`tags`、`metadata` 等属性。
- 链接路径相对于 `repo-map/`，类别只能是 `code`、`tests`、`docs`、`data`、`repo`。仓内每个 Git 跟踪文件（`repo-map/` 自身除外）必须恰好由一个节点归属；目录和文件都可链接，按覆盖文件的最长路径计算归属，同一路径不能链接两次。
- 子仓在父图中只用一个 `repo` 元素占位，只有一个 `repo` 链接，不画子仓内部节点。子仓自己的图单独维护；父仓关系只能连到占位元素。
- 共享机制只建一个节点，使用它的节点用关系相连。流程可用同层节点及关系表示。

## 粒度

从仓库实际功能倒推节点，细到「整块删掉只丢这一个功能」为止，通常对应一个或几个文件；不要细到函数。嵌套节点表达功能分组，关系表达调用、数据流或流程先后。先确定一份文件属于哪个功能，再补齐该功能的代码、测试和文档链接。

文件链接属于归属校验，不属于需批准的功能结构。挪文件或只调整链接、格式、注释时，摘要不变；改节点、上级、描述或关系会改变摘要，需要用户同意。

## 五个命令

所有命令都显式给出路径和选项。`--repo` 使用仓根或工作树根的绝对路径；不从当前目录猜仓根。

```bash
python3 <skill目录>/repo_map.py init --repo <仓根绝对路径> --id <根节点id> --title <根节点标题> --description <一句话描述>
python3 <skill目录>/repo_map.py approval --repo <工作树绝对路径>
python3 <skill目录>/repo_map.py record --repo <工作树绝对路径> --approval <原话文件绝对路径>
python3 <skill目录>/repo_map.py check --repo <仓根绝对路径>
python3 <skill目录>/repo_map.py render --repo <仓根绝对路径> --mode <草稿或正式> --out <不存在或为空的目录>
```

- `init` 拒绝覆盖已有 `repo-map/`；它会为识别到的子仓建立占位节点。
- `approval` 把当前图与 `git worktree list --porcelain` 的第一项所指主检出当前分支上的图比较，打印节点/关系变化和 `repo-map sha256 <摘要>`。主检出处于分离头指针时无法比较。这个比较供用户审阅，不作为放行依据。
- 批准流程：把变化清单和摘要交给用户，同时提供原正式图（若存在）和新草稿图；提问中必须包含摘要，且有一个选项的文字正好是「同意改图」。只有用户明确选择该项后，才把对应 hook 原话交给 `record`。`record` 会核对原话路径、hook 两侧 answers、题干摘要、选项和回答，再追加摘要、日期与原话路径。重复摘要只提示，不重复写。
- `check` 检查模型、批准记录、LikeC4 语法、支持的代码后缀、文件归属和子仓。功能结构摘要不在 `approvals.txt` 时会报告「图未经同意」及当前摘要并以状态码 1 退出。
- `render --mode 草稿` 不查批准记录，每张视图标题标「草稿·未经同意」，并在网站根目录写 `DRAFT`。草稿只用于给用户审图，不发布为正式图。
- `render --mode 正式` 要求整棵子仓树都通过完整 `check`，再生成没有 `DRAFT` 的静态网站。网站交给已批准的平台发布；平台未就绪时，草稿网站只在本机 `127.0.0.1` 提供，并通过 SSH 端口转发查看。

完整 `check` 必须先运行 LikeC4 `validate`；`export json` 不能代替它，因为 LikeC4 1.60.0 在语法错误时仍可能成功导出 JSON。整棵仓图会临时组合成一个 LikeC4 项目，只放一份 `kinds.c4`；多项目各带类型定义会触发重复元素类型错误。静态网站使用 hash 路由，因为无 hash 路由时深层视图地址在直接打开或刷新时会 404。

摘要只证明某个功能结构曾获同意。`record` 挡住拿错原话、摘要不符、缺选项或未同意等误用；agent 能写本机文件，因此故意伪造原话文件或同意记录不在本地脚本的防范范围，审核仍要核对记录引用的原话。

## 起草第一张图

1. 在工作树根运行 `init`，根 id 要显式给出，并与 `likec4.config.json` 中的名字相同。
2. 读取 Git 跟踪文件和子仓，按「整块删掉只丢一个功能」分组；从功能入口向下画节点，不复制代码结构。
3. 为每个节点写清功能描述，给代码、测试、文档分别挂正确类别的链接；给共享机制单独建节点并加关系。
4. 运行 `check`，修好除「图未经同意」外的所有问题。用 `approval` 阅读变化清单与摘要，用草稿模式出图供用户查看。
5. 用户明确同意后运行 `record`，再运行 `check` 确认通过。

新增 LikeC4 模型时只使用 `npx -y likec4@1.60.0`。版本升级需用户同意；Node、npx、固定版本和全局权限规则见仓库根 README。

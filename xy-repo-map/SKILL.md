# 仓库功能图

仓库把人维护的功能清单放在根目录 `repo-map/features.json`。清单只写功能、目的、理由出处和入口；文件归属、行数、依赖、标记与页面都从 Git 跟踪文件推导。

## 功能清单

每个功能对象必须恰有以下字段：

| 字段 | 用途 |
|---|---|
| `id` | 全树唯一的稳定标识；小写字母开头，只含小写字母、数字和连字符。 |
| `title` | 给人看的功能名，非空。 |
| `what` | 一句话说明要什么，非空。 |
| `why` | 功能为什么需要，以及理由出处。 |
| `directory` | 对应目录的仓内相对路径；仓库根写 `""`；不对应目录写 `null`。 |
| `entries` | 仓内相对文件路径，或以 `/` 结尾的目录路径；目录入口包含其下所有跟踪文件。 |
| `children` | 子功能数组。 |

`why` 必须恰有 `text`、`source`、`quote`、`from` 四个字段：

| `source` | `quote` | `from` |
|---|---|---|
| `原话` | 用户说过的话或用户规范的逐字原文，非空。 | 原话或规范的明确来历。 |
| `确认` | 空字符串。 | 用户确认回答的来历。 |
| `起草` | 空字符串。 | 空字符串。 |

`text` 是非空理由。`check` 校验格式，但不能判断引文是否真由用户说过；新增或改动清单时，由审查者对照 `from` 指向的原件逐条核对。`起草` 表示用户尚未确认，页面会显眼标出「等你拍板」。

一个最小清单如下：

```json
{
  "id": "sample",
  "title": "示例仓库",
  "what": "说明仓库提供什么。",
  "why": {
    "text": "需要一个可校验的功能清单。",
    "source": "起草",
    "quote": "",
    "from": ""
  },
  "directory": "",
  "entries": [],
  "children": []
}
```

清单必须满足以下约束：

- 根功能的 `directory` 是 `""`，每个功能 id 唯一。
- 每个非空 `directory` 下至少有一个 Git 跟踪文件；目录只能对应一个功能，子目录功能必须位于最近的祖先目录功能之内。
- 每个 `entries` 路径存在，且处于该功能最近的目录功能之内；不能落在另一个目录功能之内。目录入口必须以 `/` 结尾。
- 没有子功能的目录功能使用 `entries: []`。目录本身已经登记了它的全部跟踪文件。
- 发现 Git 子仓或已知但暂不支持统计的代码后缀时，检查会报错，不会静默略过。

## 文件、行数与依赖

只处理 `git ls-files` 返回的文件。每个文件恰好归一个功能。

| 分类 | 判定与计数 |
|---|---|
| 测试 | 代码后缀的文件位于 `tests`、`test`、`benches`、`test_data`、`testdata`、`fixtures` 目录中，或文件名为 `test_*.py`、`*_test.py`、`*_test.rs`、`conftest.py`；所有非空行都计为测试。 |
| 代码 | 已支持的代码后缀，以及 `.html`、`.css`；依照语言规则区分代码、文档字符串与注释。CSS 使用 C 风格注释，HTML 中完全位于 `<!-- -->` 注释里的行计为注释。 |
| 文档 | `.md`、`.rst`，且不在测试目录中；所有非空行都计为文档。 |
| 其他 | 其余文件，包括 `third_party`、`vendor`、`node_modules` 下的文件，行数为零。 |

代码后缀由 `repo_map_lib/constants.py` 维护。已知但不支持统计的语言后缀会列出文件并使检查失败。

文件归属按以下顺序决定：

1. 文件先归到它所在的最深目录功能。
2. 该目录功能没有子功能时，文件归它。
3. 有子功能时，显式列在 `entries` 的文件归登记它的功能；祖先和子孙同时登记时，以子孙为准。
4. 其余非测试文件从入口沿 Python `import` 依赖向下查找，只在同一目录功能内走；遇到无亲缘关系的功能入口就停止。
5. 多个功能共同登记或查找到一个文件时，文件归它们最近的共同上级，标为「共用」。
6. 仍没有归属的文件归目录功能，标为「整体」。目录里有这类代码时，目录功能会显示「没归到功能的代码」。
7. 未登记的测试文件只看它直接导入、且和测试文件属于同一目录功能的代码。文件名对应的被测文件也只在这些导入代码中查找；导入多个功能的代码时归最近共同上级。没有同目录功能的导入代码时，测试归目录功能并标为「整体」。

Python `import` 通过 AST 解析；模块名只在仓内恰好匹配一个 `.py` 文件时成立。相对导入按当前文件目录解析。测试代码的 import 只用于判定测试归属。

代码与文档中的路径提及、其他目录功能名提及，会生成 `mention` 关系。文件路径提及只匹配带 `/` 的路径，且匹配处两侧不能紧邻字母、数字、下划线、点、连字符或斜杠；目录名提及按整词匹配。提及只供页面显示，不改变文件归属。功能之间出现 `import` 和 `mention` 两种关系时，保存为 `import`。只有彼此不是祖先或子孙的功能才显示相互依赖。

## 推导结果

`map-data.json` 顶层恰有 `root`、`features`、`markers` 三个字段。`features` 以功能 id 为键，每个功能提供：

- `title`、`directory_name`、`parent`、`children`、`what`、`why`。根功能的 `directory_name` 使用 `git worktree list --porcelain -z` 中主检出的目录名，所以从 linked worktree 出图也显示仓库名。
- `lines.own` 与 `lines.total`，分别是直接归属和包含所有子功能的代码、文档、注释、测试行数。
- `files.registered`、`files.reached`、`files.directory`、`files.shared`、`files.whole`，按归属原因列出直接文件。
- `uses`，列出用到的功能和关系类型 `import` 或 `mention`。
- `markers`，列出「等你拍板」「还没实现」「没归到功能的代码」。

`markers` 提供三种标记的数量。没有目录、没有子功能、没有入口的功能会标「还没实现」。功能比文件粒度更细时可以没有行数；页面显示「—」。

## 命令

所有参数都要显式给出；`--repo` 必须是仓根绝对路径。参数错误退出码为 `2`；功能清单或仓库检查有错误退出码为 `1`；检查通过时，即使有标记也退出码为 `0`。

```sh
python3 <xy-repo-map目录>/repo_map.py check \
  --repo <仓根绝对路径>

python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> \
  --out <不存在或为空的输出目录>

python3 <xy-repo-map目录>/repo_map.py publish \
  --out <render 输出目录> \
  --name <站点名>
```

`check` 校验清单、子仓、支持的后缀、文件归属、行数、依赖和标记。

`render` 先完成同样的校验，再写 `index.html` 和 `map-data.json`。页面是可离线打开的单页，只画手机友好的功能树，不显示实现文件；页面内嵌的功能数据与 `map-data.json` 相同，但不含 `files`。输出目录必须不存在或为空。

`publish` 要求目录内同时有 `index.html` 与 `map-data.json`，然后调用平台发布脚本。把命令输出的链接交给用户。

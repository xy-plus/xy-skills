## 归属与拆分

- 会话里第一件动手做的事是本会话唯一的大任务；TaskCreate 只放它的小任务，不加父子层级。
- 每条用户消息先判归属（包括加载其他 skill 前）：修正、补充、追问、改口或验收当前大任务的留在本会话；有独立完成标准，且不做当前大任务也能验收的，是新大任务。当场能答、无需调查和产物的问题就地答，不算大任务。
- 独立新任务需走标准工作流程（`xy-workflow`，需自己的编排者派子代理、合入或与用户来回商量）的，交给另一会话，回复「不要」，事后告知；无需该流程、一个子代理就能完成的，开子代理做。本会话收到结果后交付用户，不算本会话大任务。仅当归属两边都说得通、拿不准时问用户。一条消息有多件大任务时，当前大任务留在本会话；没有大任务时留第一件；其他独立任务逐件按上述规则处理。
- 当前大任务拆出可独立验收的部分时，由本会话定共用接口、格式和完成标准，并负责拆分、审查、需本会话作出的判断、集成和整体验收。拆出的部分仍需走标准工作流程（需自己的编排者派子代理、合入或与用户来回商量）的，按「交出去」交新会话，回复「要」；仅实现、一个子代理能完成的，由本会话编排并派子代理；不适合再拆则不拆。
- 按职责交办前先查已有会话；职责匹配的就补话并说明做完是否回本会话，否则新开会话交接。
- 同时交出去的几件互不依赖；有先后的，等前一件交付再交后一件。
- 交出去的会话归它自己：原会话不停止或删除它；收尾时也不算原会话创建的东西。回复「不要」的，原会话不等、不再跟进。

## 交出去

交接说明由派方写，接手方只读、不修改。按 `xy-runs` 放 `handoff.json`，结构固定：

```json
{"from": {"name": "派你的会话名", "short_id": "短 id"},
 "task": {"what": "接哪一件", "done_when": "做到什么算完", "others": "原话里其余的事归谁"},
 "reply": "要",
 "quotes": [{"text": "逐字原话", "source": "原件路径"}],
 "rules": "这件事特有的规矩，没有写 无",
 "facts": ["已核实的事实"],
 "decide_yourself": ["要你自己定的事"],
 "boundaries": ["不碰的东西"]}
```

`reply` 只写「要」（子任务，汇报派方）或「不要」（独立任务，自己交付用户并保留）。接手会话只做分给自己的事；接手任务也按「归属与拆分」的同一规则判断是否继续拆分。`rules` 不抄自动加载的全局说明；`boundaries` 还须写明派方已定的共用接口和格式，要改先问派方。

`quotes` 至少一条，写任务依据的用户原话；派方从原话延伸的事要关联来源原话，并把证据（怎么从那句原话来、不做会出什么事、做了能得到什么、代价多少）写进 `facts`。下文 `<本 skill 目录>` 指本 SKILL.md 所在目录：用 Skill 工具加载时是 Claude Code 给出的 Base directory，经 CLAUDE.md 引入时是引入路径所在目录。派方写完后运行 `python3 <本 skill 目录>/check_handoff.py <路径>`，按报错修改至退出 0 才启动接手会话。

目录用任务所在仓库的主检出根目录；与仓库无关则用 `$HOME/tmp`（`claude --bg` 只能在已信任目录启动，家目录的信任不保存）。启动前用 `claude agents --json --all` 查现有名字；`-n` 必填，取能说明任务的短名，尽量用中文且不与现有会话重名；名字也是 SendMessage 收件地址。用子 shell，不改原会话工作目录：

```bash
(cd "<目录>" && claude --bg -n "<名字>" "请先读交接说明 <路径>，然后照做。这件事由你全权负责，结论按交接说明里的回复方式汇报。")
```

从启动输出 `backgrounded · <短 id> · <名字>` 记下实际名字和短 id，再用 `claude agents --json` 按短 id 核对它在运行，不按预想名字查。刚起就失败或没接手的，用 `claude rm <短 id>` 删除，改对后重启。核对和告知都以启动输出为准；每个会话按此格式填一行：

```text
<会话名>（<短 id>）｜claude attach <短 id>｜回复：<要（子任务）/不要（独立任务）>
```

## 等回复、补话与返工

本会话每件回复「要」的交接任务都记入任务清单，列会话名和短 id。结束本轮时说明正在等哪些任务；不盯或轮询，等对方发消息。以收到消息确认是否完成，不凭产出文件判断（可能不是最终版）；消息到达后逐件验收。

未通过就发回原接手会话；通过后按补话方式回复「验收通过，可以自删」，对方已删除则不回复。

本大任务所有回复「要」的交接任务验收通过后，再做任务间集成（含等前置任务就绪后的界面接入、端到端）和整体验收，再按本会话回复方式收尾。未全通过就结束本轮并继续等。

补话或返工都发回原接手会话，原会话不自己做；转用户的话逐字加原件位置。用 `claude agents --json --all` 按短 id 查：还在且进程在，就用 SendMessage 发；进程已停，先 `claude respawn <短 id>` 再发；已删除，带原上下文拉回后再用 SendMessage 发，不新开交接。`-n` 后填交接时记下、作为 SendMessage 收件地址的名字，可保留交接时报的名字；不带会按对话另起名，可能变成英文、重名，或和交接时报给用户的名字对不上：

```bash
(cd "<它的启动目录>" && claude --bg --resume <完整会话 id> -n "<它原来的名字>")
```

从启动输出核对短 id 和名字都与交接记录一致，应显示 `backgrounded · <原短 id> · <原名>`。若短 id 或名字有一项不符，运行 `claude rm <输出短 id>`，再回到按短 id 查的步骤重新判断；短 id 变化说明原会话仍在、拉回的是副本。

## 接手与收尾

有问题先判断谁知道：派方知道就用 SendMessage 问；只有用户知道才问用户。按用户回答做，包括改掉派方已定的接口和格式；若回答大幅改变预期或可能影响派方决定，顺便通知它，普通回答不用通知。

失败、卡住、等用户、有未提交或未推送的改动、`claude rm` 拒删时，保留并照实汇报，不加强删参数。交接说明也不能豁免这些条件。

大任务完成并验收、无待用户回答且本任务收尾完成（交出去的会话除外）后，先照常汇报。给用户的汇报或通知（含 PushNotification）最后一句写「本会话可以关闭」；向派方汇报不用写。再按「回复」二选一：

- 「要」（子任务）：用 `claude agents --json --all` 查派你的会话；进程已停先 `claude respawn <它的短 id>`。向仍在的派方用 SendMessage 发一行结论、交付在哪、`claude --resume <自己的完整会话 id>`。未送达则复查同一列表，用 PushNotification 如实通知用户：确认不在列表才说「之前负责交付的会话已不在」；仍在则说「派方仍在但消息未送达」及失败原因；查不清就说状态未知。通知附一行结论、交付在哪、自身恢复命令，并保留本会话、不自删。送达后也保留本会话，结束本轮并说明等派方验收，不盯或轮询；收到派你的会话发来「验收通过，可以自删」后，最后自删。
- 「不要」（独立任务）：用 PushNotification 给用户发一行：会话名、结论、`claude --resume <自己的完整会话 id>`；保留本会话。

自删前先停本会话运行的后台任务（`run_in_background` 的命令、Monitor）；仍有任务在跑时，`claude rm` 只会停掉本会话，登记还在。再执行 `claude rm "$(basename "$CLAUDE_JOB_DIR")"`。用户让本会话关掉或关闭自己，也在汇报后自删；`claude stop` 只停进程，会话仍在列表，不算关闭。

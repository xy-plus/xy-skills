# 清扫仓库功能

## 开始

用户须点名仓库，并提供仓根绝对路径及功能 id 列表或「全部」；范围不可省。画图、更新图、看图转来的清扫均用「全部」；用户要一次看全部时加重审。用户自定范围时，「算图」不改范围。按 `xy-workflow` 建工作树。

## 清扫流程

| 阶段 | 做什么 |
|---|---|
| 算图 | 缺少 `repo-map/features.json` 时，从仓库现状起草清单；`why` 找不到用户原话或用户规范时标 `起草`。按人的需要定功能粒度。仓库 README 没有「实际使用」一节时，按仓库现状拟定实际使用记录的位置（如部署记录、维护中的 baseline、会话和契约记录、运行目录）以及跳过名单，放在同一张审查前决定页让用户确认或修改一次；将确认内容写入 README「实际使用」一节，此后只在用户要求时修改，审查按确认后的内容找证据。范围内有功能的 `items` 为 `[]` 时，按 `xy-repo-map` 的条目写法起草条目并标 `status: 起草`，写进清单；`check` 通过后再开始审查，剃刀 `keep` 可引用这些条目。缺少 `repo-map/skip.json` 时，按目录拟定不参与优化的名单；首次建功能清单时也创建跳过名单。`check` 通过后，用 `render` 生成清扫前页面并以 `publish --as 清扫前` 发布，将链接给用户。按 README 跑仓库全套测试，记录命令、结果和失败项作为行为基线。再运行 `approvals.py plan`；用户明确要重审时用 `--review 全部`，否则用 `--review 变过的`。 |
| 审查 | 按 `xy-review` 的主审、剃刀角色和派法，审 `plan` 列出的每个功能（含上级）；两者分别填写各自表格，并逐条审直属 TODO。派审时一并提供 README「实际使用」一节、本仓历次清扫的决定原件及范围内各功能 `why.from` 原件，找不到的注明。审查发现落不到任何条目的实体时，按判删标准记录「孤儿」发现，不向清单加条目，由用户决定。首轮剃刀写了 `keep` 的功能逐个复审：每个功能另派新开的剃刀复审；交它首轮 `keep` 逐条推翻，并挑战 `smallest`（要求真要此实体吗？真做到了吗？是否有更小做法、其他实体或现成内容可替？），同时找证据：在仓库副本删去实现并跑测试；看测试执行到哪些行，查测同一分支或同样断言的用例及重复规则。「站得住」须有证据，「没找到替代」不算。检查器会列出待复审功能。复审仍无发现才算没有可删项，不设删减数量。主审还要读完整清单和 `map-data.json`，查范围内功能重叠、分组、措辞、粒度，并对照「要什么」和条目找出有条目未实现、或有实现未入图的情况；代码类条目没有测试也算未实现。复审照旧挑战 `keep`：删掉某实体会使某条目不成立的，交用户决定；不影响条目的行为不变精简直接做。审查、找删减、判理由均由审查子代理做；编排者只派审、核证、整理决定清单并按选择实施，不补审查结论、不另写基准；有疑问就续派审查者。 |
| 询问 | 将待决定事项列成清单，每项给编号、标题、说明、适配的选项和建议；三者照审查报告写并注明来源。用户只决定条目层面的事：起草条目留不留、待删条目（连同只为它存在的实现）删不删、孤儿补成条目还是删。建议按判删标准写明证据；两份报告意见相反时两边理由都写上。询问能否/是否时，选项须有「先不做」。每份文档改写单列一条决定，带 `compare` 逐块对照，选项为「用改写稿」「不用」「按我写的改」，建议照剃刀报告。用户让 AI 代选时，只核对要求是否保留、字数是否减少；不因原文是用户规则而直接否决。理由为「起草」的功能本轮不逐实体审；用户确认或改写后先更新清单理由（确认标「确认」，改写按原话记录，均写回答来历），再派剃刀逐实体审，以便检查器按用户定下的理由核对覆盖与复审范围。复审的每条发现须反驳首轮剃刀的 `keep`、`smallest` 或发现，双方理由都写入清单；新发现再问一次。后台运行 `decision_page.py ask` 并发送打印的链接；退出码 0 后读取回答文件，留在事项目录作为决定原件。 |
| 修改 | 按报告决定改动：「直接做」直接实施，「问你」只按用户选择实施。用户确认的起草条目改为「确认」；用户决定不要的条目连同只为它存在的实现一起删；用户选择补入图的孤儿写成「确认」条目。用户选「用改写稿」时以各块新写法替换原文，并照改备注；终审由主审逐项核对要求、约束和例外是否保留。按 `xy-workflow` 实施并终审。终审通过、合入前运行 `approvals.py record`（范围同本次清扫），将 `repo-map/approved.json` 与改动一并提交。 |
| 汇报 | 用 `render` 和 `publish --as 清扫后` 发布清扫后页面，再用 `publish --as 当前` 更新固定站点现状图。对比顶层功能的代码、测试、文档、注释行数及标记数量；汇报全仓清扫前后总行数、净减及占比，根功能 `doc_chars.total` 文档字数的前后值、净减及占比，以及测试结果和遗留问题。 |

功能清单格式以及 `check`、`render`、`publish` 的命令和参数见 `xy-repo-map`，本 skill 不重复定义。

### 功能审查问题

| 字段 | 问题 |
|---|---|
| `what_true` | 对照「要什么」和条目，是否有写了却没做到的，或做了却没写的？代码类条目没有测试也算未实现。上级功能须对照子功能合起来的工作。 |
| `why_holds` | 「为什么」是否真是本功能的理由（非进度、旧版状态或「要什么」的改写）？`quote`、`from` 和原件是否支持它？原话是否正确、合理、与其他原话矛盾或存在更好办法？如今还成立吗？标「确认」「原话」只说明理由出处，仍须判断。 |
| `structure` | 按第一性原理检查同一「要什么」能否用更清楚的结构实现；是否该重构、合并（含跨功能）、拆分或新建抽象。逐项检查本功能共用文件（`map-data.json` 的 `files.shared`）是否应按功能拆开。 |

剃刀先判断功能是否必要、最小规模，再逐个说明直属实体的保留理由；说不出理由的提删除，拿不准的问你。

| 字段 | 问题 |
|---|---|
| `necessity` | 功能在实际使用中有没有真意义（按判删标准，不看原话措辞）？少做能否达目的？复杂度和行数代价相称吗？ |
| `smallest` | 两步作答。先不看代码，按本功能「要什么」「为什么」及 `map-data.json` 行数估从头实现的最小做法：列出部分、职责和各自行数；按「要什么」需验证的行为估测试，每种行为一两个用例。「要什么」里的路径、阶段、模块数是现状，不等于用户要求如此拆分；最小方案只保留用户要求的结果和约束，能合并或省去的路径、阶段、模块就合并或省去；拿不准某路径或变体是否必需，提发现问用户。再读代码逐块比较，指出现状多出的内容及行数：用不上的分支、兼容、配置、层次，可复用的本仓/其他仓/依赖实现，及可合并的重复项。多出部分要么列发现，要么引用「要什么」「为什么」中要求它的原句；「没有证据支持删除」「各个测试测的不完全一样」「没找到替代」都不是保留理由。用现有文件和行说明如何按新方案减少实现；无需证明现有代码无人使用，功能仍保留，只换更小写法。上级功能还要合看子功能：重复做同一事或整块不需要的子功能，发现目标写对应子功能 id。`design` 写两步结果；`lines` 估本功能直属文件改完后的代码、文档、注释、测试行数，键与 `map-data.json` 的 `lines.own` 相同。做法不变、只删冗余实体时，行数照当前填写，另列实体发现。估算低于当前时，以本功能 id 提「重构」发现；整个功能不需则「删除」，并入其他功能则「合并」，`benefit` 写当前和改后行数。 |
| `rewrites` | 覆盖本功能在功能图中归为文档的直属文件（排除 `TODO.md` 和跳过名单）。按原文段落逐块写改稿，每块 `lines` 标原行范围；要合并表达的相邻段落合为一块，`text` 写新文，整块删除则留空。只删重复话和不必要铺垫，或换成更短说法；每块的要求、约束、例外、术语、数字均照原样保留，不添原文没有的内容；反引号内代码、路径、命令、字段名逐字保留，代码块不变；用户规则同样改写。各块按序连接后若比原文短，为整份文件（`路径:1-末行`）列发现：全空用「删除」，否则用「重构」，并写两版字数。 |
| `keep` | 每个保留实体单列一条并过三问：`lines` 写位置（`路径:起始行-结束行`）；`requirement` 逐字引用所服务的条目；`achieved` 说明如何完整做到；`cost` 说明为何不能删除、合并或复用仓库/依赖现成内容，并说明代价和复杂度是否配得上收益。 |

逐块对照便于看出增删；检查器配对整份原文的反引号和波浪号围栏，并在改写全文核对，防止为减字删掉代码、路径或字段名。

若 `keep` 范围与仓内另一处在去掉缩进、空行及不含字母数字的行后连续 6 行相同，且 6 行合计至少 40 个字母或数字，`cost` 须写另一处位置并说明为何两份都留；可合并的提「合并」。检查器会列出另一处。

每条 `keep` 的 `achieved`、`cost` 都写该实体自己的话；不同 `keep` 条目的 `achieved` 值、`cost` 值分别不得逐字相同。

`keep` 覆盖本功能直属代码、测试、文档（按 `xy-repo-map` 分类；TODO 由 `todo_items` 审）的每个非空行：每行落在一条 `keep` 或剃刀发现目标中；`keep` 互不重叠，「删除」目标不得与其重叠。`repo-map/skip.json` 命中的文件不做行覆盖、重复扫描或改写；命中 TODO 不进 `todo_items`。每条只含一个实体：Python 至多一个 `def` 或 `class` 的开头（类方法各算一条），Markdown 至多一个标题。`requirement.source` 写 `功能 id:条目 id`，可引用任意功能的条目；`requirement.text` 必须与条目文本完全相同。多个条目共用的代码可引其中一条，在 `achieved` 中写清它还服务哪些条目。理由为「起草」时 `keep` 须为 `[]`，等用户确认后再审。被调用、文档描述、测试覆盖或所在文件对得上某功能都不构成需要；测试跟着被测实体，重复做同一事的实体留一个删一个。

### 判删标准

实体留不留，看删掉它会不会让功能图上的某条条目在实际使用中不成立。图上没有对应条目的实体，按实际使用价值判断：用 README「实际使用」所列记录说明它被执行或用到几次，并写出处；或者说明它防住的故障是否在实际使用中发生过，也可以写清防护机制、多常会发生、一次损失多少；用户以前说过什么、决定过什么只作「用户想要」的线索。有测试、文档写了、被调用、所在文件对得上某个功能都不算需要；「可能有用」「以防万一」不算证据。落不到条目的实体写成「孤儿」发现，决定「问你」；按本标准有价值时，在发现中写出建议补入的起草条目，否则建议删。

主审和剃刀用 `todo_items` 逐条审直属 TODO。TODO 仅指文件名为 `TODO.md` 的跟踪文件，归属按 `xy-repo-map` 规则；没有直属 TODO 时写 `[]`。每条回答：

| 字段 | 问题 |
|---|---|
| `lines` | 条目位置（`路径:起始行-结束行`）；互不重叠并覆盖所有非空行，文件开头约定也单列。 |
| `needed` | 还要做吗？缺整块功能时建议改功能清单「还没实现」项；修 bug、重构、实验、部署核对仍留在 TODO。 |
| `smaller` | 能否精简？TODO 只写问题、未做的代价、完成条件；理由进代码注释，步骤进 README，结果进报告，TODO 只留链接。 |
| `why_holds` | 理由仍成立吗？ |

删改 TODO 均列为发现，目标写 `TODO 文件:行号`，决定一律「问你」。

清扫完成时，范围内不能有「等你拍板」；另外两种标记必须清零，除非用户在询问阶段明确决定保留，并在汇报中列出。

## 审查报告

主审、剃刀各交一份或多份 JSON 报告；需复审时，每个功能各交一份且仅含一个功能对象的「剃刀复审」报告。结构如下：`plan` 列出的每个功能在主审、剃刀报告各出现一次；检查器列出的待复审功能在复审报告也各出现一次：

```json
{
  "role": "主审",
  "repo": "/绝对/仓库/路径",
  "features": [
    {
      "feature": "功能-id",
      "what_true": "回答",
      "why_holds": "回答",
      "structure": "回答",
      "todo_items": [
        {
          "lines": "TODO.md:1-6",
          "needed": "回答",
          "smaller": "回答",
          "why_holds": "回答"
        }
      ],
      "findings": [
        {
          "kind": "删除",
          "target": "文件:行号 或 功能 id",
          "problem": "问题",
          "proposal": "建议",
          "changes_behavior": false,
          "decision": "直接做",
          "basis": {
            "source": "xy-iron-law 第 3 条",
            "text": "如无必要，勿增实体（奥卡姆剃刀）"
          },
          "evidence": "证据",
          "benefit": "收益",
          "cost": "代价"
        }
      ]
    }
  ]
}

}
```

所有报告顶层仅有 `role`、`repo`、`features`，键须与对应示例完全一致。`role` 只能是「主审」「剃刀」「剃刀复审」；功能对象键按角色分别为：主审 `feature`、`what_true`、`why_holds`、`structure`、`todo_items`、`findings`；剃刀 `feature`、`necessity`、`smallest`、`rewrites`、`keep`、`todo_items`、`findings`；复审 `feature`、`verdicts`、`findings`，且一份复审报告只含一个功能对象。复审 `verdicts` 项恰有 `lines`、`attempt`、`evidence`、`verdict`；`lines` 须与同功能首轮某条 `keep` 完全一致，每条 `keep` 恰配一条判定；`attempt`、`evidence` 非空。`evidence` 至少引用一个本实体范围外、位置有效的准备仓跟踪文件，格式为 `路径:行号` 或 `路径:起始行-结束行`；文件与行号由检查器核验。`verdict` 仅可为「站得住」或「站不住」，后者须有重叠发现。主审 `what_true`、`why_holds`、`structure` 及每条 TODO 的三个回答不得空；`what_true` 对照「要什么」和条目，代码类条目没有测试也算未实现。剃刀 `necessity` 不得空；`smallest` 恰有 `design`、`lines` 两键且 `design` 非空；`lines` 恰为 `code`、`docs`、`comments`、`tests` 四个非负整数（布尔值不算），估算可高于当前值。四项合计低于 `map-data.json` 本功能 `lines.own` 时，须有目标为本功能 id、类型为「删除」「合并」或「重构」的发现；报错须列当前和估算行数。`keep` 须符合前文规则：覆盖、不重叠、单实体、`requirement.source` 指向清单中存在的条目且 `requirement.text` 与其完全相同；每条 `achieved`、`cost` 非空，跨条目去掉首尾空白后，各自不得逐字重复；理由为「起草」时须为 `[]`。若 `keep` 范围与仓内另一处去掉缩进、空行和无字母数字行后连续 6 行相同，且 6 行合计至少含 40 个字母或数字，`cost` 须引用另一份的有效位置。`todo_items` 须为直属 TODO 文件的有效行段，互不重叠并覆盖每个非空行。复审发现的规则同剃刀；每条都须反驳首轮 `keep`、`smallest` 或发现，决定按同一判删规则填写。其目标须在本功能逐行覆盖文件中或为本功能 id。发现 `target` 可写功能 id、`文件:行号` 或 `文件:起始行-结束行`；「删除」「合并」目标为本功能 id 时覆盖其全部文件，其他类型写功能 id 不覆盖文件。`kind` 仅可为「删除」「合并」「改名」「挪位置」「拆分」「重构」「修根因」「加约束」「改清单」「孤儿」「其他」。主审、剃刀和复审决定按同一规则填写：行为不变且目标非 TODO 文件的删除/合并须「直接做」，其他均须「问你」。每条发现须有证据、收益、代价、依据。`basis.source` 按 `xy-review/rule_references.py` 格式引用规范条款，`basis.text` 须为条款逐字连续原文。

剃刀 `rewrites` 每项恰有 `lines`（`路径:起始行-结束行`）和 `text` 两字段。直属文档每个非空行须被一块覆盖；范围有效、互不重叠且属于该文档，规则同 `keep.lines`。检查器在原文全篇配对同长度反引号串及长度至少 3 的波浪号串（可跨行），去重后要求每个片段连同分隔符在改写块按序拼成的全文中原样出现至少一次；若片段完全位于 `text` 为空的块则不查。缩进代码块没有围栏标记，不由检查器检查；由改写规则、逐段对照和终审把关。按块 `text` 非空白字符总数与原文比较；若更短，`findings` 须目标为 `路径:1-末行`，全空则类型「删除」，否则「重构」，并写改前、改后字数。此时整文件由发现覆盖，不再要求 `keep`；其他文件仍按现有规则由 `keep` 覆盖。

校验所有报告：

```sh
python3 <xy-cleanup目录>/check_reports.py \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的 \
  --reports <主审报告.json> <剃刀报告.json>
```

只交一个角色报告时，另一角色报「缺少功能」属预期；剃刀报告已交但复审未交时，「缺剃刀复审」及对应功能 id 也属预期。

全仓用 `--scope 全部`；仓根、范围、报告路径均须显式给出。退出码：`0` 通过，`1` 报告内容有误，`2` 参数有误。未通过先修报告再继续。

## 认可记录

`repo-map/approved.json` 保存各功能最近认可时的 64 位小写十六进制指纹；无此文件即无认可记录。指纹包括功能清单条目（`features.json` 中除 `children` 外的字段）、子功能 id 列表及直属文件；`load_features` 加入的 `parent` 不计。文件部分为五种归属组中的路径及内容哈希。功能清单、认可记录、跳过名单及命中路径不参与文件哈希；其他功能的变化不传到本功能。

规划审查时显式指定范围和审查方式：

```sh
python3 <xy-cleanup目录>/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的
```

`--review 变过的` 只列无认可记录或指纹与记录不同的功能；`--review 全部` 列范围内所有功能。选择上级功能或「全部」会包含其所有子孙。

终审通过后、合入前，用同一范围记录认可指纹：

```sh
python3 <xy-cleanup目录>/approvals.py record \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id>
```

`record` 更新范围内所有功能指纹，保留范围外仍在清单中的记录，删除已不在清单的 id。范围内有 `why.source` 为 `起草` 的功能时拒绝并列出 id。两命令退出码相同：`0` 成功；`1` 清单、仓库、认可记录有问题或记录被拒；`2` 参数错误。参数都须显式给出；`--review` 无默认值。

## 网页决定

需用户决定的事项写入 JSON 决定清单；运行时显式提供清单路径、平台站点名及一个尚不存在的回答文件路径：

```sh
python3 <xy-cleanup目录>/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

将命令打印的链接发给用户。退出码：`0` 回答文件已写好；`1` 挂载或运行失败；`2` 参数或决定清单错误、回答文件已存在，或回答文件目录不存在、不可写或不支持硬链接。修正输入后重试。

决定清单对象键须如下，不得多字段或少字段，字符串不可空，条目编号全局唯一；每条至少有两个不重复选项且建议项属于其中之一；至少一组，每组至少一条。

每条 `items` 恰有 `id`、`title`、`lines`、`options`、`recommended`、`compare` 六字段。普通项 `compare` 为 `null`；文档改写项为非空数组，每项恰有字符串字段 `lines`、`before`、`after`；`lines` 写原文范围（如 `guide.md:1-4`），`before` 非空，`after` 可空。一个 `compare` 的范围都须指向同一路径，格式有效、起始行递增且不重叠；页面在每块旁显示范围。数组顺序即显示顺序：相同相邻块折叠为「没改的 N 段」；`after` 为空时划线显示原文为删除，否则先划线原文，再显示新写法。页面顶部汇总所有块的非空白字符数，显示原文、改写及减少量；不自动猜段落对应关系。无对照的条目照旧显示。

```json
{
  "title": "清扫决定",
  "intro": ["页面顶部说明，一段一个字符串"],
  "groups": [
    {
      "title": "功能条目",
      "notes": ["这一组的说明"],
      "items": [
        {
          "id": "policy-item",
          "title": "确认规则",
          "lines": ["要什么：……", "为什么：……"],
          "options": ["确认", "按我写的改"],
          "recommended": "确认",
          "compare": null
        }
      ]
    }
  ],
  "footnotes": [
    {"title": "不用决定的事项", "lines": ["……"]}
  ]
}
```

回答文件含标题及每个条目的选择和自填内容：

```json
{
  "title": "清扫决定",
  "answers": {
    "policy-item": {"option": "确认", "note": ""}
  }
}
```

按条目编号读取回答。`note` 非空时以用户填写为准，`option` 仅参考；意思不明时在对话中询问。回答文件留在事项目录作决定原件，引用时写文件路径。

# 清扫仓库功能

## 入口与范围

用户点名清扫一个仓时使用。开始前要有仓根绝对路径，以及清扫范围：节点 FQN 列表，或「全部」。不能自行扩大用户指定的逐节点范围；全图审查仍会查看整张图。

按 `xy-workflow` 开工作树并完成它的起始步骤。仓没有 `repo-map/` 时，在这棵工作树中按 `xy-repo-map` 建图：

```sh
python3 <xy-repo-map目录>/repo_map.py init \
  --repo <仓根绝对路径> \
  --id <根节点id> \
  --title <根节点标题> \
  --description <根节点的一句话描述>
```

从代码、测试和文档补齐节点、关系与文件链接。开审前运行下面的引用对账命令；它会检查仓图但跳过同意记录。若命令报错，先修图再重跑。不要用会检查同意记录的命令开审，因为图可能是刚起草的：

```sh
python3 <xy-cleanup目录>/references.py --repo <仓根绝对路径> \
  > <运行目录绝对路径>/references.json
```

命令成功后，引用 JSON 写入运行目录的 `references.json`。

## 图、统计和基线

按仓库自己的说明运行完整现有测试，记录命令、退出状态和相关输出，确认审查前的基线状态；失败项要如实保留。

把草稿网站渲染到本次运行目录，并保留输出；其中的 `map-data.json` 是行数基线和分批口径：

```sh
python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> \
  --mode 草稿 \
  --out <运行目录绝对路径>/draft-before
```

`map-data.json` 的格式如下：

```json
{"mode": "草稿 | 正式",
 "nodes": {"<FQN>": {"title": "<标题>", "kind": "node | repo", "parent": "<上级 FQN 或 null>",
                     "own": {"code": 0, "docs": 0, "comments": 0, "tests": 0},
                     "total": {"code": 0, "docs": 0, "comments": 0, "tests": 0}}}}
```

键是节点在它所属仓图里的 FQN；整棵仓树的根 id 不重复，因此 FQN 全局唯一。`parent` 是上级 FQN，顶层为 `null`；子仓根节点的 `parent` 是父仓中对应的 `repo` 占位 FQN。数据保留真实层级；页面如何把子仓内容画在占位框内不改变数据层级。

按仓根和运行目录定位并读取 `map-data.json`。基线记录整张图每个节点 `total` 中的代码、文档、注释、测试四项。后续逐节点分批按 `own` 四项之和计算。收尾时用同样方式对比每个顶层节点的 `total`。

若要把草稿给用户看，用平台发布，名称带 `draft`，并把发布命令打印的链接交给用户：

```sh
python3 /home/xy/web-portal/portal.py publish \
  <名称，必须带 draft> \
  <render 的输出目录绝对路径>
```

## 机械旁证和引用对账

只运行仓内已有或本机已安装的工具，不安装新工具：

- Python 仓运行 `ruff check --select F401,F841,ERA001 .`；
- Rust 仓运行 `cargo check`，记录 `dead_code` 警告；
- 每个仓都运行 `python3 <xy-repo-rules目录>/check_file_length.py --root <仓根绝对路径>`。

保存命令、退出状态和相关输出。工具不存在、启动失败或检查失败都如实报告；失败不等于没有发现。警告只是线索，审查者仍须核对调用、构建和测试。

`references.json` 包含逐行命中的 `mentions`、有文字引用但图上没有关系的 `references_without_relationship`，以及图上有关系但没有文字命中的 `relationships_without_reference`。脚本对每个节点收集链接相对仓根的路径，以及独占目录的路径；目录最后一段名字只有在全仓所有跟踪文件所在目录中唯一时才加入名字。它逐行搜索其他节点名下的文本文件并记录文件和行号。结果只作旁证：审查者判断同名误中和动态引用。

## 派审查

审查者只读，不修改工作树，也不互相传递意见。派审时提供仓路径、范围、仓图和草稿链接、`map-data.json`、基线、机械旁证、引用对账、报告格式，以及对应规范文件：

- `<xy-iron-law目录>/SKILL.md`
- `<xy-repo-rules目录>/SKILL.md`

- 主审式审查者按第一性原理、难误用设计和仓库规范全部七条审查；
- 剃刀式审查者只按奥卡姆剃刀逐项检查。

### 全图审查

整次清扫只派一个全图审查者。让它读完整张图、所有节点的 `total` 和引用对账，检查图是否覆盖真实功能、描述与代码是否相符、关系是否缺漏或多余、基础机制是否被埋得太深、分组是否合理，以及功能是否重复、重叠、大小异常或存在可共用的抽象。全图报告按范围内节点逐个列出，但不写 `files`。

### 逐节点审查

按节点 `own` 四项之和分批，每批不超过 3000 行；单个节点超过 3000 行时单独一批。从范围内层级最高的节点开始向下审。每批派一位主审式和一位剃刀式审查者。

每位审查者从节点名下文件起步，但不把它当边界；调用方、被调用方、相关测试和文档也要检查。只有该角色报告中有一条针对祖先节点本身的「直接做」整块删除建议时，该角色才可不再报告其下层；要问用户的删除仍须审下层。编排者（执行本 skill 的你）每批至少抽查一个节点的实际代码，核实报告没有漏掉明显问题。

## 报告格式

每份报告写成一个 JSON 对象。主审和剃刀报告的 `files` 必须列出该节点归属下的全部仓内相对路径，不能重复；全图报告省略 `files`。每个范围内节点都要列出；没有发现时 `findings` 为空数组，并在 `checked` 写清核对过什么。

```json
{
  "role": "主审 | 剃刀 | 全图",
  "repo": "<仓根绝对路径>",
  "nodes": [
    {
      "node": "<节点 FQN>",
      "files": ["<主审和剃刀填写：该节点的全部仓内相对路径>"],
      "findings": [
        {
          "kind": "删除 | 合并 | 改名 | 挪位置 | 拆分 | 重构 | 修根因 | 加约束 | 改图 | 其他",
          "target": "<文件:行号或节点 FQN>",
          "problem": "<问题>",
          "proposal": "<建议怎么改>",
          "changes_behavior": true,
          "decision": "直接做 | 问你",
          "basis": {
            "source": "<xy-iron-law 或 xy-repo-rules 的名称与条款号>",
            "text": "<该条规范中的逐字依据>"
          },
          "evidence": "<文件行号，或命令和输出>",
          "benefit": "<收益>",
          "cost": "<代价>"
        }
      ],
      "checked": "<没有发现时写核对过什么>"
    }
  ]
}
```

全图报告的节点对象省略 `files`。`changes_behavior` 必须是 JSON 布尔值 `true` 或 `false`。依据来源按 `xy-iron-law 第 <数字> 条` 或 `xy-repo-rules 第 <数字> 条`填写；`basis.text` 必须逐字出现在该条款里。「直接做」当且仅当类型是删除或合并、且改后对外行为不变；否则标「问你」。`改图` 必须标「问你」。

## 校验报告

把所有批次的主审、剃刀报告和唯一一份全图报告一起校验。逐节点范围显式列 FQN；全仓范围显式写「全部」。以下示例包含两批，实际执行时逐个列出本次所有批次的主审、剃刀报告，并只列一份全图报告：

```sh
python3 <xy-cleanup目录>/check_audit.py \
  --repo <仓根绝对路径> \
  --scope <节点FQN> <另一个节点FQN> \
  --reports <第一批主审JSON> <第一批剃刀JSON> <第二批主审JSON> <第二批剃刀JSON> <唯一全图JSON>
```

命令会检查仓图（跳过同意记录），并核对报告字段、枚举、范围覆盖、删除祖先例外、逐节点文件归属和依据原文。范围内每个节点须在主审、剃刀和全图报告中各出现一次；全图报告恰好一份。退出码 `0` 表示通过，`1` 表示图或报告有问题，`2` 表示参数有问题。全部范围的命令写成 `--scope 全部`。报告未通过时先修报告或图，再重新校验。

## 汇总并询问

把所有「问你」项整理成一张表，按收益从高到低排列。每项列出建议做或不做、依据原文、收益和代价。在消息里给出这张表，再用提问工具问一次，选项为「按建议全做」或「指出要改的几项」。此前不逐项追问。

运行以下命令取得当前功能结构的摘要行，并核对完整摘要是否已记入 `repo-map/approvals.txt`：

```sh
python3 <xy-repo-map目录>/repo_map.py approval --repo <仓根绝对路径>
```

若清扫建议会增删或合并节点、修改描述或关系，先在工作树中按建议改图，保留「图、统计和基线」一节在开审前渲染到 `draft-before` 的草稿作为「修改前」，再渲染修改后的草稿，取得变化清单和新摘要。修改前、修改后两份草稿都用平台发布（名称都带 `draft`），提问时同时给出两个链接、变化清单和新摘要。

只要当前摘要不在同意记录里——包括刚起草的图或从未获批的图——这次提问必须包含改图题，即使没有任何审查发现要求改图。题干包含完整摘要行，选项之一必须是「同意改图」。这使清扫结束后的完整仓图检查能通过。

若用户修改了影响图结构的决定，按反馈重改仓图，重新取得变化清单和摘要、渲染并发布更新后的草稿，只针对更新后的图结构再询问一次。用户给出「同意改图」后立即记录：

```sh
python3 <xy-repo-map目录>/repo_map.py record \
  --repo <仓根绝对路径> \
  --approval <记录该回答的原话文件绝对路径>
```

清扫 `quant-workspace` 下的仓时，固定增加一项：建议在删除后开启 Rust `missing_docs`，并仅对 Python 库的公开接口开启 ruff `D1`；脚本、测试和实验代码不纳入 Python 检查。其他仓不加固定项目，由主审按仓库规范提出。

## 按 xy-workflow 实施

把「直接做」项和用户批准的项整理成这次清扫的实施说明，按 `xy-workflow` 的实施步骤修改并审查。依次删除无用入口、删除死代码、去冗余、调整结构、增加经批准的检查。每一步后运行相应测试；前面删除的部分不再进入后续步骤。

图结构以用户同意的版本为准。实施时可更新链接和文件挪动造成的归属变化，不再改变节点、描述或关系。若实施需要改变功能结构，先更新草稿，再请求并记录新的图结构同意。

## 收尾

跑完整测试和正式仓图检查，然后渲染正式图：

```sh
python3 <xy-repo-map目录>/repo_map.py check --repo <仓根绝对路径>
python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> \
  --mode 正式 \
  --out <运行目录绝对路径>/render-after
```

用新 `map-data.json` 对比基线中各顶层节点的四项 `total`，汇报前后变化。正式产物用平台发布命令发布，并把链接交给用户：

```sh
python3 /home/xy/web-portal/portal.py publish \
  <正式图名称> \
  <正式 render 的输出目录绝对路径>
```

最后汇报测试结果、机械旁证、报告校验、节点统计变化、正式图链接、失败项和遗留问题。

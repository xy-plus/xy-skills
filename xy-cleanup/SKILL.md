# 清扫仓库功能

## 开始

用户点名仓库并给出仓根绝对路径，以及功能 id 列表或「全部」。范围不能省略。按 `xy-workflow` 建工作树。

## 清扫流程

| 阶段 | 做什么 |
|---|---|
| 算图 | 如果没有 `repo-map/features.json`，从仓库现状起草功能清单；`why` 引不到用户原话或用户写的规范时标 `起草`。按人的需要决定功能粒度。`check` 通过后，`render` 清扫前页面并用 `publish --as 清扫前` 发布，把链接给用户。按仓库 README 跑已有全套测试，记下命令、结果和失败项，作为行为基线。再运行 `approvals.py plan` 得到审查名单；用户明确要求重审时用 `--review 全部`，否则用 `--review 变过的`。 |
| 审查 | 按 `xy-review` 定义的主审、剃刀角色和派法，对 `plan` 列出的每个功能（含上级功能），主审、剃刀各答下方自己那张表，都逐条审它直属的 TODO 文件。主审还要读完整功能清单和 `map-data.json`，检查范围内功能是否重复、重叠，分组、措辞和粒度是否合适。审查、找删减、判理由都由审查子代理做；编排者只派审、核实证据、整理决定清单、按用户的选择安排实施，不补审查结论、不另写基准，有疑问就续派审查者。 |
| 询问 | 把要用户定的事写成决定清单：每条给编号、标题、说明、贴合这一条的选项和建议。说明、选项和建议都照审查报告写，注明出自哪份报告；用户问的是能不能、要不要做时，选项里要有「先不做」；两份报告对同一处意见相反时，两边理由都写上，建议取有「要什么」「为什么」或用户规范撑着的一边，都没有就取删。理由是起草的功能，剃刀这一轮不逐实体审；用户确认了理由以后，修改之前再派剃刀逐实体审这些功能，新的发现再问一次。后台运行 `decision_page.py ask`，把它打印的链接发给用户。命令退出 0 后读回答文件，回答文件留在事项目录里作为这些决定的出处。 |
| 修改 | 报告里决定为「直接做」的改动直接做，「问你」的只按用户选择实施。更新清单时，用户确认的理由标 `确认` 并写回答来历；用户改写的理由按原话记录。按 `xy-workflow` 实施并终审。终审通过、合入前运行 `approvals.py record`（范围同本次清扫），把 `repo-map/approved.json` 和改动一起提交。 |
| 汇报 | `render` 并用 `publish --as 清扫后` 发布清扫后页面，再用 `publish --as 当前` 更新固定站点的现状图。对比各顶层功能的代码、测试、文档、注释行数和各标记数量，报告测试结果与遗留问题。 |

功能清单格式以及 `check`、`render`、`publish` 的命令和参数见 `xy-repo-map`，本 skill 不重复定义。

### 每个功能要回答的问题

主审做加法：查写了没做到、做了没写的，理由站不站得住，结构该不该改。

| 字段 | 问题 |
|---|---|
| `what_true` | 「要什么」是否如实写出这个功能做的事：有没有写了却没做到的，或做了却没写的？上级功能对照它的子功能合起来做的事。 |
| `why_holds` | 「为什么」是不是这个功能要有的理由（不是进度、旧版的状态，也不是把「要什么」换个说法）？`quote` 和 `from` 撑得住这条理由吗？所引原话本身对不对、合不合理、和别的原话矛不矛盾、有没有更好的办法？现在还成立吗？出处标「确认」「原话」只说明理由从哪来，照样要判断。 |
| `structure` | 按第一性原理看：同样的「要什么」，有没有更少、更清楚的结构做到？该不该重构、合并（包括和别的功能合并）、拆分，或做新的抽象？ |

剃刀做减法：这个功能直属的每个实体，都要说出它为什么留下；说不出的提删除，拿不准的问你。

| 字段 | 问题 |
|---|---|
| `necessity` | 这个功能本身必不必要：「为什么」所引的原话是定了的要求，还是问句、设想、带条件的回答？少做一些能不能达到它的目的？复杂度和代价（行数）配得上吗？ |
| `keep` | 每个留下的实体一条，过三问：`lines` 写它在哪（`路径:起始行-结束行`）；`requirement` 逐字引用它服务的那句；`achieved` 写它怎样做到那句，而不是只做到一部分；`cost` 写为什么没有更小的做法——不能删、不能并进别的实体，仓库和依赖里也没有现成的——以及复杂度和代价配得上收益。 |

`keep` 的范围是这个功能直属的代码、测试、文档文件（`xy-repo-map` 归为这三类的文件；TODO 文件按 `todo_items` 审，不进这里）的每个非空行：每行要么落在 `keep` 的某条里，要么落在剃刀某条发现的目标里；`keep` 的各条互不重叠，「删除」发现的目标不能和 `keep` 重叠。一条只能是一个实体：Python 文件里最多含一个 `def` 或 `class` 的开头（类里的方法各算一个），Markdown 文件里最多含一个标题。`requirement` 的 `source` 写「要什么」「为什么」（指这个功能自己的）或用户规范条款（如 `xy-repo-rules 第 1 条`），`text` 逐字摘那一段。功能的理由还是起草时，`keep` 写 `[]`，等用户确认了再审。被调用、文档写了、测试覆盖都不是理由：测试跟着它测的东西走；两样东西做同一件事，留一个删一个。原话里有、清单里没有的，不能当理由：主审提改清单，剃刀提删除或问你，由用户定。`xy-review` 审改动时对旧东西「从真在用的入口追得到就撑得住」的放宽，清扫不用。

主审、剃刀都用 `todo_items` 逐条审功能直属的 TODO 文件。TODO 文件指文件名为 `TODO.md` 的跟踪文件，归哪个功能按 `xy-repo-map` 的文件归属规则定；没有直属 TODO 文件的功能写 `[]`。每条回答：

| 字段 | 问题 |
|---|---|
| `lines` | 这一条在哪：`路径:起始行-结束行`。各条合起来覆盖文件的每个非空行、互不重叠；文件开头的约定也算一条。 |
| `needed` | 这条还要不要做？缺的是一整块功能时，建议改成功能清单里「还没实现」的条目（改清单）；修 bug、重构、实验、部署核对这类留在 TODO。 |
| `smaller` | 能不能更短？TODO 只留问题、不做的代价、完成条件；理由进代码注释、步骤进 README、结果进报告，TODO 只留链接。 |
| `why_holds` | 理由还成不成立？ |

TODO 要删、要改，都写成目标为 `TODO 文件:行号` 的发现，决定一律「问你」。

清扫完成时，范围内不能有「等你拍板」。另外两种标记必须清零，或由用户在询问阶段明确决定保留，并在汇报里列出。

## 审查报告

主审和剃刀各交一份或多份 JSON 报告。每个报告必须是以下结构；`plan` 列出的每个功能在每个角色的报告中恰好出现一次：

```json
{
  "role": "主审",
  "repo": "/绝对/仓库/路径",
  "features": [
    {
      "feature": "功能-id",
      "what_true": "回答",
      "why_holds": "回答",
      "structure": "回答",
      "todo_items": [
        {
          "lines": "TODO.md:1-6",
          "needed": "回答",
          "smaller": "回答",
          "why_holds": "回答"
        }
      ],
      "findings": [
        {
          "kind": "删除",
          "target": "文件:行号 或 功能 id",
          "problem": "问题",
          "proposal": "建议",
          "changes_behavior": false,
          "decision": "直接做",
          "basis": {
            "source": "xy-iron-law 第 3 条",
            "text": "如无必要，勿增实体（奥卡姆剃刀）。"
          },
          "evidence": "证据",
          "benefit": "收益",
          "cost": "代价"
        }
      ]
    }
  ]
}
```

```json
{
  "role": "剃刀",
  "repo": "/绝对/仓库/路径",
  "features": [
    {
      "feature": "功能-id",
      "necessity": "回答",
      "keep": [
        {
          "lines": "tool/main.py:1-20",
          "requirement": {"source": "要什么", "text": "逐字摘录"},
          "achieved": "怎样做到这句",
          "cost": "为什么没有更小的做法；复杂度和代价配得上收益"
        }
      ],
      "todo_items": [],
      "findings": []
    }
  ]
}
```

所有键都必须精确匹配对应角色的示例。`role` 只能是「主审」或「剃刀」；主审的 `what_true`、`why_holds`、`structure` 和每条 TODO 的三个回答都不能为空；剃刀的 `necessity` 不能为空；`keep` 按上一节的规则覆盖、不重叠、一条一个实体，`requirement` 逐字引用，`achieved`、`cost` 不能为空，理由是起草的功能 `keep` 为 `[]`；`todo_items` 每条必须指向本功能直属的 TODO 文件、行号存在，同一文件的各条不重叠，合起来覆盖它的每个非空行。发现的 `target` 写功能 id、`文件:行号` 或 `文件:起始行-结束行`。发现类型为「删除」「合并」「改名」「挪位置」「拆分」「重构」「修根因」「加约束」「改清单」「其他」。决定为「直接做」或「问你」。行为不变、目标又不在 TODO 文件里的删除或合并必须「直接做」，其余一律「问你」。每条发现都要有证据、收益、代价和依据。`basis.source` 按 `xy-review/rule_references.py` 的格式写规范条款，`basis.text` 必须是该条款的逐字连续原文。

校验所有报告：

```sh
python3 <xy-cleanup目录>/check_reports.py \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的 \
  --reports <主审报告.json> <剃刀报告.json>
```

只交了一个角色的报告时，另一个角色「缺少功能」的几行是预期的。

全仓范围显式写 `--scope 全部`。范围、报告路径和仓根都要显式给出。退出码 `0` 表示通过，`1` 表示报告内容有问题，`2` 表示参数有问题。报告未通过时先修报告，再继续清扫。

## 认可记录

`repo-map/approved.json` 保存每个功能最近一次认可时的 64 位小写十六进制指纹。没有这个文件时，等同于还没有认可记录。指纹由功能自己的清单条目和直属文件组成：清单部分包含 `features.json` 中该功能除 `children` 以外的全部字段，再加子功能 id 列表；`load_features` 加入的 `parent` 不属于清单字段。文件部分包含五种归属组里的路径及内容哈希。功能清单文件和认可记录文件不参与文件哈希，其他功能的变化也不会传到本功能。

指纹是对键排序、无空白的 JSON 文本按 UTF-8 编码后取 SHA-256。普通文件按字节取 SHA-256，符号链接按链接目标字符串取 SHA-256。认可记录里的功能 id 按字母顺序排列。

规划审查时显式选择范围和审查方式：

```sh
python3 <xy-cleanup目录>/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的
```

`--review 变过的` 只列没有认可记录或指纹与记录不同的功能；`--review 全部` 列出范围内所有功能。上级功能或「全部」会包含它们的子孙功能。

终审通过后、合入前，按同一范围记录认可指纹：

```sh
python3 <xy-cleanup目录>/approvals.py record \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id>
```

`record` 更新范围内全部功能的指纹，保留范围外仍在功能清单里的记录，并删掉清单里已不存在的 id。范围内有 `why.source` 为 `起草` 的功能时，拒绝写入并列出功能 id。两条命令的退出码相同：`0` 表示成功，`1` 表示清单、仓库或认可记录有问题，或记录被拒；`2` 表示参数错误。所有参数都要显式给出；`--review` 没有默认值。

## 网页决定

清扫里要用户定的事写进一个 JSON 决定清单。运行时显式给出清单路径、平台站点名和一个尚不存在的回答文件路径：

```sh
python3 <xy-cleanup目录>/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令打印的链接发给用户。退出码 `0` 表示回答文件已写好；退出码 `1` 表示挂载或运行失败；退出码 `2` 表示参数、决定清单有问题，或回答文件已经存在。修正输入后重新运行。

决定清单对象的键必须与下面一致。各对象不能多字段或少字段，字符串不能为空；条目编号全局唯一；每条至少有两个不重复选项，建议项必须是其中之一；至少有一组，每组至少有一条。

```json
{
  "title": "清扫决定",
  "intro": ["页面顶部说明，一段一个字符串"],
  "groups": [
    {
      "title": "功能条目",
      "notes": ["这一组的说明"],
      "items": [
        {
          "id": "policy-item",
          "title": "确认规则",
          "lines": ["要什么：……", "为什么：……"],
          "options": ["确认", "按我写的改"],
          "recommended": "确认"
        }
      ]
    }
  ],
  "footnotes": [
    {"title": "不用决定的事项", "lines": ["……"]}
  ]
}
```

回答文件包含标题和每个条目的选择与自填内容：

```json
{
  "title": "清扫决定",
  "answers": {
    "policy-item": {"option": "确认", "note": ""}
  }
}
```

按条目编号读取回答。`note` 非空时以用户写的内容为准，`option` 只作参考；意思不明确时在对话中询问。回答文件留在事项目录里作为这些决定的原件，引用决定时写文件路径。

# 清扫仓库功能

## 开始

用户点名仓库并给出仓根绝对路径，以及功能 id 列表或「全部」。范围不能省略。按 `xy-workflow` 建工作树。

## 清扫流程

| 阶段 | 做什么 |
|---|---|
| 算图 | 如果没有 `repo-map/features.json`，从仓库现状起草功能清单；`why` 引不到用户原话或用户写的规范时标 `起草`。按人的需要决定功能粒度。`check` 通过后，`render` 清扫前页面并用 `publish` 发布，把链接给用户。按仓库 README 跑已有全套测试，记下命令、结果和失败项，作为行为基线。 |
| 审查 | 按 `xy-review` 定义的主审、剃刀角色和派法，对范围内每个最细功能分别回答下方三个问题。主审还要读完整功能清单和 `map-data.json`，检查范围内功能是否重复、重叠，分组、措辞和粒度是否合适。上级功能名下没细分到子功能的文件，随它下面最相关的最细功能一起审，派审时把这些文件列给审查者。 |
| 询问 | 把要用户定的事写成决定清单：每条给编号、标题、说明、贴合这一条的选项和建议。后台运行 `decision_page.py ask`，把它打印的链接发给用户。命令退出 0 后读回答文件，回答文件留在事项目录里作为这些决定的出处。 |
| 修改 | 行为不变的删除和合并直接做；需要用户决定的改动只按用户选择实施。更新清单时，用户确认的理由标 `确认` 并写回答来历；用户改写的理由按原话记录。按 `xy-workflow` 实施并终审。 |
| 汇报 | `render` 并发布清扫后页面。对比各顶层功能的代码、测试、文档、注释行数和各标记数量，报告测试结果与遗留问题。 |

功能清单格式以及 `check`、`render`、`publish` 的命令和参数见 `xy-repo-map`，本 skill 不重复定义。

### 每个功能要回答的问题

| 字段 | 问题 |
|---|---|
| `needed` | 这个功能名下的代码、测试和文档，是否都是它「要什么」所需要的？ |
| `smaller` | 能否用更少的代码做到同样的事？ |
| `why_holds` | 「为什么」仍然成立吗？行数是否配得上？ |

清扫完成时，范围内不能有「等你拍板」。另外两种标记必须清零，或由用户在询问阶段明确决定保留，并在汇报里列出。

## 审查报告

主审和剃刀各交一份或多份 JSON 报告。每个报告必须是以下结构；范围内每个最细功能在每个角色的报告中恰好出现一次：

```json
{
  "role": "主审",
  "repo": "/绝对/仓库/路径",
  "features": [
    {
      "feature": "功能-id",
      "needed": "回答",
      "smaller": "回答",
      "why_holds": "回答",
      "findings": [
        {
          "kind": "删除",
          "target": "文件:行号 或 功能 id",
          "problem": "问题",
          "proposal": "建议",
          "changes_behavior": false,
          "decision": "直接做",
          "basis": {
            "source": "xy-iron-law 第 3 条",
            "text": "如无必要，勿增实体（奥卡姆剃刀）。"
          },
          "evidence": "证据",
          "benefit": "收益",
          "cost": "代价"
        }
      ]
    }
  ]
}
```

所有键都必须精确匹配示例。`role` 只能是「主审」或「剃刀」；每个功能的三个回答都不能为空。发现类型为「删除」「合并」「改名」「挪位置」「拆分」「重构」「修根因」「加约束」「改清单」「其他」。决定为「直接做」或「问你」。只有行为不变的删除或合并可以「直接做」；「改清单」必须「问你」。每条发现都要有证据、收益、代价和依据。`basis.source` 按 `xy-review/rule_references.py` 的格式写规范条款，`basis.text` 必须是该条款的逐字连续原文。

校验所有报告：

```sh
python3 <xy-cleanup目录>/check_reports.py \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --reports <主审报告.json> <剃刀报告.json>
```

只交了一个角色的报告时，另一个角色「缺少功能」的几行是预期的。

全仓范围显式写 `--scope 全部`。范围、报告路径和仓根都要显式给出。退出码 `0` 表示通过，`1` 表示报告内容有问题，`2` 表示参数有问题。报告未通过时先修报告，再继续清扫。

## 网页决定

清扫里要用户定的事写进一个 JSON 决定清单。运行时显式给出清单路径、平台站点名和一个尚不存在的回答文件路径：

```sh
python3 <xy-cleanup目录>/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令打印的链接发给用户。退出码 `0` 表示回答文件已写好；退出码 `1` 表示挂载或运行失败；退出码 `2` 表示参数、决定清单有问题，或回答文件已经存在。修正输入后重新运行。

决定清单对象的键必须与下面一致。各对象不能多字段或少字段，字符串不能为空；条目编号全局唯一；每条至少有两个不重复选项，建议项必须是其中之一；至少有一组，每组至少有一条。

```json
{
  "title": "清扫决定",
  "intro": ["页面顶部说明，一段一个字符串"],
  "groups": [
    {
      "title": "功能条目",
      "notes": ["这一组的说明"],
      "items": [
        {
          "id": "policy-item",
          "title": "确认规则",
          "lines": ["要什么：……", "为什么：……"],
          "options": ["确认", "按我写的改"],
          "recommended": "确认"
        }
      ]
    }
  ],
  "footnotes": [
    {"title": "不用决定的事项", "lines": ["……"]}
  ]
}
```

回答文件包含标题和每个条目的选择与自填内容：

```json
{
  "title": "清扫决定",
  "answers": {
    "policy-item": {"option": "确认", "note": ""}
  }
}
```

按条目编号读取回答。`note` 非空时以用户写的内容为准，`option` 只作参考；意思不明确时在对话中询问。回答文件留在事项目录里作为这些决定的原件，引用决定时写文件路径。

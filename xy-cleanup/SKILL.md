# 清扫仓库功能

## 什么时候用

用户点名要清扫一个仓时使用。先让任务输入明确包含：

- 仓根的绝对路径；
- 清扫范围：节点 FQN 列表，或「全部」。

不要自行把指定范围扩大成整仓。全图审查仍会查看整张图，逐节点审查只覆盖用户给出的范围。若仓没有 `repo-map/`，在清扫工作树里创建一张待审图，再继续。

## 准备仓图

按 `xy-workflow` 在仓内开工作树。先看仓图是否存在；没有时根据仓的实际结构创建：

若已有仓图，先读图再写清扫实施说明。

```sh
python3 <xy-repo-map目录>/repo_map.py init \
  --repo <仓根绝对路径> \
  --id <根节点id> \
  --title <根节点标题> \
  --description <根节点的一句话描述>
```

从代码和测试补齐节点、关系与文件链接。开审前检查图的语法、元素和文件归属，但不要要求图已有用户同意记录；图本身的准确性也是审查内容。`check_audit.py` 会以不检查同意记录的方式运行仓图检查。仓图有任何其他检查错误时先修好再开审。

在本机生成草稿图，供审查者看层级与节点统计：

```sh
python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> --mode 草稿 --out <新的输出目录绝对路径>
```

草稿只在本机审阅，不发布。图里的每个节点应有用途清楚的描述，归属检查应覆盖所有仓图以外的跟踪文件。

## 建立基线与旁证

先按 `xy-workflow` 跑仓库现有测试，确认基线干净，并记下整张图每个节点的代码、文档、注释、测试四项行数。行数从草稿图或仓图统计接口取得，记录节点 FQN 和四个数。

收集机械旁证，只运行仓中已有或本机已安装的工具，不安装新工具：

- Python 仓运行 `ruff check --select F401,F841,ERA001 .`；
- Rust 仓运行 `cargo check`，记录 `dead_code` 警告；
- 每个仓都运行 `python3 <xy-repo-rules目录>/check_file_length.py --root <仓根绝对路径>`。

把命令、退出状态和完整相关输出留在审查材料里。工具不存在、启动失败或检查失败都如实记录；失败不等于没有发现。不要把警告自动当作删除结论，后续仍要核对调用、构建和测试。

先运行引用对账。它会检查仓图（不要求同意记录），也会为每个节点收集链接路径和它独占目录的名字，再逐行查找其他节点名下的文本文件。把标准输出重定向保存为审查材料中的 JSON：

```sh
python3 <xy-cleanup目录>/references.py --repo <仓根绝对路径> > <审查材料目录>/references.json
```

结果包含逐行命中的 `mentions`、有文字引用但图上没有关系的 `references_without_relationship`，以及图上有关系但没有文字命中的 `relationships_without_reference`。它只是查找线索：同名命中可能无关，动态调用也可能没有静态文字，是否真实依赖由审查者判断。

## 派审查

只读审查者不修改工作树，不互相传递意见。派审时给他们仓路径、范围、仓图与草稿图、四项基线、机械旁证、引用对账、审查报告格式，以及各自需要遵守的规范。

### 全图审查

整次清扫只派一个全图审查者。让它读完整张图、节点四项统计和引用对账，检查：

- 图是否覆盖代码中真实存在的功能，节点描述是否符合代码；
- 关系有没有缺失或多余，基础机制是否被埋在不合适的位置，分组是否清楚；
- 功能有没有重复、重叠、可以合用的抽象或大小异常。

全图报告仍按范围内节点逐个填写 `nodes`，但不写 `files`。

### 逐节点审查

将范围内节点按四项行数之和分批，每批总量不超过 3000 行；单个节点超过 3000 行时单独成批。从范围里层级较高的节点开始向下审。每批派两个彼此独立的只读审查者：

- 主审式审查者检查第一性原理、难误用设计和仓库规范中的文件长度要求；
- 剃刀式审查者只按奥卡姆剃刀逐项检查：每个节点、文件、函数、参数、分支、依赖、测试和文档是否有留下的理由，能否删掉或复用仓内现成做法。

各自只提交自己的 JSON 报告，不采纳另一方的结论。上层节点只有在该角色报告明确建议整块删除且标为「直接做」时，该角色才可以不再报告它的下层；要问用户的删除仍需继续审下层。节点名下文件是审查起点，不是边界；调用方、被调用方、相关测试和文档都要追查。每批至少抽查一个节点的实际代码，确认报告没有漏掉明显问题。

## 报告格式

每份报告是一个 JSON 对象。主审、剃刀报告的 `files` 必须列出该节点归属下的全部仓内相对路径；全图报告的节点对象必须省略 `files`。没有发现也要列出节点并用 `checked` 说明核对过什么。

```json
{
  "role": "主审 | 剃刀",
  "repo": "<仓根绝对路径>",
  "nodes": [
    {
      "node": "<节点 FQN>",
      "files": ["<仅主审和剃刀填写：仓内相对路径>"],
      "findings": [
        {
          "kind": "改图",
          "target": "<文件:行号或节点 FQN>",
          "problem": "<问题>",
          "proposal": "<建议怎么改>",
          "changes_behavior": true,
          "decision": "问你",
          "basis": {
            "source": "<xy-iron-law 或 xy-repo-rules 的名称与条款号>",
            "text": "<该条规范中的逐字依据>"
          },
          "evidence": "<文件行号，或命令和输出>",
          "benefit": "<收益>",
          "cost": "<代价>"
        }
      ],
      "checked": "<没有发现时写核对过什么>"
    }
  ]
}
```

全图报告的节点对象如下，省略 `files`：

```json
{"node":"<节点 FQN>","findings":[],"checked":"<核对过什么>"}
```

`basis.source` 按 `xy-iron-law 第 <数字> 条` 或 `xy-repo-rules 第 <数字> 条`填写；`basis.text` 必须逐字出现在所指条款里。「直接做」当且仅当问题类型是删除或合并、且改后对外行为不变；其余情况必须标「问你」。改图必须标为「问你」。

## 校验报告

将全部主审、剃刀、全图报告一起校验：

```sh
python3 <xy-cleanup目录>/check_audit.py \
  --repo <仓根绝对路径> \
  --scope <节点FQN> [<另一个节点FQN> ...] \
  --reports <报告JSON路径...>
```

若范围是整张图，显式传 `--scope 全部`。命令会先检查仓图（不要求同意记录），再核对报告字段与枚举、范围覆盖、删除祖先例外、逐节点文件归属和依据原文。范围内每个节点在主审、剃刀、全图报告中都要恰好出现一次；只有某个角色报告了对祖先整块删除且「直接做」，该角色才可略过其后代。退出码 `0` 表示通过，`1` 表示图或报告有问题，`2` 表示命令参数有问题。修好所有问题后再汇总询问。

## 只问一次

把所有标为「问你」的发现汇总成一张表，按收益从高到低排列。每项列出问题、建议做或不做、规范原文、收益和代价；把机械旁证作为证据，不把机器提示直接变成决定。一次提问里让用户按建议接受或修改其中几项。不要在此之前逐项追问。

清扫 `quant-workspace` 下的仓时，固定增加一项：建议在删除之后开启 Rust `missing_docs`，并只对 Python 库的公开接口开启 ruff `D1`；脚本、测试和实验代码不纳入 Python 缺文档检查。其他仓不加固定项目，由主审根据仓库规范自行提出。

如果建议会增删或合并节点、改节点描述或关系，先在工作树中按建议编辑仓图。保留修改前的本地草稿，生成修改后的草稿，并运行 `repo_map.py approval` 取得变化清单与摘要。一次提问中同时给出修改前后草稿图、变化清单和摘要，并加一道包含摘要行、选项中含「同意改图」的仓图确认题。用户修改了影响图结构的决定时，按反馈重改仓图，只针对更新后的摘要再确认图结构。

得到「同意改图」后立即运行：

```sh
python3 <xy-repo-map目录>/repo_map.py record \
  --repo <仓根绝对路径> --approval <记录该回答的原话文件绝对路径>
```

## 按 xy-workflow 实施

把所有「直接做」项和用户批准的项整理成这次清扫的实施说明，按 `xy-workflow` 的既定步骤修改并审查。顺序是：删除无用入口、删除死代码、去冗余、调整结构、增加经批准的检查。每一步完成后都跑对应测试；前面已经删除的部分不再进入后续步骤。

图结构以用户同意的版本为准。实施时允许更新链接和因文件挪动产生的归属；不要再次改变节点、描述或关系。若工作确实需要改变功能结构，停止相关实施，更新草稿并重新请求图结构同意，再记录该回答。

## 收尾

跑完整测试和最终仓图检查，再渲染正式图：

```sh
python3 <xy-repo-map目录>/repo_map.py check --repo <仓根绝对路径>
python3 <xy-repo-map目录>/repo_map.py render \
  --repo <仓根绝对路径> --mode 正式 --out <新的输出目录绝对路径>
```

按顶层节点汇报代码、文档、注释、测试四项行数的前后变化，附上测试结果、旁证命令结果、报告校验结果和新图位置。工具失败、未解决问题以及需要用户决定的事要单独列出。

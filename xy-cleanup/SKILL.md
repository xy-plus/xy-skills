# 定期清扫

## 开始

用户须提供仓根绝对路径和功能 id 列表或「全部」。画图、更新图、看图转来的清扫用「全部」；用户点名局部范围时不得扩大。重复、冗余、注释和测试等零碎问题不在定期清扫里，按每次改动的标准流程处理。按 `xy-workflow` 建工作树，清扫修改都在工作树里完成。

默认只看上次认可后新增或变过的功能；用户要求重看全部时使用 `--review 全部`，否则使用 `--review 变过的`。计划会给出最近一次写下该功能当前认可记录的提交。提交号从 Git 历史查，避免改认可文件格式而让已有仓库无法读取，详见「认可记录」。

## 准备

1. 没有 `repo-map/features.json` 时，按 `xy-repo-map` 根据现状起草功能图；理由无法核实的标「起草」，功能粒度按人审批的需要定。首次建立功能图时一并创建 `repo-map/skip.json`。
2. 运行 `repo_map.py check`，通过后运行 `approvals.py plan`。计划为空时告诉用户「范围内没有变过的功能」，删除工作树并结束，不建立实际使用记录、卡片或决定页。
3. README 没有「实际使用」时，根据现状拟定记录来源和跳过名单，用决定页请用户确认一次，再写进 README；之后只按用户要求修改。卡片判断是否使用，只采用这节里用户确认的来源。
4. 用 `repo_map.py render` 和 `publish --as 清扫前` 生成并发布清扫前图，把链接给用户。按 README 跑全套测试，把命令、结果和失败项记作基线。
5. 派子代理在副本里按 README「实际使用」逐条推出可短跑场景并测非测试代码覆盖。Python 用 coverage.py 并统计子进程，Rust 用 llvm-tools。确认不会碰真实账户、写生产数据库或部署服务后才运行；真实数据只读，产物写入副本，能用 dry-run 时就用。确认不了就记 `ran: false` 和原因。只量本次计划功能的直属代码文件；只在实盘等无法安全短跑的文件列为未量测，不要记作未执行。

   README「实际使用」的来源按表格优先：有表格时只把表格数据行算作来源，表格外的列表和段落作为说明；没有表格才按列表项，都没有才按段落。每条来源可以推出零个、一个或多个场景。

   子代理把 `usage-coverage.json` 写在事项目录。逐条读来源时，把它指到的具体配置、部署和调用方路径列进该项的 `uses`；每个来源至少一项，`uses` 是非空字符串数组，一项一条。路径直接写，Git 标签里的文件写成 `<标签>:<路径>`，定时单元写单元文件路径。场景写命令、是否跑成及失败原因。没有场景时说明 `why_none`，有场景时清空 `why_none`。

   成功场景都未执行到的行合并写进 `files.*.missed`，范围按行排序、不相邻且不超出文件。没有任何成功场景时，`files` 必须是空对象，并把全部直属代码文件各列入 `unmeasured`、写明原因。每份计划功能的直属代码文件必须恰好出现在 `files` 或 `unmeasured` 一次。

   运行下面的校验，通过后才继续：

   ```bash
   python3 <xy-cleanup目录>/check_usage_coverage.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --usage-coverage <usage-coverage.json>
   ```

## 功能卡片

计划中每个功能一张卡片，包括计划中的上级功能。卡片子代理只读工作树，不改代码。

每张卡片只写人判断这个功能是否需要时必须知道的内容：每条一句话，不写函数名、文件名或代码行号。直属行数（`map-data.json` 中 `lines.own` 四项合计）少的相邻功能可以交同一子代理，合计不超过约 8000 行。

给卡片子代理这些输入：

- 本节卡片说明、功能 id 和工作树绝对路径。
- `map-data.json`、覆盖记录、README「实际使用」来源。
- 计划列出的上次认可提交、本仓历次清扫决定原件、本功能 `why.from` 原件。

卡片写到 `<事项目录>/cards/<功能 id>.json`，照这个字段和类型写：

```json
{
  "feature": "功能 id",
  "used": ["几句概括实际用到的内容和使用者，约五句以内"],
  "unused": [
    {
      "what": "一句话说明没人用的东西",
      "evidence": "查看 config/runtime.yml 未选它，查 scripts/run-app.sh 未调用它",
      "lines": 12,
      "risk": "删除可能影响的内容"
    }
  ],
  "changed": ["一句话一条：上次认可以来变了什么"],
  "todo": ["一句话一条：本功能 TODO.md 里攒下的大问题"],
  "map_issues": ["一句话一条：功能图写偏的地方"],
  "suggestion": ["一句话一件：选「照建议」会做的改动"],
  "recommended": "照建议"
}
```

`feature` 是字符串；`used`、`changed`、`todo`、`map_issues`、`suggestion` 是字符串数组；`unused` 是对象数组，其中 `what`、`evidence`、`risk` 是字符串，`lines` 是非负整数。

`map_issues` 写图上没写到、写了没做到、`what` 与条目矛盾、理由不成立、分组不合适和非「等你拍板」的功能图标记。「等你拍板」对应的起草条目由拼页命令自动列出，不写进 `map_issues`。

功能提供的内容包括模式、选项、配置、输出、入口、旧格式或旧用法、额外校验和兜底，按人能理解的粒度归类，每样只进 `used` 或 `unused` 一处。`used` 合成约五句以内、每句几十个字，概括实际用到了什么和谁在用；不逐样复述功能条目已经写清的内容。只有没人用的内容才逐样列进 `unused`。

实际使用只认：

- README 所列来源中明确选到或跑到的内容。
- 成功短跑覆盖到的内容。
- 这些来源中实际使用的调用方。

被测试或文档提到、理论上走得到、只被研究或实验代码调用、只写在功能清单里（含起草条目），都不能证明在用。

判「没人用」时，逐条检查覆盖记录各来源的 `uses`：配置类打开对应文件核实有没有选它，部署和调用方类查有没有调用它，包括「实际使用」记录中手册写明的手工命令；命令、子命令等入口也要查调用方。`evidence` 写明查了哪些 `uses` 项和结果。没量过或短跑没跑成不妨碍这样查；查完各来源的 `uses` 仍无法判断时才存疑从留。

短跑的 `missed` 只帮助找到待查内容，单凭没执行到不能证明没人用。查完 `uses` 仍定不了的才存疑从留，例如每次都会走的代码；这不能代替逐项查证。拿不出正面证据的内容按「用到」写，注明「没量过」或「短跑没走到」。

有正面证据的没人用的内容都放进 `suggestion`；删改风险和跨功能影响写在对应的 `unused.risk`。建议用户选「留」时，也在对应的 `unused.risk` 写实际理由及出处，例如曾防住的真实故障。`suggestion` 只列选「照建议」会做的改动，不写保留等不改的事。

交卡前核对 `suggestion` 中的改动互不矛盾；例如补一条功能要求时，不能同时删掉验证它的唯一测试或实现。

`lines` 写建议删除后能少的代码、测试和文档行数总和，不写位置；`risk` 说明删除风险及会连带改到的其他功能，即使那些功能不在本次页面上也要说明。`changed` 对比上次认可提交与当前功能图和文件；`todo` 按 `map-data.json` 的直属文件归属读取。条目为空的功能，按 `xy-repo-map` 现状起草全部条目放进建议。推荐「照建议」时建议列表不能空；推荐「不要这个功能」只适用于没有子功能的功能。

修改卡片问法后，按 [review-misses.md](review-misses.md) 在表中所列功能文字未改的提交上重做卡片，检查「图上写偏」能否发现旧问题。

## 拼成一页

运行 `feature_cards.py` 校验卡片并生成决定清单：

```bash
python3 <xy-cleanup目录>/feature_cards.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --cards <卡片.json…> --output <decisions.json>
```

命令重新计算计划，只接受计划内每个功能恰好一张卡片；字段、字符串、删除行数、建议和功能层级都须有效。计划为空、缺卡片、多卡片、重复卡片、未知功能和不完整字段都会拒绝生成页面。

它按计划顺序为每个功能生成一项决定和固定选项；上级没有「不要这个功能」。命令从功能图自动列出本次纳入原因、功能理由及所有起草条目，改写过的起草条目附上次认可的文字。这样用户实际看到将确认的文字，卡片也不会漏列。

每个功能只做一项决定，页面选项为「照建议」「留」「按我写的改」；没有子功能的功能另有「不要这个功能」。上级不能选择删除，避免父子功能回答相冲突或引发未审批的级联删除。

| 选择 | 按回答处理 |
|---|---|
| 照建议 | 做卡片建议中的每件事。 |
| 留 | 不删改代码、测试、文档或 TODO，也不做建议中的事。卡片上起草的理由和条目仍会照写确认。 |
| 按我写的改 | 以建议为基础按备注修改；含义不明时先问。 |
| 不要这个功能 | 删除该叶功能的代码、测试、文档、TODO 和功能图条目。 |

用户不在页上逐个点、只在对话中回复「都按你的建议（来吧）」时，走以下步骤：

1. 停止后台运行的 `decision_page.py ask`，并清理本次页面挂载。
2. 查找 xy-goal 记录这句话的原话文件；没有时把对话原文保存到事项目录。将该文件路径记作决定原件。
3. 每个功能按卡片上的推荐项处理，只做卡片列出的事，不多做。
4. 对仍保留在功能图中的功能，将卡片列出的起草条目 `status` 和起草理由 `source` 改为「确认」，`why.from` 写决定原件路径。

把「前三项会确认本页列出的起草文字，包括选择「留」时」写在决定页顶部。后台运行 `decision_page.py ask`，把链接给用户；退出码为 0 后读取回答文件，原样留在事项目录作为决定原件。

## 按回答修改

按 `xy-workflow` 实施：把回答文件和卡片交实施者，让它按用户选项及卡片描述定位实现。

「按我写的改」以建议为基础，备注意思不明确时先问；备注改过的起草文字按修改后的内容确认。

删除任何内容（包括「不要这个功能」）若会改动其他已选「留」功能的代码、测试、文档或 TODO，哪怕只去掉一个引用，都先停下询问用户；把用户回答原样交终审。

终审时把回答文件和对应卡片交给两位审查者。主审逐个功能核对改动是否符合选择：「留」的内容没有改动；需要询问的影响按用户原话处理。网页上选择前三项时，该功能列出的起草条目 `status` 和起草理由 `source` 都改成「确认」，`from` 记录回答文件的 `#answers.<功能 id>`；按上一段的对话批量答复处理时，起草理由的 `from` 记录决定原件路径。完成终审和全套测试后、合入前，运行 `approvals.py record` 记录决定页中仍在清单里的每个功能；`repo-map/approved.json` 随改动一起提交。

汇报前运行 `repo_map.py render`，再用 `publish --as 清扫后` 和 `publish --as 当前` 更新并发布图。

简要列出：

- 每个功能改前后的行数，以及全仓前后行数和净减。
- 删除内容、未做事项及原因。
- 测试结果和用户选择保留的标记。

## 认可记录

`repo-map/approved.json` 保存各功能认可时的 64 位小写十六进制指纹；文件不存在即无记录。指纹包括功能条目（`features.json` 中除 `children` 外的字段）、子功能 id 和直属文件；加载时加入的 `parent` 不计。文件部分是五种归属组中的路径及内容哈希。功能清单、认可文件、跳过名单和命中路径不参与文件哈希，其他功能的变化不传到本功能。

规划时显式给出仓库、范围和审查方式：

```sh
python3 <xy-cleanup目录>/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <范围> \
  --review 变过的
```

`变过的` 只列无记录或指纹不同的功能；`全部` 列所选范围内所有功能。指定上级或单独写 `全部` 会递归包含子孙。计划第三列是最近一次写下该功能当前记录的 40 位完整提交哈希；无记录写「无」。记录格式保持不变，由 Git 历史定位提交，以兼容已有仓库；未提交或历史找不到当前记录时退出 1 并要求先提交认可文件。

终审通过后、合入前，按本次实际审过的功能记录认可：

```sh
python3 <xy-cleanup目录>/approvals.py record \
  --repo <仓根绝对路径> \
  --features <功能-id…> \
  --kept-markers <标记列表>
```

列出卡片上用户选了留下的标记（`功能-id:标记名`），没有写 `无`。

`record` 只更新 `--features` 列出的功能，不递归；单独写 `全部` 会记录清单中全部功能。它保留范围外仍有效的记录，删除功能清单中已不存在的 id；所列功能仍有起草理由或条目时拒绝记录。两条命令退出码相同：`0` 成功，`1` 清单、仓库或认可记录有问题或记录被拒，`2` 参数错误。

## 网页决定

把决定写入 JSON 清单，并显式提供平台站点名和一个尚不存在的回答文件：

```sh
python3 <xy-cleanup目录>/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令返回的链接交给用户。决定清单字段和嵌套格式如下，不得加减字段：

```json
{
  "title": "决定标题",
  "intro": ["页面说明"],
  "groups": [{
    "title": "分组标题",
    "notes": ["分组说明"],
    "items": [{
      "id": "feature-id",
      "title": "条目标题",
      "lines": ["要决定的内容"],
      "options": ["确认", "按我写的改"],
      "recommended": "确认",
      "compare": null
    }]
  }],
  "footnotes": [{"title": "补充说明", "lines": ["说明"]}]
}
```

文字不可空，条目编号全局唯一；每条至少两个不同选项，建议项必须在选项中，且至少有一组、每组至少一条。

普通条目的 `compare` 为 `null`；需要逐段对照的条目用非空数组，每项恰为 `lines`、`before`、`after`，例如范围 `guide.md:1-4`。同一条内范围须为同一路径、递增且不重叠；`before` 非空，`after` 可空（表示删除）。数组顺序即显示顺序，相邻未改块合并为「没改的 N 段」；删除项划线显示原文，改写项先划线原文再显示新文；页面顶部统计非空白字符的原文、改写和减少量，不自动猜段落对应关系。

回答文件按条目 id 保存选择和备注：

```json
{
  "title": "清扫决定",
  "answers": {
    "功能-id": {"option": "留", "note": ""}
  }
}
```

按编号读取回答。`note` 非空时以用户填写为准，`option` 仅作参考；意思不明先询问。回答文件留在事项目录作为决定原件。退出码：`0` 回答文件已写好；`1` 挂载或运行失败；`2` 参数或决定清单错误、回答文件已存在，或其目录不存在、不可写或不支持硬链接。

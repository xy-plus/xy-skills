# 清扫仓库功能

## 开始

用户点名仓库并给出仓根绝对路径，以及功能 id 列表或「全部」。范围不能省略。画图、更新图、看图转来的清扫，范围是「全部」；用户要一次看全部，再加重审。用户自己点名范围的清扫，「算图」不改范围。按 `xy-workflow` 建工作树。

## 清扫流程

| 阶段 | 做什么 |
|---|---|
| 算图 | 如果没有 `repo-map/features.json`，从仓库现状起草功能清单；`why` 引不到用户原话或用户写的规范时标 `起草`。按人的需要决定功能粒度。仓里还没有 `repo-map/skip.json` 时，按目录拟一份不参与优化的名单（如实验记录、归档），放进决定页面让用户确认或修改一次，再创建该文件；没有要跳过的路径时写 `[]`，之后只在用户要求改名单时再问。第一次创建功能清单时一并创建跳过名单。`check` 通过后，`render` 清扫前页面并用 `publish --as 清扫前` 发布，把链接给用户。按仓库 README 跑已有全套测试，记下命令、结果和失败项，作为行为基线。再运行 `approvals.py plan` 得到审查名单；用户明确要求重审时用 `--review 全部`，否则用 `--review 变过的`。 |
| 审查 | 按 `xy-review` 定义的主审、剃刀角色和派法，对 `plan` 列出的每个功能（含上级功能），主审、剃刀各答下方自己那张表，都逐条审它直属的 TODO 文件。零删减的功能（理由不是「起草」、有要逐行覆盖的文件，且首轮没有目标在本功能要逐行覆盖的文件里、或是本功能 id 的「删除」「合并」发现）逐个复审；每个要复审的功能各派一个新开的剃刀复审——不续用第一个剃刀的会话，把第一个剃刀这些功能的 `keep` 交给它逐条推翻，连同它的 `smallest` 试着找出更小的做法（所引那句要求真要这个实体吗？真做到了吗？真没有更小的做法，别的实体或现成的东西真替不了吗？），并找证据：在仓库副本里删了跑测试；看每个测试跑到哪些行，找测同一分支、同样断言的测试；找别处重复写的规矩。判「站得住」也要证据，「没找到替代」不算。检查器会列出要复审的功能。「删除」「合并」算首轮有减法；改写稿变短时要求的整份文件「重构」也算，其他重构、拆分、挪位置等不算。触发条件用「零」而不是「极少」，是为避免把删减数量变成配额；复审也没找到的，才算确实没什么可删，不规定要删出几条。派审时把这个仓以前各次清扫的决定回答原件，和范围内功能 `why.from` 指向的原件（找不到的写明），一并交给审查者。主审还要读完整功能清单和 `map-data.json`，检查范围内功能是否重复、重叠，分组、措辞和粒度是否合适。审查、找删减、判理由都由审查子代理做；编排者只派审、核实证据、整理决定清单、按用户的选择安排实施，不补审查结论、不另写基准，有疑问就续派审查者。 |
| 询问 | 把要用户定的事写成决定清单：每条给编号、标题、说明、贴合这一条的选项和建议。说明、选项和建议都照审查报告写，注明出自哪份报告；用户问的是能不能、要不要做时，选项里要有「先不做」；两份报告对同一处意见相反时，两边理由都写上，建议取有「要什么」「为什么」或用户规范撑着的一边，都没有就取删。改写稿的发现每份文件一条决定，条目带 `compare` 按块一一列出原文和新写法，选项为「用改写稿」「不用」「按我写的改」，建议照剃刀报告；用户让 AI 代定时，只核对要求有没有丢、字有没有少，不因为原文是用户自己的规则就直接否掉。理由是起草的功能，剃刀这一轮不逐实体审；用户确认或改写理由后，先改清单里的理由（确认的标「确认」，改写的按原话记录，都写回答来历），再派剃刀逐实体审这些功能；先改清单，才能让检查器按用户定下的理由校验覆盖和复审范围。复审的每条发现都要和首轮剃刀的 `keep`、`smallest` 或发现相反。复审是在挑战首轮保留结论，决定一律「问你」，把两边理由都写进决定清单交用户定；新的发现再问一次。后台运行 `decision_page.py ask`，把它打印的链接发给用户。命令退出 0 后读回答文件，回答文件留在事项目录里作为这些决定的出处。 |
| 修改 | 报告里决定为「直接做」的改动直接做，「问你」的只按用户选择实施。选了「用改写稿」的文件，把各块原文换成各块的新写法，用户在备注里写了改动的照改；终审时主审逐条核对原文要求、约束和例外都还在。用户决定保留的东西，修改时写进清单的「要什么」，出处标「确认」并写回答来历。按 `xy-workflow` 实施并终审。终审通过、合入前运行 `approvals.py record`（范围同本次清扫），把 `repo-map/approved.json` 和改动一起提交。 |
| 汇报 | `render` 并用 `publish --as 清扫后` 发布清扫后页面，再用 `publish --as 当前` 更新固定站点的现状图。对比各顶层功能的代码、测试、文档、注释行数和各标记数量；写出全仓清扫前后的总行数、净减行数和占比，以及文档字数（根功能的 `doc_chars.total`）前后、净减多少和占比；报告测试结果与遗留问题。 |

功能清单格式以及 `check`、`render`、`publish` 的命令和参数见 `xy-repo-map`，本 skill 不重复定义。

### 每个功能要回答的问题

| 字段 | 问题 |
|---|---|
| `what_true` | 「要什么」是否如实写出这个功能做的事：有没有写了却没做到的，或做了却没写的？上级功能对照它的子功能合起来做的事。 |
| `why_holds` | 「为什么」是不是这个功能要有的理由（不是进度、旧版的状态，也不是把「要什么」换个说法）？`quote` 和 `from` 撑得住这条理由吗？所引原话本身对不对、合不合理、和别的原话矛不矛盾、有没有更好的办法？现在还成立吗？出处标「确认」「原话」只说明理由从哪来，照样要判断。 |
| `structure` | 按第一性原理看：同样的「要什么」，有没有更清楚的结构做到？该不该重构、合并（包括和别的功能合并）、拆分，或做新的抽象？逐个看本功能的共用文件（`map-data.json` 里 `files.shared` 列出的）要不要按功能拆开。 |

剃刀做减法，从大到小：先答这个功能要不要、最小要多大，再逐个说出直属的每个实体为什么留下；说不出的提删除，拿不准的问你。

| 字段 | 问题 |
|---|---|
| `necessity` | 这个功能本身必不必要：「为什么」所引的原话放回原件上下文，是定了的要求，还是问句、设想、带条件的回答？少做一些能不能达到它的目的？复杂度和代价（行数）配得上吗？ |
| `smallest` | 同样的「要什么」最小要多大，分两步答。第一步先不看代码，只按这个功能的「要什么」「为什么」和 `map-data.json` 里的行数，写出从头写的最小做法：分几块、每块做什么、各约多少行；测试按「要什么」里要验证的行为估，每条行为一两个用例。「要什么」里写的分几条路径、几个阶段、几个模块，是对现状的描述，不等于用户要它这样分：最小做法只留「要什么」「为什么」里用户要的结果和约束，路径、阶段、模块能并的并、能省的省；拿不准某条路径或变体是不是用户要的，写成发现问你。第二步再读现有代码逐块对照：现有的比第一步多在哪、多出多少行——哪些分支、兼容、配置、层次用不上，哪些能改用本仓、别的仓或依赖里现成的，哪些重复能并成一份。多出来的，要么写成发现，要么引出「要什么」「为什么」里要求它的那一句；「没有证据支持删除」「各个测试测的不完全一样」「没找到替代」都不算留下的理由。更小做法的证据是现有哪些文件、哪些行做的事照新做法可以怎样少写，不用证明现有代码没人用：功能还在，只是换一种更小的写法。上级功能还要看子功能合起来：有没有两个子功能做同一件事、有没有整块不要的子功能，有就写成目标为那几个子功能 id 的发现。`design` 写这两步的结果；`lines` 估照最后定下的做法写成后，这个功能直属文件的代码、文档、注释、测试各多少行，键和 `map-data.json` 里这个功能的 `lines.own` 相同；做法和现在一样、只是删掉几处多余实体的，照写现在的行数，那几处照旧写成发现。估得比现在少，就把这个做法写成一条目标为本功能 id 的「重构」发现（整个功能不要了写「删除」，并进别的功能写「合并」），收益里写现在多少行、改完约多少行。 |
| `rewrites` | 这个功能直属的每份文档（功能图归为文档的文件，`TODO.md` 和跳过名单里的除外）按原文的段一块一块改写：每块写一条，`lines` 是这一块在原文的行范围（一段一块；相邻几段要并成一段说时，写成一块），`text` 是这一块的新写法，整块都不需要就写空字符串。每块只删重复的话和不必要的铺垫、换更短的说法：这一块的每条要求、约束、例外、术语、数字照原样留着，不添原文没有的说法，反引号里的代码、路径、命令、字段名原样保留，代码块照原样。用户自己的规则也照样改写。一份文件各块的新写法按顺序接起来比原文少字时，写一条目标为这份文件全部行（`路径:1-末行`）的发现：各块都写空就写「删除」，否则写「重构」，收益写原文和改写各多少字。 |
| `keep` | 每个留下的实体一条，过三问：`lines` 写它在哪（`路径:起始行-结束行`）；`requirement` 逐字引用它服务的那句；`achieved` 写它怎样做到那句，而不是只做到一部分；`cost` 写为什么没有更小的做法——不能删、不能并进别的实体，仓库和依赖里也没有现成的——以及复杂度和代价配得上收益。 |

按块改写能让原文与新写法逐段对应，便于看出删掉了什么、加进了什么；检查器按整份文件配对反引号，并在新写法全文核对，避免删掉代码、路径或字段名来凑字数。

`keep` 的行范围和仓里别处逐字重复时（去掉缩进、空行和没有字母数字的行后连续 6 行相同，且 6 行合计至少 40 个字母或数字），`cost` 要写出至少一处另一份的位置，说明为什么两份都要留；能并的提「合并」。检查器会列出另一份在哪。

每条 `keep` 的 `achieved`、`cost` 写这个实体自己的话，两条不能逐字相同。

`keep` 的范围是这个功能直属的代码、测试、文档文件（`xy-repo-map` 归为这三类的文件；TODO 文件按 `todo_items` 审，不进这里）的每个非空行：每行要么落在 `keep` 的某条里，要么落在剃刀某条发现的目标里；`keep` 的各条互不重叠，「删除」发现的目标不能和 `keep` 重叠。`repo-map/skip.json` 命中的文件不进入逐行覆盖、重复块扫描或改写稿；命中的 TODO 文件不进入 `todo_items`。一条只能是一个实体：Python 文件里最多含一个 `def` 或 `class` 的开头（类里的方法各算一个），Markdown 文件里最多含一个标题。`requirement` 的 `source` 写「要什么」「为什么」（指这个功能自己的）或用户规范条款（如 `xy-repo-rules 第 1 条`），`text` 逐字摘那一段。功能的理由还是起草时，`keep` 写 `[]`，等用户确认了再审。被调用、文档写了、测试覆盖都不是理由：测试跟着它测的东西走；两样东西做同一件事，留一个删一个。原话里有、清单里没有的，不能当理由：主审提改清单，剃刀提删除或问你，由用户定。清单里没写、但以前的决定回答里用户明确选过保留的，不提删除，提「改清单」把它写进「要什么」，决定写「问你」，附回答原件。`xy-review` 审改动时对旧东西「从真在用的入口追得到就撑得住」的放宽，清扫不用。

主审、剃刀都用 `todo_items` 逐条审功能直属的 TODO 文件。TODO 文件指文件名为 `TODO.md` 的跟踪文件，归哪个功能按 `xy-repo-map` 的文件归属规则定；没有直属 TODO 文件的功能写 `[]`。每条回答：

| 字段 | 问题 |
|---|---|
| `lines` | 这一条在哪：`路径:起始行-结束行`。各条合起来覆盖文件的每个非空行、互不重叠；文件开头的约定也算一条。 |
| `needed` | 这条还要不要做？缺的是一整块功能时，建议改成功能清单里「还没实现」的条目（改清单）；修 bug、重构、实验、部署核对这类留在 TODO。 |
| `smaller` | 能不能更短？TODO 只留问题、不做的代价、完成条件；理由进代码注释、步骤进 README、结果进报告，TODO 只留链接。 |
| `why_holds` | 理由还成不成立？ |

TODO 要删、要改，都写成目标为 `TODO 文件:行号` 的发现，决定一律「问你」。

清扫完成时，范围内不能有「等你拍板」。另外两种标记必须清零，或由用户在询问阶段明确决定保留，并在汇报里列出。

## 审查报告

主审和剃刀各交一份或多份 JSON 报告；有要复审的功能时，每个功能各交一份「剃刀复审」报告，每份恰有一个功能对象。每个报告必须是以下结构；`plan` 列出的每个功能在主审和剃刀报告中恰好出现一次，检查器算出的每个待复审功能在剃刀复审报告中恰好出现一次：

```json
{
  "role": "主审",
  "repo": "/绝对/仓库/路径",
  "features": [
    {
      "feature": "功能-id",
      "what_true": "回答",
      "why_holds": "回答",
      "structure": "回答",
      "todo_items": [
        {
          "lines": "TODO.md:1-6",
          "needed": "回答",
          "smaller": "回答",
          "why_holds": "回答"
        }
      ],
      "findings": [
        {
          "kind": "删除",
          "target": "文件:行号 或 功能 id",

          "changes_behavior": false,
```

```json
}
```

所有报告顶层键恰有 `role`、`repo`、`features`，键必须精确匹配对应角色的示例。`role` 只能是「主审」「剃刀」或「剃刀复审」；各角色的功能对象恰有以下键：主审为 `feature`、`what_true`、`why_holds`、`structure`、`todo_items`、`findings`；剃刀为 `feature`、`necessity`、`smallest`、`rewrites`、`keep`、`todo_items`、`findings`；剃刀复审为 `feature`、`verdicts`、`findings`，一份复审报告只能有一个功能对象。复审的每条 `verdicts` 恰有 `lines`、`attempt`、`evidence`、`verdict`；`lines` 必须与首轮剃刀同一功能的一条 `keep` 完全相同，每条 `keep` 恰有一条判定；`attempt`、`evidence` 不能为空；`evidence` 至少引用一处本实体行范围以外的有效位置，格式为准备仓跟踪文件的 `路径:行号` 或 `路径:起始行-结束行`，文件和行号都由检查器核验；`verdict` 只能是「站得住」或「站不住」；判「站不住」时必须有和该行范围重叠的发现目标。主审的 `what_true`、`why_holds`、`structure` 和每条 TODO 的三个回答都不能为空；剃刀的 `necessity` 不能为空；剃刀的 `smallest` 恰有 `design`、`lines` 两个键，`design` 是非空字符串，`lines` 恰有 `code`、`docs`、`comments`、`tests` 四个非负整数值，布尔值不算整数，估算可以高于当前行数；四项合计少于 `map-data.json` 里本功能 `lines.own` 时，必须有目标为本功能 id、类型为「删除」「合并」或「重构」的发现，错误要写出当前和估算的四项行数。`keep` 按上一节的规则覆盖、不重叠、一条一个实体，`requirement` 逐字引用，`achieved`、`cost` 不能为空，去掉首尾空白后两条 `keep` 的 `achieved`、`cost` 不得逐字相同，理由是起草的功能 `keep` 为 `[]`；如果 `keep` 覆盖的行与仓内别处去掉缩进、空行和没有字母数字的行后连续 6 行相同，且 6 行合计至少 40 个字母或数字，`cost` 要写至少一处另一份的有效位置；`todo_items` 每条必须指向本功能直属的 TODO 文件、行号存在，同一文件的各条不重叠，合起来覆盖它的每个非空行。剃刀复审的发现字段和校验规则与剃刀相同，每条发现都针对首轮剃刀的 `keep`、`smallest` 或发现提出相反意见，决定一律「问你」。复审发现的目标必须在本功能要逐行覆盖的文件里，或是本功能 id。发现的 `target` 写功能 id、`文件:行号` 或 `文件:起始行-结束行`。「删除」「合并」写本功能自己的 id 时，算覆盖它的全部文件；别的类型写本功能 id 不顶覆盖。发现类型为「删除」「合并」「改名」「挪位置」「拆分」「重构」「修根因」「加约束」「改清单」「其他」。主审和剃刀发现的决定为「直接做」或「问你」；行为不变、目标又不在 TODO 文件里的删除或合并必须「直接做」，其余一律「问你」。每条发现都要有证据、收益、代价和依据。`basis.source` 按 `xy-review/rule_references.py` 的格式写规范条款，`basis.text` 必须是该条款的逐字连续原文。

剃刀的 `rewrites` 是数组，每项恰有 `lines`（`路径:起始行-结束行`）和 `text`（这一块的新写法）两个键。直属文档的每个非空行都必须被块覆盖，范围有效、互不重叠，且不能落在其他文件；校验规则与 `keep.lines` 相同。检查器在原文整份文件上把长度相同的反引号串两两配对（跨行也算），每个片段连同两头反引号都必须在该文件各块 `text` 按顺序接起来的全文中原样出现；完全落在 `text` 为空的块里的片段不查。每份文件按所有块 `text` 的非空白字符数之和比较原文；更短时，`findings` 必须有目标为 `路径:1-末行` 的发现，各块全空时用「删除」，否则用「重构」，并写出改写前后的字数。此时整份文件由发现覆盖，不再要求 `keep`；这个整文件发现也算首轮有减法，不要求该功能复审；其他文件照现有规则用 `keep` 覆盖。

校验所有报告：

```sh
python3 <xy-cleanup目录>/check_reports.py \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的 \
  --reports <主审报告.json> <剃刀报告.json>
```

只交了一个角色报告时，另一个角色「缺少功能」的几行是预期的。剃刀报告已交、复审报告还没交时，「缺剃刀复审」及其功能 id 的几行是预期的。

全仓范围显式写 `--scope 全部`。范围、报告路径和仓根都要显式给出。退出码 `0` 表示通过，`1` 表示报告内容有问题，`2` 表示参数有问题。报告未通过时先修报告，再继续清扫。

## 认可记录

`repo-map/approved.json` 保存每个功能最近一次认可时的 64 位小写十六进制指纹。没有这个文件时，等同于还没有认可记录。指纹由功能自己的清单条目和直属文件组成：清单部分包含 `features.json` 中该功能除 `children` 以外的全部字段，再加子功能 id 列表；`load_features` 加入的 `parent` 不属于清单字段。文件部分包含五种归属组里的路径及内容哈希。功能清单文件、认可记录文件、跳过名单文件和名单命中的路径不参与文件哈希，其他功能的变化也不会传到本功能。

规划审查时显式选择范围和审查方式：

```sh
python3 <xy-cleanup目录>/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id> \
  --review 变过的
```

`--review 变过的` 只列没有认可记录或指纹与记录不同的功能；`--review 全部` 列出范围内所有功能。上级功能或「全部」会包含它们的子孙功能。

终审通过后、合入前，按同一范围记录认可指纹：

```sh
python3 <xy-cleanup目录>/approvals.py record \
  --repo <仓根绝对路径> \
  --scope <功能-id> <另一个功能-id>
```

`record` 更新范围内全部功能的指纹，保留范围外仍在功能清单里的记录，并删掉清单里已不存在的 id。范围内有 `why.source` 为 `起草` 的功能时，拒绝写入并列出功能 id。两条命令的退出码相同：`0` 表示成功，`1` 表示清单、仓库或认可记录有问题，或记录被拒；`2` 表示参数错误。所有参数都要显式给出；`--review` 没有默认值。

## 网页决定

清扫里要用户定的事写进一个 JSON 决定清单。运行时显式给出清单路径、平台站点名和一个尚不存在的回答文件路径：

```sh
python3 <xy-cleanup目录>/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令打印的链接发给用户。退出码 `0` 表示回答文件已写好；退出码 `1` 表示挂载或运行失败；退出码 `2` 表示参数、决定清单有问题，回答文件已经存在，或回答文件目录不存在、不可写或不支持硬链接。修正输入后重新运行。

决定清单对象的键必须与下面一致。各对象不能多字段或少字段，字符串不能为空；条目编号全局唯一；每条至少有两个不重复选项，建议项必须是其中之一；至少有一组，每组至少有一条。

每条 `items` 恰有 `id`、`title`、`lines`、`options`、`recommended`、`compare` 六个字段。普通条目的 `compare` 写 `null`；文档改写条目写非空数组，每项恰有 `lines`、`before`、`after` 三个字符串字段，`lines` 写原文行范围（如 `guide.md:1-4`），`before` 非空，`after` 可以为空。一个 `compare` 的各项必须指向同一路径，行范围格式有效、按起始行递增且不重叠；页面在每块旁显示行范围。数组顺序就是显示顺序：相同的相邻块折叠成「没改的 N 段」，`after` 为空时将原文划线标为删除，其余块先划线显示原文，再显示新写法。顶部按所有块的非空白字符数总和显示原文、改写后和少了多少；页面不自动猜测段落对应关系。没有对照的条目照旧显示。

```json
{
  "title": "清扫决定",
  "intro": ["页面顶部说明，一段一个字符串"],
  "groups": [
    {
      "title": "功能条目",
      "notes": ["这一组的说明"],
      "items": [
        {
          "id": "policy-item",
          "title": "确认规则",
          "lines": ["要什么：……", "为什么：……"],
          "options": ["确认", "按我写的改"],
          "recommended": "确认",
          "compare": null
        }
      ]
    }
  ],
  "footnotes": [
    {"title": "不用决定的事项", "lines": ["……"]}
  ]
}
```

回答文件包含标题和每个条目的选择与自填内容：

```json
{
  "title": "清扫决定",
  "answers": {
    "policy-item": {"option": "确认", "note": ""}
  }
}
```

按条目编号读取回答。`note` 非空时以用户写的内容为准，`option` 只作参考；意思不明确时在对话中询问。回答文件留在事项目录里作为这些决定的原件，引用决定时写文件路径。

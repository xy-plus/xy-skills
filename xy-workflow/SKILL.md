## 改动分档

加载本 skill 后，紧接着按顺序加载 `xy-goal`、`superpowers:brainstorming`、`sync-think`。四个都加载完才开始工作，读代码和文档、跑命令、和用户讨论都在这之后。

动手前按 [superpowers:brainstorming 的 Three Paths](https://github.com/obra/superpowers/blob/v6.4.1/skills/brainstorming/SKILL.md) 分档，在消息里说出档位和原因，不等回复；哪件事归哪档以原文为准，不自己另加判据；各档怎么走按本流程。拿不准走重的那档；只升不降，做到一半发现比预想复杂就停下说明、升档。

- 只调查：要的是一个答案（能不能做、行不行），不是要留下的代码；查完给结论，为查写的代码只当一次性的，不合入；不走下面编号步骤。
- 小改动：改本仓已有代码、范围清楚，例如加开关、小接口、单文件修复；按本仓衡量，不按熟悉程度，需改的流程已在本仓里存在且读得到才算小改动。
- 架构级：新项目、新子系统、改组件之间的组织方式或别人依赖的接口。

## 工作流程

superpowers 不低于 6.4.1，缺了就提醒用户安装；引用的 skill 和本流程冲突时以本流程为准，派子代理时把它该守的边界写进任务说明。

本流程要求用 `xy-goal`；本会话还没开契约就先开。契约自动记录并编号用户原话；spec 和审查都引用契约原话，不另抄。spec 和审查报告放在 `<runs>/<项目目录名>/<年月日-时分秒>-<仓库名>-<主题>/`，不入库。运行目录和子代理 brief 也放在这里；事项指针登记这个目录，并把目录和契约路径告诉每个子代理。每项产物在契约里登记：spec、代码；审查不单列，审查通过就是 spec 项的验收。代码项须通过终审、快进合入并推送，且完成收尾，才算验收；按命令输出核实这些结果。

每项结束前（验收或取消），收掉本项创建或使用、且清单里已没有其他开放事项在用的资源。先停掉不再需要的临时后台进程并确认它们已退出。`claude --bg` 起的后台会话用 `claude rm <短 id>` 删除，再确认它不在 `claude agents --json --all` 列表中。还要检查没有其他进程或配置在用这些资源。工作树和分支按 `superpowers:finishing-a-development-branch` 处置，不再需要的走放弃；运行目录和工作流目录交给 `xy-runs` 定期清理。仍有开放事项、进程或配置在用的，写明使用者，留给最后一个使用它的事项收尾；要保留的先移到长期位置并写明理由。把收尾结果写进该事项的指针或验收结论（`update <T> --pointer '<指针>'`／`accept --verdict`），并按命令输出核验验收。`xy-iron-law` 和 `xy-repo-rules` 已加载；子代理不继承，派出时把这两份 SKILL.md 交给它并说明照做。

自己只编排，尽量不写代码；spec 和任务说明自己写。子代理只做交给它的事，不合入、不再派子代理。要用户定的事在第 1 步按 `sync-think` 问清，之后尽量不停下来等用户。所有审查都按 `xy-review` 派和处理；按 `superpowers:receiving-code-review` 的态度核实后再改，有理由就顶回去。审查是闸，不通过，下一步不开始。

要拆给多个代理并行或实现者换成较弱模型时，spec 之外由编排者定的决策（怎么拆、各段边界、先后）直接写进各段的任务说明；派出前自查各段任务说明合起来覆盖 spec、互不重叠、没有占位、前后一致。并行时按 `superpowers:dispatching-parallel-agents` 判断能否并行及任务说明怎么写；各开工作树、各派一个，各审各合。

1. 被改仓有 `repo-map/` 时，先读图，再写 spec，并说明功能结构是否要改、如何改。用 `superpowers:brainstorming` 讨论并写 spec，每条要求注明来自哪条原话。小改动的 spec 只写几句，说明做法、改哪些文件、怎么测，并逐句注明原话出处；架构级写完整 spec。spec 开头说明任务拆分：不拆分就写理由；拆分则列出各部分的边界、验收标准、依赖和接口，并说明它们合起来覆盖整件事、互不重叠且适合独立验收。
2. 主审和剃刀按 `xy-review` 审 spec，通过后才实现。报告放 `<工作流目录>/spec/`；判因后拆出的各份放 `<工作流目录>/spec-<名>/`，并按 `xy-review` 的 `group<G>/round<R>/` 存放。主审按铁律 1 审拆分是否充分：不拆的理由是否成立；是否把适合独立验收的部分合在一起；合并的协调成本是否低于拆分收益；拆出的部分是否切断了必须共享的上下文或隐含决策。剃刀按铁律 3 审拆分是否过度：各部分是否适合独立验收，协调成本是否低于拆分收益。拆分方案通过后才派发。
3. 开工作树前，确认被改子仓的 `.gitignore` 忽略 `.worktrees/`；再运行 `git worktree add .worktrees/<分支> -b <分支>`。树里装好依赖，跑一遍测试确认基线干净；不用 Claude Code 自带的 worktree 工具。要改结构时，实现后用 `xy-repo-map` 的 `approval` 给出清单和摘要，取得用户「同意改图」后用 `record` 记账。只改链接、格式、注释不需询问。按审过的 spec 派一个工作子代理实现，并带 `superpowers:test-driven-development`。任务说明写明工作树绝对路径，命令用绝对路径或 `git -C`。卡住或遇到 spec 未写的情况，就停下报告编排者，由编排者决定，不等用户。任务说明还要写明：互不依赖的测试并行跑；收掉自己启动的临时进程和后台会话，后台会话用 `claude rm` 删除，不用 `claude stop`，报告列出启动过的进程和会话；每轮报告只写本轮工作、结果和证据。续跑时只写增量：本轮任务和依据；首轮交代的规则、spec、任务说明不重复，变化只指出改在哪里。最后一个任务要把 spec 中需保留的信息和实现经验写进代码注释或 README、runbook、TODO 等文档，避免 spec 删除后丢失。
4. 把工作树变基到主分支最新提交，再做终审。报告放在 `<工作流目录>/code/`，与 `spec/`、`spec-<名>/` 平级，并按 `xy-review` 的 `group<G>/round<R>/` 存放。主审按 `superpowers:requesting-code-review` 派出，提供提交范围并要求只读，撰写审查报告；剃刀撰写剃刀报告。以两份报告结论作为闸门。
5. 按 `superpowers:verification-before-completion` 核实证据，再按 `superpowers:finishing-a-development-branch` 走「本地合并」；不出菜单、不等用户，合并后推主分支。主检出由大家共用，不在那里跑测试；只用 `git merge --ff-only` 快进合并，使主分支指向工作树里审过、测过的提交。不能快进就回第 4 步。删除工作树会一并删除其中被忽略的产物。

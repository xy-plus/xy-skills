## 加载与分档

讨论、调查或可能改代码前，加载本流程、`xy-goal`、`superpowers:brainstorming` 和 `sync-think`；加载完再开始，包括读代码、读文档、运行命令和讨论。`superpowers` 必须只启用 7.0.2。开工前用 `claude plugin list` 核对；不符就停下并按 README 安装固定版本。引用的 skill 与本流程冲突时，以本流程为准。

按 `superpowers:brainstorming` 7.0.2 原文判定任务规模，不另加判据，并告知用户档位和原因，不等回复。快速任务是请求已提供所需信息的任务：跳过讨论、spec 编写和规格审查，从本流程第 2 步开始，仍完成实现、终审、全套测试和合入。Spike（短调查）只答问题，调查中产生的临时代码不并入产品。小改动和项目走完整流程；spec 按规模简写或写全。项目 spec 写完后做 builder check（构建者检查），确认没有会改变计划的未决问题，再审规格。

## 工作流程

1. **明确要求与规格**：通过 `sync-think` 澄清必须由用户决定的事；取得决定后，按已定流程继续，不因等待其他回复停下。按本流程做的任务都用 `xy-goal` 目标契约记录原话、待办和验收条件；当前会话没有契约时先开。按 `xy-goal` 登记事项目录和产物指针；spec、审查报告及子代理 brief 放在任务运行目录，并把目录和契约路径告诉每个子代理。检查功能归属和功能图，按 `xy-repo-map` 确认条目；有图时运行 `repo_map.py check`。写 spec 时逐条注明原话；派方或作者延伸项还要写证据。列明任务拆分、边界、依赖、接口和验收；改用户可见行为、用法或用户规则的事项交用户定。通过 `xy-review` 审规格后再实现。

2. **隔离实现**：确认 `.worktrees/` 已加入仓库忽略规则后，用 `git worktree add .worktrees/<分支> -b <分支>` 建工作树，在其中安装依赖并检查测试基线。不要用 Claude Code 自带 worktree 工具：它曾让隔离目录无法通过路径检查，导致 `sub-agent-runner` 拒绝派发任务。编排者负责规格、拆分和集成。可分给多个代理，但任务说明合起来须覆盖 spec、彼此不重叠，并写清各自边界、依赖、接口和验收；代理只做分配内容，不合入、不再派代理。

   按审过的 spec（快速任务按用户原话）派一个工作子代理实现，并带 `superpowers:test-driven-development`。子代理不会自动继承规矩，派出时把 `rules/xy-iron-law/SKILL.md` 和 `rules/xy-repo-rules/SKILL.md` 交给它并说明照做。任务说明写工作树绝对路径，命令用绝对路径或 `git -C`。卡住或遇 spec 未写的情况，停下报告编排者，由其决定，不等用户。任务说明还写明：互不依赖的测试并行跑；收掉本轮启动的临时进程和后台会话，后台会话用 `claude rm` 删除，不用 `claude stop`；每轮报告只写本轮增量、结果和证据，并列本轮启动的临时进程和后台会话。

   每次改代码时，顺手清理改到的文件及其测试、文档中的零碎，也可检查相关文件；不改变对外行为的小问题直接改。值得重构、会改变对外行为或需要改功能图的大问题先不做，写进所属功能目录的 `TODO.md`，列清问题、不做的代价和完成条件，并在报告中说明。功能没有自己的目录时用功能图登记的第一个目录；没有功能图时写仓库根目录的 `TODO.md`。

   清理项包括但不限于：

   | 类 | 包括但不限于 |
   |---|---|
   | 多余的 | 没人调用的函数、走不到的分支、注释掉的代码、没用的导入变量和参数；只有一个实现的通用接口、没人用的开关、兼容旧用法的分支、只转调一次的包装、删除后的引用和配置残留 |
   | 重复的 | 同一件事写了两份；复制后只改几个值的代码 |
   | 臃肿的 | 过长文件、类、函数和测试；过多参数、过深嵌套和绕弯条件 |
   | 命名 | 看不出意思、和内容不符、同一事物有几种叫法 |
   | 测试 | 重复用例、已删代码的测试、一条测好几件事、看不出目的的断言、靠睡眠和时序的测试、只测实现细节的测试、新增警告 |
   | 注释和文档 | 复述代码、过时或说错、啰嗦、重复的说明；讲原因、约束、警告和用法的说明保留 |
   | 配置和依赖 | 没人读的配置项、没人用的开关、不再使用的依赖 |

   功能图随同改动按 `xy-repo-map` 更新；新功能在同一次改动里登记。修改代码时通过 `xy-review` 的扫描检查改动与相关测试、文档，处理可修的命中。清单参照 [Fowler 代码坏味道](https://courses.cs.duke.edu/compsci308/spring23/resources/Code_Smells_Taxonomy.pdf)、[测试坏味道目录](https://test-smell-catalog.readthedocs.io/) 和 [Google 代码审查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

3. **终审**：实现完成后更新到最新主分支，按 `xy-review` 两步法审查代码改动；主审和剃刀都通过才进入验证。终审报告放在工作流目录的 `code/`，按其规定的对象、组和轮次保存。

4. **验证与收尾**：按 README 测试部分运行全套测试，核对功能图。按 `superpowers:verification-before-completion` 核实证据；终审和全套测试通过后，按 `xy-goal` 验收并更新产物指针。不出菜单、不等用户，按 `superpowers:finishing-a-development-branch` 的本地合并流程只快进合入已审查提交并推送，不能快进就回第 3 步。主检出由大家共用，不在那里跑测试。把 spec 中需要长期保留的信息和实现经验写进维护中的代码注释或文档，避免 spec 删除后遗失。按 `xy-handoff` 收尾后台会话；每项验收或取消前，检查临时进程、配置、工作树和开放事项的使用关系。停止并清理独占资源；共享资源注明使用者，留给最后使用者收尾；长期保留的产物先移到长期位置并记录。删除工作树会一并删除其中被忽略的产物。

## 长期清理

新功能和代码在同一次改动里登记；功能的删除、合并和改名只在 `xy-cleanup` 清扫时做。只改已有功能入口、格式、注释、`what` 或条目时，无需额外询问。清理清单的配置类别名目按 `xy-cleanup` 当前流程维护。

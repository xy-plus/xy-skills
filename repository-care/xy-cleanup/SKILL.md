# 定期清扫

下文 `<xy-cleanup目录>` 和 `<xy-repo-map目录>` 分别指对应技能的 `SKILL.md` 所在目录。

## 清扫流程

清扫维护三样：代码、功能图、用户看过哪些。开新图和迁移都是没有认可记录的清扫；首次建图时所有功能都会进入计划。

1. 用户提供仓根绝对路径、功能 id 列表或「全部」。画图、更新图、看图转来的清扫用「全部」；用户点名局部范围时不得扩大。按 `xy-workflow` 建隔离工作树，清扫修改都在工作树里完成。
2. 图不存在时，按 `xy-repo-map` 从现状起草完整功能图；文件位置不符合「目录怎么摆」时按规则挪动。首次建图一并创建 `repo-map/skip.json`，没有路径时写 `[]`。图已存在但 `check` 失败时，先按报错修图。范围内功能的「要什么」和条目，该改的按 `xy-repo-map`「功能清单」改写，`check` 通过也要做。根功能没有 `used_by_repositories` 时，先问用户一次：从上一级目录的仓和它功能图登记的同级子仓里挑出登记过的仓作为建议，没有就建议不查；按回答写进根功能，不要就写 `[]`。改动提交后再计划。
3. 运行 `python3 <xy-cleanup目录>/changed_features_only/approvals.py plan --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部>`。计划按认可提交与当前提交间的登记、文件归属和跳过边界变化列出要审功能，在环里的功能即使没变也列出。若计划涉及图上没登记的功能或条目，先按 `xy-repo-map` 补成起草、提交，再重新计划。计划为空时告知用户「范围内没有变过的功能」并结束，不建立使用记录、卡片或决定页。
4. 按 README「实际使用」记录逐条推出短跑场景并量测计划功能的直属非测试代码覆盖。Python 用 coverage.py 并统计子进程，Rust 用 llvm-tools；确认不会碰真实账户、写生产数据库或部署服务后才运行。真实数据只读，产物写入副本，能用 dry-run 时就用；无法安全执行的场景记 `ran: false` 和原因。README 中有表格时只把表格数据行算作来源，表格外的列表和段落仅作说明；没有表格时按段落读取来源。每条来源可推出零个或多个场景。

   将 `usage-coverage.json` 写在事项目录。每条来源都列出实际指到的配置、部署和调用方路径，`uses` 是非空字符串数组、一项一条；Git 标签里的文件写成 `<标签>:<路径>`，定时单元写单元文件路径。没有场景时说明 `why_none`，有场景时清空它。成功场景都未执行到的行合并写进 `files.*.missed`，范围按行排序、不相邻且不超出文件。没有任何成功场景时，`files` 必须为空，并把所有直属代码文件列入 `unmeasured`、说明原因。每份直属代码文件恰好出现在 `files` 或 `unmeasured` 一次。

   ```bash
   python3 <xy-cleanup目录>/usage_coverage_check/check_usage_coverage.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --usage-coverage <usage-coverage.json>
   ```

5. 运行 `repo_map.py render` 并发布 `--as 清扫前`，把链接给用户；按 README 跑全套测试，把命令、结果和失败项记作基线。为计划中每个功能出卡片，交用户决定；按回答实施并由主审和剃刀终审。短跑覆盖、清扫前图、基线测试、卡片、决定页和终审都沿这条流程完成。
卡片交齐、拼页前，新开一个只读的复审者，分两段做。第一段不看任何卡片：给它计划、`map-data.json`、`repo-map/skip.json`、覆盖记录、README「实际使用」和根功能 `used_by_repositories`，按「功能卡片」的两头查专找没人用的内容，只看不在跳过名单里的内容，先把结果写定；第二段才给它卡片，核对一张卡要删的东西是否正被别的卡要确认或保留的条目、能力用着。有冲突时交两张卡的子代理先改一致再拼页。第一段找到的交给对应功能的卡片子代理，补进卡片 `unused`，或在 `used` 里写明为什么其实在用，再拼页。
6. 终审和全套测试通过后、合入前运行 `record --mainline <主线分支或提交> --decisions <本次决定清单> --answers <回答文件>`，把回答覆盖且由本分支改动的功能记录为当前 HEAD。出页后只把主线合并进清扫分支，不变基（计划提交必须还在历史里）；已经变基的，重新计划、出卡和出页。
7. 功能图已由 AI 更新但只需用户确认、功能图不存在/错误/过期，都按这条流程处理：先修图并提交，再计划，再由用户确认卡片和起草文字。

## 功能卡片

计划中每个功能一张卡片，包括计划中的上级功能。卡片子代理只读工作树，不改代码。

每张卡片只写人判断这个功能是否需要时必须知道的内容，每条一句话。除两处 `evidence` 外都给仓库主人看，照 `xy-repo-map`「功能清单」的写法写：东西叫它的名字（命令、脚本、配置），使用者叫 README「实际使用」里的名字，不用「来源」「短跑」「覆盖」「入口」这些本 skill 的说法。例：

- 改前：创建策略工作树的独立入口没有被当前实际来源或其他仓内调用者使用。
- 改后：`tools/worktree/worktree.sh` 没人调：实盘、在维护的 baseline 和各仓脚本都不用它。

直属行数（`map-data.json` 中 `lines.own` 四项合计）少的相邻功能可以交同一子代理，合计不超过约 8000 行。

同一个环里的功能（`map-data.json` 里 `cycle_with` 互相列出）交同一个子代理。

给卡片子代理这些输入：

- 本节卡片说明、功能 id 和工作树绝对路径。
- `map-data.json`、覆盖记录、README「实际使用」来源，以及根功能 `used_by_repositories` 登记的仓（反查要查的其他仓）。
- 计划列出的上次认可提交、本仓历次清扫决定原件、本功能 `why.from` 原件。

卡片写到 `<事项目录>/cards/<功能 id>.json`，照这个字段和类型写：

```json
{
  "feature": "功能 id",
  "used": [{"who": "现在谁在用它、用来做什么", "evidence": "查了哪份配置、哪条命令，结果如何"}],
  "unused": [
    {
      "what": "一句话说明没人用的东西",
      "evidence": "查看 config/runtime.yml 未选它，查 scripts/run-app.sh 未调用它",
      "reverse_search": "本仓和用到本仓的其他仓的各分支、tag、发布包里只有 tests/test_app.py 引用它，它自己的说明没写别的用法",
      "lines": 12,
      "risk": "删除可能影响的内容"
    }
  ],
  "changed": ["一句话一条：上次认可以来变了什么；没有认可记录写 []"],
  "todo": ["一句话一条：本功能 TODO.md 里攒下的大问题"],
  "map_issues": ["一句话一条：功能图哪里写偏、照建议怎么改"],
  "suggestion": ["一句话一件：选「照建议」会做的代码、测试、文档改动"],
  "cross_feature_changes": [{"feature": "别的功能 id", "change": "一句话说明要改它什么"}],
  "item_changes": [{"item": "本功能条目 id", "text": "改后的完整文字"}],
  "recommended": "照建议"
}
```

`lines` 是非负整数，`used` 最多三条；没有连带改动或条目改动时相应字段写 `[]`。`cross_feature_changes.feature` 必须是图上别的功能，`change` 不能为空。`item_changes.item` 按功能 id 格式，同卡不重复；`text` 非空且只占一行。

`map_issues` 写图上没写到、写了没做到、`what` 与条目矛盾、理由不成立、分组不合适和非「等你拍板」的功能图标记；只改功能图文字的改动只写在这里，不再列进 `suggestion`。「等你拍板」对应的起草条目由拼页命令自动列出，不写进 `map_issues`。建议会改到别的功能的代码、测试、文档或 TODO 时，逐条写进 `cross_feature_changes`，不能只写在 `risk` 里。新增、改写条目一律写进 `item_changes`；`suggestion` 和 `map_issues` 里不写条目原文，也不写「保留起草」「改成确认」这类状态。

功能提供的模式、选项、配置、输出、入口、旧格式、旧用法、额外校验和兜底按人能理解的粒度归类，每样只进 `used` 或 `unused` 一处。实际使用证据只认 README 来源中明确选到或跑到的内容、成功短跑覆盖到的内容及这些来源实际使用的调用方；测试或文档提及、理论上可达、研究代码调用、功能条目描述都不能证明在用。

判「没人用」要两头查。往下追：逐条查覆盖记录各来源的 `uses`，配置类打开文件确认是否选用；部署、调用方和 README 写出的手工命令都查是否调用，包括命令及子命令入口。往上反查：从待删内容出发，在本仓和根功能 `used_by_repositories` 登记的仓里，查各分支、tag、发布产物和它自己的说明中引用它的地方；没登记的只查本仓，登记的仓有找不到的就不判没人用。反查到登记外的使用者，按在用写进 `used`，并报告登记缺口：漏登在本仓 README「实际使用」的，在 `suggestion` 里补登；漏登在别的仓的，在依据里写明哪个仓、漏了什么，由那个仓的清扫补登。反查到的测试不算在用，删时要连带改的写进 `risk`。`evidence` 写往下追、`reverse_search` 写往上反查各查了哪些地方、结果如何。`missed` 只帮助定位待查代码，没量过、短跑没跑成或未执行到都不能单独证明没人用。两头都查完、都没找到使用者，就是没人用的正面证据，列进 `unused`；有一头查不完（例如配置读不到、登记的仓找不到），才不列 `unused`，在 `used` 里写明哪头没查完。

在环里的功能，这一侧有要改的，`suggestion` 写这次怎么解开成环的 import：把哪段挪到哪个功能、改成谁依赖谁，以及解开后从根功能 `existing_cycle_imports` 删掉哪几条，并推荐「照建议」；同一个环的各卡改法要配套。这一侧不用改的不写。

有正面证据的未使用内容才列进 `unused` 和 `suggestion`。`suggestion` 只列「照建议」会做的改动，`unused.risk` 写删除风险和跨功能影响；建议用户选「留」时，保留理由及出处也写在 `unused.risk` 里。`used.who` 不写怎么查的，不复述功能条目。`lines` 写建议删除后能少的代码、测试和文档行数总和。

交卡前核对 `suggestion` 和 `map_issues` 里的改动互不矛盾；例如补一条功能要求时，不能同时删掉验证它的唯一测试或实现。

拼页前由第 5 步的只读复审者做跨卡核对：一张卡要删的东西是否正被别的卡要确认或保留的条目、能力用着；有冲突时交两张卡的子代理先改一致再拼页。

`changed` 对比上次认可提交与当前功能图和文件，没有认可记录时写 `[]`；`todo` 按 `map-data.json` 的直属文件归属读取。推荐「照建议」时 `suggestion` 和 `map_issues` 不能都空；推荐「不要这个功能」只适用于没有子功能的功能。

修改卡片问法后，按 [review-misses.md](review-misses.md) 在表中所列功能文字未改的提交上重做卡片，检查「图上写偏」能否发现旧问题。

## 拼成一页

运行 `feature_cards/feature_cards.py` 校验卡片并生成决定清单：

```bash
python3 <xy-cleanup目录>/feature_cards/feature_cards.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --cards <卡片.json…> --output <decisions.json>
```

命令重新计算计划，只接受计划内每个功能恰好一张卡片；字段、字符串、删除行数、建议和功能层级都须有效。计划为空、缺卡片、多卡片、重复卡片、未知功能和不完整字段都会拒绝生成页面。

每项决定的标题按功能图从根到本功能的顺序，用「 › 」连接各级标题；范围外的上级仍列出，根功能只显示自身标题。

每个功能一项决定，选项为「照建议」「留」「留，下次还问我」「按我写的改」；卡片没有建议时不列「照建议」，没有子功能的功能另有「不要这个功能」，上级不能选择删除，避免父子功能回答相冲突或引发未审批的级联删除。建议改或删的排前一组，建议留的排后一组。每项前面列「要什么」「谁在用」（含没人用）和「照建议会做」；有连带改动或要改的条目时列出内容，被连带的功能也在本页时注明来源；在环里的功能多一行「互相引用」。有认可记录的功能再逐条列出起草条目，改过的文字附上次认可的写法。其余（理由、变了什么、依据、可减行数、风险、图上要改的地方、TODO 大问题、没有认可记录的功能的起草条目）收在一个默认收起的块里，标题写各类条数。

| 选择 | 按回答处理 |
|---|---|
| 照建议 | （含连带改动）做卡片 `suggestion` 和 `map_issues` 里写的每件事，含 `cross_feature_changes` 列出的连带改动；把 `item_changes` 按原文写进图并标「确认」。 |
| 留 | 不删改代码、测试、文档或 TODO，也不做建议中的事。卡片上起草的理由和条目仍会照写确认。 |
| 留，下次还问我 | 不删改代码、测试、文档，不确认起草；有备注时记进该功能 `TODO.md`，没备注不记；不记认可，下次清扫会因没有认可记录再出卡片。 |
| 按我写的改 | 以建议为基础按备注修改；含义不明时先问。`item_changes` 按备注改后写进图并标「确认」。 |
| 不要这个功能 | 删除该叶功能的代码、测试、文档、TODO 和功能图条目。 |

用户不在页上逐个点、只在对话中回复「都按你的建议（来吧）」时，走以下步骤：

1. 停止后台运行的 `decision_page/decision_page.py ask`，并清理本次页面挂载。
2. 查找 xy-goal 记录这句话的原话文件；没有时把对话原文保存到事项目录。将该文件路径记作决定原件。
3. 每个功能按卡片上的推荐项处理，只做卡片列出的事，不多做。
4. 对仍保留在功能图中的功能，将卡片列出的起草条目 `status` 和起草理由 `source` 改为「确认」，`why.from` 写决定原件路径。

后台运行 `decision_page/decision_page.py ask`，把链接给用户；退出码为 0 后读取回答文件，原样留在事项目录作为决定原件。

## 按回答修改

按 `xy-workflow` 实施：把回答文件和卡片交实施者，让它按用户选项及卡片描述定位实现。

「按我写的改」以建议为基础，备注意思不明确时先问；备注改过的起草文字按修改后的内容确认。

卡片 `cross_feature_changes` 列出的连带改动，随该卡的「照建议」一起获批，即使被连带的功能选了「留」；没列出的连带改动若会改动已选「留」的功能，先停下询问用户，把用户回答原样交终审。

被连带改动的功能选了「留，下次还问我」时，即使该改动已列在「照建议」卡片里，也先不做改它的部分，停下问用户，并把回答原样交终审；这条优先于随「照建议」获批。

终审时把回答文件和对应卡片交给两位审查者。主审逐个功能核对改动是否符合选择：「留」和「留，下次还问我」的内容没有改动；需要询问的影响按用户原话处理。网页上选「照建议」或「按我写的改」时，把 `item_changes` 写进图并标「确认」；选「留」不写 `item_changes`。「留，下次还问我」不改图，也不确认起草。网页上选「照建议」「留」或「按我写的改」时，该功能列出的起草条目（包括收起的）`status` 和起草理由 `source` 都改成「确认」，`from` 记录回答文件的 `#answers.<功能 id>`；按上一段的对话批量答复处理时，起草理由的 `from` 记录决定原件路径。完成终审和全套测试后，按「认可记录」运行 `record`；`repo-map/approved.json` 随改动一起提交。

汇报前运行 `python3 <xy-repo-map目录>/repo_map.py render`，再用 `publish --as 清扫后` 和 `publish --as 当前` 更新并发布图。

简要列出：

- 每个功能改前后的行数，以及全仓前后行数和净减。
- 删除内容、未做事项及原因。
- 留到下次清扫的功能（主线带来改动）。
- 测试结果和用户选择保留的标记。
- 反查发现的登记缺口：漏登的使用者，以及应登记在哪个仓的 README「实际使用」。

## 认可记录

`repo-map/approved.json` 保存各功能上次经用户确认时的 40 位小写完整提交号；文件不存在即无记录。清扫终审和全套测试通过后、合入前运行 `record`；它把决定清单中已回答且仍在图里的功能记录为当前 HEAD。

`plan` 要求已跟踪文件没有改动（未跟踪文件不影响计划），并从 `HEAD:repo-map/approved.json` 读取记录。文件不存在视为无记录。记录格式错误、提交不存在或不是 HEAD 的祖先时退出 1。出页后只把主线合并进清扫分支，不变基（计划提交必须还在历史里）；已经变基的，重新计划、出卡和出页。

规划时显式给出仓库、范围和审查方式：

```sh
python3 <xy-cleanup目录>/changed_features_only/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <范围> \
  --review 变过的
```

`全部` 列范围内每个功能；`变过的` 列无记录、认可后有变化或在环里的功能。指定上级会递归包含子孙。计划每行是 `功能 id<TAB>原因<TAB>上次认可提交`，无记录写「无」；空计划说明范围内功能数。

计划逐项比较功能登记的 `title`、`what`、`why`、`items`、子功能 id 集合，根功能另比 `subrepositories` 和 `external_dependencies`。`directory` 字符串本身不比较，文件归属变化由文件检查发现。对每份文件，分别按记录提交和 HEAD 两版功能图计算直属归属：同一路径对应同一份文件；Git 判定的改名把旧、新路径对应起来。归属变化、内容或权限位变化、增加和删除都会让相关功能进入计划；同一功能内纯改名不算变化。功能清单、认可文件、跳过名单和两版各自跳过名单命中的路径不作为普通文件计算。

跳过名单按解析后的路径集合比较；格式或顺序变化不算，集合变化属于根功能的计划变化。`repo-map/features.json` 另按登记字段逐项比较。遇到记录提交中的旧功能图格式、范围外登记变化、范围外归属变化或范围外跳过边界变化时，退出 1 并说明应扩大到「全部」或由用户重定范围；不自行扩大范围。`--review 变过的` 不猜旧格式下文件的归属。

`record` 只接受本次 `feature_cards.py` 生成且 `decision_page.py ask` 使用的决定清单和对应回答文件：

```sh
python3 <xy-cleanup目录>/changed_features_only/approvals.py record \
  --repo <仓根绝对路径> \
  --mainline <主线分支或提交> \
  --decisions <决定清单.json> \
  --answers <回答文件.json>
```

`record` 复用决定页校验器验证决定清单和完整回答；回答 `title` 必须与清单 `title` 一致，仓名取主检出名。清单 `title` 固定带计划提交，回答只能用于一次：计划提交须沿 HEAD 的第一父链可达；清单里已有认可记录的功能若记录提交等于或晚于计划提交，拒绝再次使用。工作树必须完全干净，且仓库必须是隔离工作树，主检出拒绝记录。回答只覆盖清单中完整回答且仍在功能图里的功能；清单外仍有效的认可记录保留，图中已不存在的 id 删除。主线参数必须显式提供可解析的分支或提交。取 `B = merge-base HEAD <主线>`；若 B 不是计划提交的祖先，就比较 `merge-base <计划提交> B` 到 B 之间的文件和功能登记变化；快进和普通合并都按此识别。被主线改动到的已回答功能保留原认可、不记为当前 HEAD，并逐个列为「留到下次清扫：<功能 id>（主线带来改动）」。其他功能记为当前 HEAD；理由或条目仍是「起草」只会挡住实际要记录的功能。

选择「留，下次还问我」的功能不记为当前 HEAD，并从 `repo-map/approved.json` 删除已有记录；这项优先于主线改动时保留认可的规则，也不受起草状态阻挡。它会在下次清扫因没有认可记录再次出卡。

对话中一次回复「都按你的建议（来吧）」时，按卡片推荐项生成与清单 `title` 相同的回答文件，备注记录该句原话文件路径，再走同一校验和记录步骤。回答完成一次记录后不可复用。两条命令退出码：`0` 成功，`1` 仓库、清单、记录或回答有问题，`2` 参数错误。

## 网页决定

决定清单的 `title` 由卡片工具写入主检出仓名和计划提交。把它交给页面命令，并显式提供平台站点名和一个尚不存在的回答文件：

```sh
python3 <xy-cleanup目录>/decision_page/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令返回的链接交给用户。决定清单字段和嵌套格式如下，不得加减字段：

```json
{
  "title": "决定标题",
  "intro": ["页面说明"],
  "groups": [{
    "title": "分组标题",
    "notes": ["分组说明"],
    "items": [{
      "id": "feature-id",
      "title": "条目标题",
      "lines": ["要决定的内容"],
      "options": ["确认", "按我写的改"],
      "recommended": "确认",
      "details": null,
      "compare": null
    }]
  }],
  "footnotes": [{"title": "补充说明", "lines": ["说明"]}]
}
```

文字不可空，条目编号全局唯一；每条至少两个不同选项，建议项必须在选项中，且至少有一组、每组至少一条。

每项必须有 `details`：`null` 表示不显示补充块；对象只含非空 `title` 和非空字符串数组 `lines`，页面默认收起、只显示标题，点开后逐行显示内容。含制表符的行排成两栏，制表符前是标签。

普通条目的 `compare` 为 `null`；需要逐段对照的条目用非空数组，每项恰为 `lines`、`before`、`after`，例如范围 `guide.md:1-4`。同一条内范围须为同一路径、递增且不重叠；`before` 非空，`after` 可空（表示删除）。数组顺序即显示顺序，相邻未改块合并为「没改的 N 段」；删除项划线显示原文，改写项先划线原文再显示新文；页面顶部统计非空白字符的原文、改写和减少量，不自动猜段落对应关系。

回答文件按条目 id 保存选择和备注：

```json
{
  "title": "清扫决定：仓名 计划提交 <40 位提交号>",
  "answers": {
    "功能-id": {"option": "留", "note": ""}
  }
}
```

按编号读取回答。`note` 非空时以用户填写为准，`option` 仅作参考；意思不明先询问。回答文件留在事项目录作为决定原件。回答写好后，页面换成一张静态的「已收到」页（锁定，显示提交的选择和备注），命令随即退出；静态页留在门户上，下次同名决定页会先换掉它。退出码：`0` 回答文件已写好；`1` 挂载或运行失败；`2` 参数或决定清单错误、回答文件已存在，或其目录不存在、不可写或不支持硬链接。

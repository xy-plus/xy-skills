# 定期清扫

下文 `<xy-cleanup目录>` 和 `<xy-repo-map目录>` 分别指对应技能的 `SKILL.md` 所在目录。

## 清扫流程

清扫维护三样：代码、功能图、用户看过哪些。开新图和迁移都是没有认可记录的清扫；首次建图时所有功能都会进入计划。

1. 用户提供仓根绝对路径、功能 id 列表或「全部」。画图、更新图、看图转来的清扫用「全部」；用户点名局部范围时不得扩大。按 `xy-workflow` 建隔离工作树，清扫修改都在工作树里完成。
2. 图不存在时，按 `xy-repo-map` 从现状起草完整功能图；文件位置不符合「目录怎么摆」时按规则挪动。首次建图一并创建 `repo-map/skip.json`，没有路径时写 `[]`。图已存在但 `check` 失败时，先按报错修图；图错误修正并提交后再计划。
3. 运行 `python3 <xy-cleanup目录>/changed_features_only/approvals.py plan --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部>`。计划按认可提交与当前提交间的登记、文件归属和跳过边界变化列出要审功能。若计划涉及图上没登记的功能或条目，先按 `xy-repo-map` 补成起草、提交，再重新计划。计划为空时告知用户「范围内没有变过的功能」并结束，不建立使用记录、卡片或决定页。
4. 按 README「实际使用」记录逐条推出短跑场景并量测计划功能的直属非测试代码覆盖。Python 用 coverage.py 并统计子进程，Rust 用 llvm-tools；确认不会碰真实账户、写生产数据库或部署服务后才运行。真实数据只读，产物写入副本，能用 dry-run 时就用；无法安全执行的场景记 `ran: false` 和原因。README 中有表格时只把表格数据行算作来源，表格外的列表和段落仅作说明；没有表格时按段落读取来源。每条来源可推出零个或多个场景。

   将 `usage-coverage.json` 写在事项目录。每条来源都列出实际指到的配置、部署和调用方路径，`uses` 是非空字符串数组、一项一条；Git 标签里的文件写成 `<标签>:<路径>`，定时单元写单元文件路径。没有场景时说明 `why_none`，有场景时清空它。成功场景都未执行到的行合并写进 `files.*.missed`，范围按行排序、不相邻且不超出文件。没有任何成功场景时，`files` 必须为空，并把所有直属代码文件列入 `unmeasured`、说明原因。每份直属代码文件恰好出现在 `files` 或 `unmeasured` 一次。

   ```bash
   python3 <xy-cleanup目录>/usage_coverage_check/check_usage_coverage.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --usage-coverage <usage-coverage.json>
   ```

5. 运行 `repo_map.py render` 并发布 `--as 清扫前`，把链接给用户；按 README 跑全套测试，把命令、结果和失败项记作基线。为计划中每个功能出卡片，交用户决定；按回答实施并由主审和剃刀终审。短跑覆盖、清扫前图、基线测试、卡片、决定页和终审都沿这条流程完成。
6. 终审和全套测试通过后、合入前运行 `record --decisions <本次决定清单> --answers <回答文件>`，把回答覆盖的功能记录为当前 HEAD。若之后变基，须在变基后的提交上重新终审并重跑 `record`。
7. 功能图已由 AI 更新但只需用户确认、功能图不存在/错误/过期，都按这条流程处理：先修图并提交，再计划，再由用户确认卡片和起草文字。

## 功能卡片

计划中每个功能一张卡片，包括计划中的上级功能。卡片子代理只读工作树，不改代码。

每张卡片只写人判断这个功能是否需要时必须知道的内容：每条一句话，不写函数名、文件名或代码行号。直属行数（`map-data.json` 中 `lines.own` 四项合计）少的相邻功能可以交同一子代理，合计不超过约 8000 行。

给卡片子代理这些输入：

- 本节卡片说明、功能 id 和工作树绝对路径。
- `map-data.json`、覆盖记录、README「实际使用」来源。
- 计划列出的上次认可提交、本仓历次清扫决定原件、本功能 `why.from` 原件。

卡片写到 `<事项目录>/cards/<功能 id>.json`，照这个字段和类型写：

```json
{
  "feature": "功能 id",
  "used": ["几句概括实际用到的内容和使用者，约五句以内"],
  "unused": [
    {
      "what": "一句话说明没人用的东西",
      "evidence": "查看 config/runtime.yml 未选它，查 scripts/run-app.sh 未调用它",
      "lines": 12,
      "risk": "删除可能影响的内容"
    }
  ],
  "changed": ["一句话一条：上次认可以来变了什么"],
  "todo": ["一句话一条：本功能 TODO.md 里攒下的大问题"],
  "map_issues": {
    "why": "成立；否则写理由缺了什么，例如只抱怨或报进度、只说设备或愿望、只说了几项中的一项",
    "what": "一致；否则写它与 title、why、条目或子功能矛盾的地方",
    "group": "合适；否则写放错上级或漏掉该归入本组的功能",
    "items": ["条目没写到、写了没做到或非「等你拍板」的标记，一句一条"]
  },
  "suggestion": ["一句话一件：选「照建议」会做的改动"],
  "recommended": "照建议"
}
```

`feature` 是字符串；`used`、`changed`、`todo`、`suggestion` 是字符串数组；`map_issues` 是必填对象，`why`、`what`、`group` 是非空字符串，`items` 是字符串数组；`unused` 是对象数组，其中 `what`、`evidence`、`risk` 是字符串，`lines` 是非负整数。

`map_issues.why` 写「成立」，或具体说明理由为何不成立；`map_issues.what` 写「一致」，或指出它与 title、why、条目、子功能矛盾的地方；`map_issues.group` 写「合适」，或说明放错上级、漏掉该归入本组的功能。`map_issues.items` 逐条写功能条目没写到、写了没做到，以及非「等你拍板」的功能图标记。拼页只显示不成立的 why、what、group 栏和 items；通过的栏不列出。「等你拍板」对应的起草条目由拼页命令自动列出，不写进 items。

功能提供的模式、选项、配置、输出、入口、旧格式、旧用法、额外校验和兜底按人能理解的粒度归类，每样只进 `used` 或 `unused` 一处。实际使用证据只认 README 来源中明确选到或跑到的内容、成功短跑覆盖到的内容及这些来源实际使用的调用方；测试或文档提及、理论上可达、研究代码调用、功能条目描述都不能证明在用。

判「没人用」必须逐条查覆盖记录各来源的 `uses`：配置类打开文件确认是否选用；部署、调用方和 README 写出的手工命令都查是否调用，包括命令及子命令入口。`evidence` 写明检查的路径和结果。`missed` 只帮助定位待查代码，没量过、短跑没跑成或未执行到都不能单独证明没人用。查完仍无正面证据的按「用到」写，注明「没量过」或「短跑没走到」；仍不能判断时存疑从留。

有正面证据的未使用内容才列进 `unused` 和 `suggestion`。`suggestion` 只列「照建议」会做的改动，`unused.risk` 写删除风险和跨功能影响；建议用户选「留」时，在其中写保留理由及出处。`used` 约五句以内，概括实际用途和使用者，不复述功能条目。`lines` 写建议删除后能少的代码、测试和文档行数总和。

交卡前核对 `suggestion` 中的改动互不矛盾；例如补一条功能要求时，不能同时删掉验证它的唯一测试或实现。

`changed` 对比上次认可提交与当前功能图和文件；`todo` 按 `map-data.json` 的直属文件归属读取。推荐「照建议」时建议列表不能空；推荐「不要这个功能」只适用于没有子功能的功能。

修改卡片问法后，按 [review-misses.md](review-misses.md) 在表中所列功能文字未改的提交上重做卡片，检查「图上写偏」能否发现旧问题。

## 拼成一页

运行 `feature_cards/feature_cards.py` 校验卡片并生成决定清单：

```bash
python3 <xy-cleanup目录>/feature_cards/feature_cards.py --repo <仓根绝对路径> --scope <功能 id…|全部> --review <变过的|全部> --cards <卡片.json…> --output <decisions.json>
```

命令重新计算计划，只接受计划内每个功能恰好一张卡片；字段、字符串、删除行数、建议和功能层级都须有效。计划为空、缺卡片、多卡片、重复卡片、未知功能和不完整字段都会拒绝生成页面。

它按计划顺序为每个功能生成一项决定和固定选项；上级没有「不要这个功能」。命令从功能图自动列出本次纳入原因、功能理由及所有起草条目，改写过的起草条目附上次认可的文字。这样用户实际看到将确认的文字，卡片也不会漏列。

每个功能只做一项决定，页面选项为「照建议」「留」「按我写的改」；没有子功能的功能另有「不要这个功能」。上级不能选择删除，避免父子功能回答相冲突或引发未审批的级联删除。

| 选择 | 按回答处理 |
|---|---|
| 照建议 | 做卡片建议中的每件事。 |
| 留 | 不删改代码、测试、文档或 TODO，也不做建议中的事。卡片上起草的理由和条目仍会照写确认。 |
| 按我写的改 | 以建议为基础按备注修改；含义不明时先问。 |
| 不要这个功能 | 删除该叶功能的代码、测试、文档、TODO 和功能图条目。 |

用户不在页上逐个点、只在对话中回复「都按你的建议（来吧）」时，走以下步骤：

1. 停止后台运行的 `decision_page/decision_page.py ask`，并清理本次页面挂载。
2. 查找 xy-goal 记录这句话的原话文件；没有时把对话原文保存到事项目录。将该文件路径记作决定原件。
3. 每个功能按卡片上的推荐项处理，只做卡片列出的事，不多做。
4. 对仍保留在功能图中的功能，将卡片列出的起草条目 `status` 和起草理由 `source` 改为「确认」，`why.from` 写决定原件路径。

把「前三项会确认本页列出的起草文字，包括选择「留」时」写在决定页顶部。后台运行 `decision_page/decision_page.py ask`，把链接给用户；退出码为 0 后读取回答文件，原样留在事项目录作为决定原件。

## 按回答修改

按 `xy-workflow` 实施：把回答文件和卡片交实施者，让它按用户选项及卡片描述定位实现。

「按我写的改」以建议为基础，备注意思不明确时先问；备注改过的起草文字按修改后的内容确认。

删除任何内容（包括「不要这个功能」）若会改动其他已选「留」功能的代码、测试、文档或 TODO，哪怕只去掉一个引用，都先停下询问用户；把用户回答原样交终审。

终审时把回答文件和对应卡片交给两位审查者。主审逐个功能核对改动是否符合选择：「留」的内容没有改动；需要询问的影响按用户原话处理。网页上选择前三项时，该功能列出的起草条目 `status` 和起草理由 `source` 都改成「确认」，`from` 记录回答文件的 `#answers.<功能 id>`；按上一段的对话批量答复处理时，起草理由的 `from` 记录决定原件路径。完成终审和全套测试后，按「认可记录」运行 `record`；`repo-map/approved.json` 随改动一起提交。

汇报前运行 `python3 <xy-repo-map目录>/repo_map.py render`，再用 `publish --as 清扫后` 和 `publish --as 当前` 更新并发布图。

简要列出：

- 每个功能改前后的行数，以及全仓前后行数和净减。
- 删除内容、未做事项及原因。
- 测试结果和用户选择保留的标记。

## 认可记录

`repo-map/approved.json` 保存各功能上次经用户确认时的 40 位小写完整提交号；文件不存在即无记录。清扫终审和全套测试通过后、合入前运行 `record`；它把决定清单中已回答且仍在图里的功能记录为当前 HEAD。

`plan` 要求干净工作树，并从 `HEAD:repo-map/approved.json` 读取记录。文件不存在视为无记录。记录格式错误、提交不存在或不是 HEAD 的祖先时退出 1；若基线提交已经不是祖先，说明变基后须在变基后的提交上重新终审并记录。

规划时显式给出仓库、范围和审查方式：

```sh
python3 <xy-cleanup目录>/changed_features_only/approvals.py plan \
  --repo <仓根绝对路径> \
  --scope <范围> \
  --review 变过的
```

`全部` 列范围内每个功能；`变过的` 列无记录或认可后有变化的功能。指定上级会递归包含子孙。计划每行是 `功能 id<TAB>原因<TAB>上次认可提交`，无记录写「无」；空计划说明范围内功能数。

计划逐项比较功能登记的 `title`、`what`、`why`、`items`、子功能 id 集合，根功能另比 `subrepositories` 和 `external_dependencies`。`directory` 字符串本身不比较，文件归属变化由文件检查发现。对每份文件，分别按记录提交和 HEAD 两版功能图计算直属归属：同一路径对应同一份文件；Git 判定的改名把旧、新路径对应起来。归属变化、内容或权限位变化、增加和删除都会让相关功能进入计划；同一功能内纯改名不算变化。功能清单、认可文件、跳过名单和两版各自跳过名单命中的路径不作为普通文件计算。

跳过名单按解析后的路径集合比较；格式或顺序变化不算，集合变化属于根功能的计划变化。`repo-map/features.json` 另按登记字段逐项比较。遇到记录提交中的旧功能图格式、范围外登记变化、范围外归属变化或范围外跳过边界变化时，退出 1 并说明应扩大到「全部」或由用户重定范围；不自行扩大范围。`--review 变过的` 不猜旧格式下文件的归属。

`record` 只接受本次 `feature_cards.py` 生成且 `decision_page.py ask` 使用的决定清单和对应回答文件：

```sh
python3 <xy-cleanup目录>/changed_features_only/approvals.py record \
  --repo <仓根绝对路径> \
  --decisions <决定清单.json> \
  --answers <回答文件.json>
```

`record` 复用决定页校验器验证决定清单和完整回答；回答 `title` 必须与清单 `title` 一致。清单 `title` 固定带计划提交，回答只能用于一次：计划提交须是 HEAD 的祖先；清单里已有认可记录的功能若记录提交等于或晚于计划提交，拒绝再次使用。工作树必须干净，且仓库必须是隔离工作树，主检出拒绝记录。回答只覆盖清单中完整回答且仍在功能图里的功能；清单外仍有效的认可记录保留，图中已不存在的 id 删除。将这些功能记为当前 HEAD；功能的理由或条目仍有「起草」时拒绝记录。

对话中一次回复「都按你的建议（来吧）」时，按卡片推荐项生成与清单 `title` 相同的回答文件，备注记录该句原话文件路径，再走同一校验和记录步骤。回答完成一次记录后不可复用。两条命令退出码：`0` 成功，`1` 仓库、清单、记录或回答有问题，`2` 参数错误。

## 网页决定

决定清单的 `title` 由卡片工具写入仓名和计划提交。把它交给页面命令，并显式提供平台站点名和一个尚不存在的回答文件：

```sh
python3 <xy-cleanup目录>/decision_page/decision_page.py ask \
  --decisions <决定清单.json> \
  --name <站点名> \
  --answers <尚不存在的回答文件.json>
```

把命令返回的链接交给用户。决定清单字段和嵌套格式如下，不得加减字段：

```json
{
  "title": "决定标题",
  "intro": ["页面说明"],
  "groups": [{
    "title": "分组标题",
    "notes": ["分组说明"],
    "items": [{
      "id": "feature-id",
      "title": "条目标题",
      "lines": ["要决定的内容"],
      "options": ["确认", "按我写的改"],
      "recommended": "确认",
      "compare": null
    }]
  }],
  "footnotes": [{"title": "补充说明", "lines": ["说明"]}]
}
```

文字不可空，条目编号全局唯一；每条至少两个不同选项，建议项必须在选项中，且至少有一组、每组至少一条。

普通条目的 `compare` 为 `null`；需要逐段对照的条目用非空数组，每项恰为 `lines`、`before`、`after`，例如范围 `guide.md:1-4`。同一条内范围须为同一路径、递增且不重叠；`before` 非空，`after` 可空（表示删除）。数组顺序即显示顺序，相邻未改块合并为「没改的 N 段」；删除项划线显示原文，改写项先划线原文再显示新文；页面顶部统计非空白字符的原文、改写和减少量，不自动猜段落对应关系。

回答文件按条目 id 保存选择和备注：

```json
{
  "title": "清扫决定：仓名 计划提交 <40 位提交号>",
  "answers": {
    "功能-id": {"option": "留", "note": ""}
  }
}
```

按编号读取回答。`note` 非空时以用户填写为准，`option` 仅作参考；意思不明先询问。回答文件留在事项目录作为决定原件。退出码：`0` 回答文件已写好；`1` 挂载或运行失败；`2` 参数或决定清单错误、回答文件已存在，或其目录不存在、不可写或不支持硬链接。

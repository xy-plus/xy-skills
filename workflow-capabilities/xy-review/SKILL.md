# 对抗审查

## 派审查

常规审查派主审和剃刀各一人，研究任务只派主审。两人用独立会话、并行只读；主审按 `xy-iron-law` 第 1、2 条和仓库规范审查，剃刀按铁律第 3 条判断必要性。代码审查的剃刀还按 `xy-workflow` 清理清单逐项回应扫描命中。一个会话只审一个对象；同一对象的下一轮和代码终审续用原会话，组未通过并判因后新开会话。

每个对象分两步派审：

1. **读对象前推导**：只给上游，不给对象位置。上游包括契约目录、相关原话及原件位置、短回答的题干和所选选项、被审仓功能图中相关功能的登记；审代码时再给已审 spec。说明对象是什么（spec、代码改动或既有功能），而不是把待审内容贴给审查者。主审和剃刀各写 `<对象目录>/group<G>/round1/derivation-main.json` 或 `derivation-razor.json`，运行 `review_report_check/check.py` 校验后再看对象。
2. **对照对象**：同一会话继续，给出本轮 `submitted*` 版本和路径。审查者只按本轮目录中的推导对照对象并写报告。后续轮先把上一轮推导复制到本轮目录；若收到新的用户原话，在副本上改写。报告只对照本轮目录中的推导。spec 通过后的代码终审是新对象，仍先写代码推导再看代码。

派审说明不得预设结论或把范围判断写成事实。新对象的上游判断由审查者独立完成；报告作者、提交说明和作者注释不能代替对象证据。短回答必须回到原件核对。派审资料中的转述不能替代原话原件。

审查对象包括代码和文档（规则、spec、SKILL.md、README、TODO、注释）；每项要求对两者相同：追根、查遗漏与误用、合并同根内容、同一件事只留一处，有更简洁的写法或结构就改。文档须与实际代码互核。

规格、审查报告和送审版本放在任务运行目录，按 `<对象目录>/group<G>/round<R>/` 保存；G 从 1 起，R 仅限 1、2、3。每轮保存一个 `submitted*` 文件，写清其不可变版本及路径，或保存原文。主审报告名为 `review-main.json`，剃刀报告名为 `review-razor.json`。审查者只读；写报告前核对路径、文件名和目标是否已存在，不能覆盖已有报告。

审 spec 时，主审检查拆分、边界和共享上下文，剃刀检查是否拆得过细。审代码时，作者先运行 `python3 <xy-review skill目录>/change_scan/scan_changes.py --repo <工作树绝对路径> --base <本轮基准提交>`，把标准输出原样存入本轮 `submitted-scan.json`。剃刀检查改到的文件及其测试、文档和其中原有的零碎；代码能从在用入口追到，只证明它该在，不证明重复或冗余写法应保留。主审与剃刀都通过后才进入下一步。

主审按独立推导检查遗漏、偏离、做成别的、补丁和同根特例；剃刀区分用户目标与实现必要性，比较保留项的实际收益、代价和更小做法。用户原话说明目标，不自动证明实现必要；测试或研究产物也不单独构成保留理由。保留旧项可依据真实在用入口或已知用户要求，仍要检查有无重复和更小做法。

审被审仓的 `repo-map/features.json` 时，主审运行 `repo_map.py check`，核对用户可见变化是否登记，新增或改写条目的状态和理由出处是否正确。新增或改动的 `why.source` 为「原话」时，`quote` 必须逐字出现在 `from` 指向的原件；为「确认」时，回答必须明确确认该文字。引用 `answers.json` 按键写 `#answers.<键>`。剃刀把新增功能当作实体审查。

主审、剃刀引用规范条款时，`source` 写 `xy-iron-law 第 N 条` 或 `xy-repo-rules 第 N 条`，`text` 从该条连续逐字复制。检查器按对应条号和当前规范校验。

## 报告模板

四种模板由紧邻的 `report-template` 标记声明；检查器按文件名匹配，不能依赖代码块顺序。推导单独存文件，主审和剃刀报告不重复嵌入推导。

<!-- report-template: derivation-main.json, derivation-razor.json -->
```json
{
  "root": "<只看上游：要解决的根本问题；修错时写错在哪、根源在哪>",
  "needs": [{
    "need": "<最少要的一样：用户要的结果或约束，不写实现>",
    "quote": {
      "source": "<契约原话编号、原件路径、功能图确认条目、已审 spec 条目（同时写依据的用户原话编号），或 xy-iron-law/xy-repo-rules 条号>",
      "text": "<来源中的逐字原文；引已审 spec 条目时贴它依据的用户原话原文>"
    }
  }],
  "approach": "<只按 needs 想出的最小做法，写到结构层；大改动只到结构层>"
}
```

<!-- report-template: review-main.json -->
```json
{
  "first_principles": {
    "quote_problems": {
      "items": [{"problem": "<原话哪里不对、不合理、矛盾或有更好办法>", "evidence": "<证据>", "quote": {"source": "<原件>", "text": "<逐字原文>"}, "suggestion": "<建议用户如何决定及理由>"}],
      "checked": "<审过哪些原话；没审时说明原因>"
    },
    "deviations": {
      "items": [{"problem": "<对照推导：缺的、多的、做成别的、补丁式的、同根没合的；逐条>", "evidence": "<文件和行号或命令及输出>", "quote": {"source": "<契约原话、原件、派方/作者发起的 spec 依据或规范条号>", "text": "<来源中的逐字原文>"}}],
      "checked": "<对照了什么；没有发现时 items 为空>"
    }
  },
  "hard_to_misuse": {
    "items": [{"problem": "<哪种误用没被设计挡住或当场报错>", "evidence": "<文件和行号或命令及输出>", "quote": {"source": "<来源>", "text": "<逐字原文>"}}],
    "checked": "<检查范围；没有发现时 items 为空>"
  },
  "repo_rules": {
    "1": {"items": [], "checked": "<对照仓库规范第 1 条>"},
    "2": {"items": [], "checked": "<对照仓库规范第 2 条>"},
    "3": {"items": [], "checked": "<对照仓库规范第 3 条>"},
    "4": {"items": [], "checked": "<对照仓库规范第 4 条>"}
  },
  "verdict": "通过 | 改了就过 | 不通过"
}
```

<!-- report-template: review-razor.json -->
```json
{
  "occams_razor": {
    "keep": [{"entity": "<新实体>", "requirement": "<对应推导中的 need，贴 need 原文>", "achieved": "<怎样达到要求；未定的程度写明做到哪一步>", "cost": "<实际收益依据、发生次数或机制、运行位置和频率、维护代价，以及更小做法比较>"}],
    "keep_old": [{"entity": "<旧实体>", "reason": "<真实在用入口或明确要求及出处>"}],
    "delete": {"items": [{"entity": "<实体>", "loss": "<删后失去什么>"}], "checked": "<检查范围；无删除项时为空数组>"},
    "ask_user": {"items": [{"entity": "<实体>", "now": "<现在>", "change_to": "<建议变化>", "saving": "<能省什么>"}], "checked": "<检查范围；无待定项时为空数组>"},
    "quote_problems": {
      "items": [{"problem": "<原话要的东西哪里不必要、代价不配或更小做法足够>", "evidence": "<证据>", "quote": {"source": "<原件或规范条号>", "text": "<逐字原文>"}, "suggestion": "<建议用户如何决定及理由>"}],
      "checked": "<审过哪些要求；没审时说明原因>"
    }
  },
  "cleanup": {
    "hits": [{"id": "<扫描命中 id>", "decision": "改 | 留 | 要用户定", "reason": "<一句理由>"}],
    "categories": [{"category": "<清理类别>", "looked_at": "<检查范围>", "conclusion": "<结论和发现>"}]
  },
  "verdict": "通过 | 改了就过 | 不通过"
}
```

代码审查的剃刀报告才写 `cleanup`；每个扫描命中恰好回应一次，每类清理清单恰好记录一次。普通审查报告不写 `cleanup`。`keep`、`keep_old` 和其他清单都可为空。

<!-- report-template: diagnosis.json -->
```json
{
  "diagnosis": "<这组为什么没过，引用各轮报告的阻断项和证据>",
  "actions": ["<拆分 | 重想 | 问用户 | 顶回；按先后列出，不重复>"]
}
```

每份报告单独保存为 JSON，键用英文、值用中文。运行 `python3 <xy-review skill目录>/review_report_check/check.py <报告路径>` 校验；格式不通过就修改报告。

主审结论只可为「通过」「改了就过」「不通过」：所有发现项为空才可通过；后两种须有发现。剃刀通过要求 `delete.items` 为空且扫描回应中没有「改」；后两种至少有删除项或「改」命中。无需为了填清单而凑保留项。

## 收到报告后

主审或剃刀规则改动后，按 README 的说明重跑 `review-misses.md` 中的三个案例。

先校验报告，再逐项核对意见和证据。成立的按清单改，不成立的附证据回应；谁审谁不改对象。主审提出 spec 外要求时，先追溯原话和推导；作者延伸项还须有证据并经剃刀审必要性。改变用户行为、用法或用户规则的事项交用户定，没有来源支持的删除。被删的待审增量，其实现不能通过。

主审或剃刀的 `quote_problems` 若成立，当场问用户并等待回答。其他待定事项汇总到任务末尾询问。「改了就过」按原意见修改并核证据，不再复审；超出原意见的改动按 spec 外处理。「不通过」回到实现步骤，同组下一轮由两人复审。每轮报告写本轮处理；判因时用得到三轮的 `submitted*`、报告和处理记录。

每组最多三轮；第 3 轮仍不通过，停止开新轮，先派一个新开的、非作者且只读的判因者，写 `group<G>/diagnosis.json`。判因为太大、同类反复、需求分歧或审查有误时，分别按最小做法重想、回到根因、问用户或凭证据顶回。纯实现拆分可按判因继续；改变用户行为、用法或用户规则的拆分须用户决定。

非正式改测循环写入同目录 `report-round<N>.md`，运行 `stuck_loop_audit/audit.py`。第三轮后仍无有效判因时停止，并使用本目录的改测记录、对象和原话形成 `diagnosis.json`，再运行报告检查器校验。

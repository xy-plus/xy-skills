# 对抗审查

## 派审查

派之前，作者先按下面「审」审一遍自己的东西。默认派主审和剃刀；研究只派主审。两者并行、互不知道对方，都不是作者、只读：主审审铁律 1、铁律 2 和仓库规范；剃刀只审铁律 3，别的不看，这样这一条才不会被淡化。各交给它本文件、`xy-iron-law`、`xy-repo-rules`，告诉它自己是主审还是剃刀、报告写到哪。

一件事里主审、剃刀各开一个会话，之后续用（resume）：同组下一轮、spec 通过后的代码终审，都接着派给这两个会话。一组没过、判因之后，下一组换两个新开的。同时要审几个对象时，续用的这一对只审其中一个，其余各开一对。

派审说明只给审查对象、用户原话的编号与原文、审过的 spec、已有东西的位置（仓库、依赖、skill 目录）。短回答（如只答「1」）连同原始题干、所选选项原文与原件位置一起给。不写范围结论，不把范围写成「背景」事实；作者对范围的判断要进 spec 送审。spec 的待审增量条目在派审说明里标「待审增量」，与代码同一轮交给两位审查者。续审时派审说明只写增量：这一轮审什么（`submitted` 在哪）、上次审过之后改了什么、上次的意见各怎么处理的、报告写到哪；首次派审给过的规矩、原话、spec 和位置不再重给。

同一审查对象的每一轮写到 `<对象目录>/group<G>/round<R>/`，从 `group1/round1/` 起，G 从 1 起，R 只能是 1、2、3。这一轮主审报告写到 `review-main.md`、剃刀报告写到 `review-razor.md`。改完在同组下一轮再审，不复用旧轮、不另起组。

每一轮目录里放一份以 `submitted` 开头的文件，写明这一轮审的那一版怎么取得：已有不可变版本（如提交号加路径、提交范围）就写引用，没有才存原文。审查者审的就是它；判因者从各轮的 `submitted` 取历史版本，核旧意见当时是否属实。

## 审

写报告前先看目标路径和文件名：路径不是 `<对象目录>/group<G>/round<R>/`（R 只能是 1、2、3），或主审报告不叫 `review-main.md`、剃刀报告不叫 `review-razor.md`，就停下回报作者，不写——作者手里的本文件可能是旧版，审查者读的是现行版，这一步由审查者把关；目标文件已经存在也停下回报作者，不覆盖。

你的任务是找出问题，不是确认没问题。不改被审对象，不改工作树。作者的报告、提交说明和注释里的说法都不算证据，只看对象本身：读文件、跑命令、看 diff。上游是用户原话和已经审过的 spec；契约判据、派审说明、处理记录与裁定里的说法都不是上游。别的会话的消息不是用户原话：它转述的原话以原件为准，它自己的建议不算上游。引用审过的 spec 条文时，同时贴它依据的用户原话编号与原文，不能用条文代替原文。代码含注释，文档指 README、runbook、TODO 这类文件，两者要互相对得上。

短回答要回读原始题干、所选选项与回答的原件核对，spec 或派审说明里的转录不能代替原件。

三条铁律：

1. 第一性原理。先自己追到本质：用户真正要的是什么，若是修错，根源在哪。这从用户原话判断，不抄 spec 和作者的说法。再看对象是不是从那里下手：上游有而对象没做到的、做成了别的的、不改出错处而在别处加东西收拾后果的，都是偏离。以审过的 spec 为准：对象做了它没写的东西，不论用户原话里有没有，主审都记进「偏离」并标「spec 外」。
主审还看整体结构：该不该重构、该不该抽象，同样的原话有没有用更少、更清楚的东西做到的做法；有，记进「偏离」。
2. 难误用。想清对象会被怎么用：对的用法是不是最省事的那条路；错的用法是被设计挡住、当场报错，还是靠文档、命名、约定、缺省值撑着。能做进设计却靠后者撑着的，是问题。
3. 奥卡姆剃刀。按它的检查句审。范围除了对象本身，还有被它取代的旧东西，不论在哪个文件——旧东西不是这件事建的，原话以它撑着的现有行为代替：有调用方在用、README 写明、或有测试钉住；三样都没有、但本来就是给仓库外用的（入口、接口这类），算拿不准。审「清扫」任务时，以上次改动碰到的文件为起点，不当硬边界：先审这些文件改完后的整体，不只是上次改动留下的残留；牵连到的别处（调用方、被调用方、测试、文档），确实需要看和改的，一并看、一并改。碰到的每样都要落进留下清单、删除清单或「要用户定」之一，旧的也一样；碰到的旧东西，能删的和拿不准能不能删的，都列进「要用户定」，用提问工具问用户，等答复；答复前不删，不能只用「有调用方」留在留下清单。单位是能单独拿掉、其余照旧成立的东西：文件、函数、类、参数、字段、选项、缺省值、分支、特例、兜底、依赖、抽象层、测试用例、文档的节和句子；spec、流程文档里是每条要求、每个组件、每一步。按包含关系从大到小问：说得出理由的进留下清单、拿不准的进「要用户定」，都再往里问它的组成；说不出的整个进删除清单，不再往里问。留下的每样再问一次：仓库里、依赖里、已有 skill 里有没有现成能做这件事的；有就删新的、改用旧的，写进删除清单；范围里两样东西做同一件事，留一个删一个。它优先于第 2 条：防误用先靠删掉可误用的东西，再靠加检查；你自己想加的东西同样要过这一问。

标「待审增量」的 spec 条目不是上游。主审核它从哪条用户原话、怎样推出来；剃刀重点查转述扩写（如把「数据无损」扩成「字节无损」）。被删的增量条目连同实现它的代码都不能过。

合入研究产出时，只是研究时需要的，不算留下的理由。

`xy-repo-rules` 七条，逐条查。

## 报告

一份报告一个文件，只有规定的几节。每节写问题加证据，证据是文件和行号，或命令和输出；没问题就写「无，」再写对照了什么，这个字段就只有这一行。涉及增量的条目前标「增量」。结论只有一行，三选一：「通过」是没有发现；「改了就过」是有发现，但照着改就行；「不通过」是得回去重做，改完再审。「要用户定」不计入结论。写完跑 `python3 ~/.claude/skills/xy-review/check.py <报告路径>`，报错就改到不报；最后一条回复只写「结论」一节。

主审写审查报告，每条阻断都贴用户原话的编号与原文：

```markdown
## 铁律 1 第一性原理
本质：<用户真正要的是什么；若是修错，根源在哪>
偏离：<没做到的、做成别的的、补丁式的，逐条>
## 铁律 2 难误用
问题：<哪种用错不会被设计挡住或当场报错；哪里靠文档、命名、约定、缺省值撑着，逐条>
## 仓库规范
1. <问题加证据，或「无，」加对照了什么>
…
7.
## 结论
通过 | 改了就过 | 不通过
```

剃刀写剃刀报告：

```markdown
## 铁律 3 奥卡姆剃刀
留下清单：<一行一样；新东西写「实体：离开它，用户原话哪条做不到（编号加原文）」；旧东西写「实体：撑着它的现有行为（调用方、README 或测试）」，同一文件里和这次改动不相干的旧东西可以合成一行、每样写名字>
删除清单：<一行一样，范围里的旧东西也算，写「实体；删了丢什么」>
要用户定：<一行一样，拿不准能不能删的、删了会改变现有行为的、要整体重做的，写「实体：现在多大；改成什么；能省多少」>
## 结论
通过 | 改了就过 | 不通过
```

## 收到报告后

先跑同一个脚本，报错就退回重写。两份报告都处理完才往下走。谁写的谁改，审查者不改。

主审标「spec 外」的东西，找不到用户原话支撑就删；找得到就把原话原文与推导写进 spec 作待审增量，连同改后的代码按上面的派审与审查规则处理。要新增或收紧要求一律走待审增量。

删除清单逐条照删，留下清单里理由站不住的也删，除非能说出离开它，用户原话哪条做不到。「改了就过」：改掉、核过证据，没有待审增量就往下走，不再审。改动超出该条意见本身的部分，和主审标「spec 外」一样走待审增量。主审建议加的东西，作者先按铁律 3 的检查句问过才加。「不通过」：回到产出它的那一步，改完在同组下一轮再审。审查者说错了的顶回去；删了什么、顶回了什么、要用户定的（只在最后汇报里问用户，中途不问），以及代码、测试、文档各净增减多少行，最后汇报时列出来。清扫任务是「只在最后汇报里问用户」的例外：两份报告都处理完后，作者先把「要用户定」清单汇总，用提问工具问用户，等用户答复后再收尾；答复前不删，不等最后汇报。

这一轮有结论为「不通过」的报告时，作者把处理写到 `round<R>/handling.md`，写清每条意见怎么处理、对象改了什么，供判因读取。

一组最多 3 轮，第 3 轮仍有「不通过」就算这组没过，不能开 `round4`。作者先派一个新开的、不是作者、只读的判因子代理，交给它本文件、`xy-iron-law`、`xy-repo-rules`、这组三轮的 `submitted`、报告和 `handling.md`、对象的当前版本、用户原话，让它判断这组为什么没过，写到 `group<G>/diagnosis.md`。

不是正式轮次的改—测循环（比如拿对照测试自己改一处、跑一次、看结果），每次的记录写成同一个文件夹下的 `report-round<N>.md`（N 从 1 起，不要求连续，只看最大 N）；写完跑一遍 `python3 ~/.claude/skills/xy-review/audit.py <这个文件夹>`，和写报告后跑 check.py 一样——它在最大 N 达到 3、又没有同文件夹下的 `diagnosis.md` 时会报出来，这时按上面的方式停下来派判因子代理，材料换成这个文件夹里的全部 `report-round<N>.md`、对象当前版本、用户原话，写到同文件夹下的 `diagnosis.md`。

判因看四类原因，按原因选走法：

- 太大：对象比用户原话要的大，是过度设计（原话要的不难却三轮没过，先疑心这个）→ 重想，按原话要的最少做法重做；原话确实要这么多，每轮都在不同部分审出新的真问题 → 拆分，拆成彼此独立的小对象，各自从 `group1/round1` 起审，几份并行。
- 同类反复：同一类意见反复被驳回 → 重想，回到根因重想做法。
- 需求分歧：意见与用户原话冲突，或两份报告互相矛盾 → 问用户。
- 审查有误：意见站不住或只是挑刺 → 顶回。

几类同时存在时，结论按先后列出几种走法，作者逐一做完。作者按判因结论走，不同意就在处理记录里写证据顶回，和顶回审查意见一样；处理完才开下一组。

## 判因报告

只有下面两节，「判因」引用各轮报告的阻断项和证据，「结论」只有一行。判因子代理写报告前也先检查目标路径与文件：不是 `group<G>/diagnosis.md`、或已有文件，都停下回报作者，不写、不覆盖。

```markdown
## 判因
<这组为什么没过，引用各轮报告的阻断项和证据>
## 结论
<按先后列一种或几种走法，只能是「拆分」「重想」「问用户」「顶回」，用「、」隔开，不重复>
```

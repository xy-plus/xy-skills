# 对抗审查

## 派审查

派之前，作者先按下面「审」审一遍自己的东西。默认派主审和剃刀；研究只派主审。两者并行、互不知道对方，都不是作者、只读：主审审铁律 1、铁律 2 和仓库规范；剃刀只审铁律 3，别的不看，这样这一条才不会被淡化。各交给它本文件、`xy-iron-law`、`xy-repo-rules`，告诉它自己是主审还是剃刀、报告写到哪。

一件事里主审、剃刀各开一个会话，之后续用（resume）：同组下一轮、spec 通过后的代码终审，都接着派给这两个会话。一组没过、判因之后，下一组换两个新开的。同时要审几个对象时，续用的这一对只审其中一个，其余各开一对。

其他 skill（如 `xy-cleanup`）可以直接使用本 skill 定义的主审、剃刀角色和派法；调用方自带对象专用的报告格式与校验。

派审说明只给审查对象、契约目录（审查者读 `quotes/` 下的全部原话，`links.md` 标「自动：」的机器输入不用读）、和这件事直接相关的原话编号与原文、审过的 spec、已有东西的位置（仓库、依赖、skill 目录）。短回答（如只答「1」）连同原始题干、所选选项原文与原件位置一起给。不写范围结论，不把范围写成「背景」事实；作者对范围的判断要进 spec 送审。spec 的待审增量条目在派审说明里标「待审增量」，与代码同一轮交给两位审查者。续审时派审说明只写增量：这一轮审什么（`submitted` 在哪）、上次审过之后改了什么、上次的意见各怎么处理的、报告写到哪；首次派审给过的规矩、原话、spec 和位置不再重给。审查报告不必重复列出读过的全部原话；检查器无法证明审查者真的读过，重复列清单只增加手续。

同一审查对象的每一轮写到 `<对象目录>/group<G>/round<R>/`，从 `group1/round1/` 起，G 从 1 起，R 只能是 1、2、3。这一轮主审报告写到 `review-main.json`、剃刀报告写到 `review-razor.json`。改完在同组下一轮再审，不复用旧轮、不另起组。

每一轮目录里放一份以 `submitted` 开头的文件，写明这一轮审的那一版怎么取得：已有不可变版本（如提交号加路径、提交范围）就写引用，没有才存原文。审查者审的就是它；判因者从各轮的 `submitted` 取历史版本，核旧意见当时是否属实。

## 审 spec 和代码

审 spec 时，主审按第一性原理判断拆分是否充分：不拆的理由是否成立、适合独立验收的部分是否被合在一起、合并的协调成本是否低于拆分收益，以及拆出的部分是否切断了必须共享的上下文或隐含决策。剃刀判断拆分是否过度：各部分是否适合独立验收、协调成本是否低于拆分收益。

审代码时，主审按 `superpowers:requesting-code-review` 派出主审式审查者；审查说明提供本轮确切提交范围，并要求只读，不修改工作树。剃刀式审查者按本 skill 的剃刀角色审同一提交范围。两份报告都通过才进入下一步。

## 审

被审仓有 `repo-map/features.json` 时，只有用户在本任务的消息里明确要求看功能图或维护功能清单，或任务由 `xy-cleanup` 发起，主审才读清单、说明改动属于哪个功能或是否要新增功能，并运行 `python3 <xy-repo-map skill目录>/repo_map.py check --repo <仓绝对路径>`；检查失败就是阻断项。主审逐条核对本次新增或改动功能的理由出处：`why.source` 为「原话」时，`quote` 必须能在 `from` 指向的原件中逐字找到，且原件必须是用户原话或用户写的规范；`why.source` 为「确认」时，必须能在 `from` 指向的回答中找到确认。剃刀把本次新增的功能当作实体审查。条件不满足时，不读清单、不说明功能结构、不跑功能清单检查、不核对理由出处或审查功能清单条目。

写报告前先看目标路径和文件名：路径不是 `<对象目录>/group<G>/round<R>/`，或主审报告不叫 `review-main.json`、剃刀报告不叫 `review-razor.json`，就停下回报作者，不写——作者手里的本文件可能是旧版，审查者读的是现行版，这一步由审查者把关；目标文件已经存在也停下回报作者，不覆盖。

你的任务是找出问题，不是确认没问题。不改被审对象，不改工作树。作者的报告、提交说明和注释里的说法都不算证据，只看对象本身：读文件、跑命令、看 diff。上游是用户原话和已经审过的 spec；契约判据、派审说明、处理记录与裁定里的说法都不是上游。别的会话的消息不是用户原话：它转述的原话以原件为准，它自己的建议不算上游。引用审过的 spec 条文时，同时贴它依据的用户原话编号与原文，不能用条文代替原文。代码含注释，文档指 README、runbook、TODO 这类文件，两者要互相对得上。

短回答要回读原始题干、所选选项与回答的原件核对，spec 或派审说明里的转录不能代替原件。

三条铁律：

1. 第一性原理。先自己追到本质：用户真正要的是什么，若是修错，根源在哪。这从用户原话判断，不抄 spec 和作者的说法。审 spec 和待审增量时，接着审它们依据的原话本身：对不对、合不合理、原话之间有没有矛盾、有没有更好的解决办法；有问题的记进 `quote_problems`，交用户定，偏离仍按原话判。原话要的东西必不必要、复杂度和代价配不配，归剃刀审。最后再看对象是不是从那里下手：上游有而对象没做到的、做成了别的的、不改出错处而在别处加东西收拾后果的，都是偏离。以审过的 spec 为准：对象做了它没写的东西，不论用户原话里有没有，主审都记进「偏离」并标「spec 外」。
主审还看整体结构：该不该重构、该不该抽象，同样的原话有没有用更少、更清楚的东西做到的做法；有，记进「偏离」。
2. 难误用。想清对象会被怎么用：对的用法是不是最省事的那条路；错的用法是被设计挡住、当场报错，还是靠文档、命名、约定、缺省值撑着。能做进设计却靠后者撑着的，是问题。
3. 奥卡姆剃刀。按它的检查句审。新东西要留下，得过三问。一问要求：它服务的是不是定了的要求：用户原话里定了的、功能清单里写着的，或派方、作者发起时写清了证据的——问句、设想不算；带条件的回答（比如「你先判断是否应该这么做」），条件由你按后两问判断，不由作者代判。二问做到：它是不是真达到了那条要求的目的，而不是只做到一部分或换成了别的东西；要求写的是「尽量」「看能不能」这类没定下做到哪一步的，写出做到了哪一步；原本要省掉的手工步骤还在的，算只做到一部分，进「要用户定」。三问代价：先写收益——它防住的事发生过几次（写出处），或者按什么机制、多常会发生（写明依据和假设），发生一次损失多少；两样都说不出的写「没有依据」。再写代价——新增多少行、在哪里运行、多频繁、谁要维护。最后和最小的做法比：什么都不做、或只改一句说明，能做到几成。收益没有依据，或者算下来明显抵不上代价的，不能判配得上，进「要用户定」，写清两边。三问都写进留下清单。没有定了的要求撑着的进删除清单；只做到一部分、代价不配、条件判断不了的进「要用户定」，写清能做到哪一步、代价多少。一样东西只进一张清单：进了删除清单或「要用户定」的，不再写进留下清单。范围是对象本身和它取代的旧东西，不论在哪个文件。旧东西撑得住，要么从真在用的入口追得到（入口指全局 CLAUDE.md 引入的、settings.json 里装着的 hook、SKILL.md 或 CI 里会被执行的命令、已装的 systemd 单元、对外发布的接口），要么有已知的用户原话写着要它；不要求为旧东西去找原话；测试和 README 不单独算理由，跟着它们测的、写的东西走：东西删了，测试和文档一起删；两样都没有、又确定没人用的进删除清单，拿不准的进「要用户定」。单位是能单独拿掉、其余照旧成立的东西：文件、函数、类、参数、字段、选项、缺省值、分支、特例、兜底、依赖、抽象层、测试用例、文档的节和句子；spec 和流程文档里是每条要求、每个组件、每一步。从大到小问：有理由的留下，拿不准的问用户，再问组成；说不出理由的整个删掉，不再往下问。留下的每样再问：仓库、依赖、已有 skill 里有没有现成的？有就删新的、改用旧的。两样东西做同一件事，留一个删一个。它优先于第 2 条：防误用先靠删掉可误用的东西，再靠加检查；你想加的东西也要过这一问。

原话说明要求是什么，不自动证明实现必要。审 spec 和待审增量时，也这样审它们依据的原话本身：原话要的东西必不必要、复杂度和代价配不配、少做一些能不能达到目的。有问题的记进剃刀的 `quote_problems`，交用户定。

标「待审增量」的 spec 条目不是上游。主审核它从哪条用户原话、怎样推出来；剃刀重点查转述扩写（如把「数据无损」扩成「字节无损」）。被删的增量条目连同实现它的代码都不能过。

合入研究产出时，只是研究时需要的，不算留下的理由。

`xy-repo-rules` 七条，逐条查。

## 报告

一份报告一个文件，内容是符合模板的 JSON；键用英文，值用中文。主审每项问题写 `problem` 和 `evidence`，证据是文件和行号，或命令和输出；依据写入 `quote`：`source` 写契约原话编号、原件路径、spec 里派方或作者发起的证据（spec 路径和条目），或 `xy-iron-law`/`xy-repo-rules` 的条号，`text` 写该来源的逐字原文。没有发现时 `items` 为空，`checked` 写对照了什么。涉及增量的项以「增量」开头：主审写在 `problem`，剃刀写在 `entity`。主审 `verdict` 只能是「通过」「改了就过」「不通过」；「通过」当且仅当所有问题清单都空，另两种必须有发现。下文 `<本 skill 目录>` 是这份 SKILL.md 所在的目录：用 Skill 工具加载时就是 Claude Code 给出的 Base directory，经 CLAUDE.md 引入时就是引入路径所在的目录。写完跑 `python3 <本 skill 目录>/check.py <报告路径>`，报错就改到不报；最后一条回复只写 `verdict` 的值。

规范条款引用格式：主审的偏离、难误用、仓库规范问题，以及剃刀 `quote_problems` 中引用规范条款时，`source` 写 `xy-iron-law 第 N 条` 或 `xy-repo-rules 第 N 条`；`text` 从所标条款逐字复制一段连续原文，标点照抄。检查器会按来源中的条号读取对应规范并核对原文，避免把规范说成不支持该结论的意思。

剃刀写剃刀报告：

```json
{
  "occams_razor": {
    "keep": [{"entity": "<新东西：实体>", "requirement": "<它服务的定了的要求：用户原话编号加原文、功能清单的条目和原文，或派方、作者发起时写的证据；问句、设想不算，带条件的回答写你对条件的判断>", "achieved": "<它怎样达到这条要求的目的，而不是只做到一部分；要求没定下做到哪一步时，写做到了哪一步，原本要省掉的手工步骤还在不在>", "cost": "<收益：防住的事发生过几次（出处），或按什么机制、多常会发生（依据和假设），一次损失多少；都说不出写「没有依据」；代价：新增行数、在哪里运行、多频繁；和什么都不做或只改一句说明比，配不配>"}],
    "keep_old": [{"entity": "<旧东西：实体>", "reason": "<从哪个真在用的入口追到，或用户原话 N『原文』写着要它；同一文件里和这次改动不相干的旧东西可以合成一项，entity 写各样的名字>"}],
    "delete": {
      "items": [{"entity": "<实体>", "loss": "<删了丢什么>"}],
      "checked": "<对照了什么；没有发现时 items 为空>"
    },
    "ask_user": {
      "items": [{"entity": "<实体>", "now": "<现在多大>", "change_to": "<改成什么>", "saving": "<能省多少>"}],
      "checked": "<对照了什么；没有拿不准的项时 items 为空>"
    },
    "quote_problems": {
      "items": [{"problem": "<这条原话哪里不对、不合理、和哪条原话矛盾，或有什么更好的解决办法；逐条>", "evidence": "<文件和行号、命令和输出，或与之矛盾的原话编号和原文>", "quote": {"source": "<被审原话的契约编号或原件路径>", "text": "<被审原话的逐字原文>"}, "suggestion": "<建议用户怎么定，理由>"}],
      "checked": "<审了哪些原话；本轮不审原话时写明为什么>"
    }
  },
  "verdict": "通过 | 改了就过 | 不通过"
}
```

`keep`、`keep_old` 可以为空；`keep`、`keep_old`、`delete.items`、`ask_user.items` 合计至少一项。剃刀结论只看 `delete.items` 是否为空：「通过」当且仅当它为空；另两种结论必须有删除发现。

## 收到报告后

按 `superpowers:receiving-code-review` 的态度逐条核实报告和证据；核实成立后再改，意见站不住脚时附理由和证据顶回。先跑同一个脚本，报错就退回重写。两份报告都处理完才往下走。谁写的谁改，审查者不改。

主审标「spec 外」的东西：找得到用户原话的，把原话原文与推导写进 spec 作待审增量；找不到的，作者写清证据也写进待审增量，由剃刀按奥卡姆剃刀审必要性，过了就留；其中改用户看得到的行为、用法或用户自己的规则的，先附建议交用户定，用户同意了才留；两样都给不出的删掉。待审增量连同改后的代码，按上面的派审与审查规则处理。要新增或收紧要求一律走待审增量。

删除清单逐条照删；留下清单里理由站不住的也删，除非能追到真在用的入口或已知的用户原话要求它。
「改了就过」：改掉、核过证据，没有待审增量就往下走，不再审。
改动超出该条意见本身的部分，和主审标「spec 外」一样走待审增量。主审建议加的东西，作者先按铁律 3 的检查句问过才加。
「不通过」：回到产出它的那一步，改完在同组下一轮再审。
审查者说错了的顶回去；建议另开 task 的，不顶回，列进「要用户定」。
主审、剃刀 `quote_problems` 里站得住的交用户定：当场问，答复前不往下走。站不住的照前一句顶回。
最后汇报列：删了什么、顶回了什么、要用户定的、派方或作者发起且没有原话的要求，以及代码、测试、文档各净增减多少行；除 `quote_problems` 外，要用户定的只在最后汇报问，中途不问。
这一轮有结论为「不通过」的报告时，作者把处理写到 `round<R>/handling.md`，写清每条意见怎么处理、对象改了什么，供判因读取。

一组最多 3 轮，第 3 轮仍有「不通过」就算这组没过，不能开 `round4`。作者先派一个新开的、不是作者、只读的判因子代理，交给它本文件、`xy-iron-law`、`xy-repo-rules`、这组三轮的 `submitted`、报告和 `handling.md`、对象的当前版本、用户原话，让它判断这组为什么没过，写到 `group<G>/diagnosis.json`。

不是正式轮次的改—测循环（比如拿对照测试自己改一处、跑一次、看结果），每次的记录写成同一个文件夹下的 `report-round<N>.md`（N 从 1 起，不要求连续，只看最大 N）；写完跑一遍 `python3 <本 skill 目录>/audit.py <这个文件夹>`，和写报告后跑 check.py 一样——它在最大 N 达到 3、又没有同文件夹下的 `diagnosis.json` 时会报出来，这时按上面的方式停下来派判因子代理，材料换成这个文件夹里的全部 `report-round<N>.md`、对象当前版本、用户原话，写到同文件夹下的 `diagnosis.json`。判因文件写完后运行 `python3 <本 skill 目录>/check.py <这个文件夹>/diagnosis.json` 校验结构与内容。

判因看四类原因，按原因选走法：

- 太大：对象比用户原话要的大，是过度设计（原话要的不难却三轮没过，先疑心这个）→ 重想，按原话要的最少做法重做；原话确实要这么多，每轮都在不同部分审出新的真问题 → 拆分，拆成彼此独立的小对象，各自从 `group1/round1` 起审，几份并行。
- 同类反复：同一类意见反复被驳回 → 重想，回到根因重想做法。
- 需求分歧：意见与用户原话冲突，或两份报告互相矛盾 → 问用户。
- 审查有误：意见站不住或只是挑刺 → 顶回。

几类同时存在时，结论按先后列出几种走法，作者逐一做完。作者按判因结论走，不同意就在处理记录里写证据顶回，和顶回审查意见一样；判因结论为「拆分」的，拆出的新 task 会改用户看得到的行为、用法或用户自己的规则的，按「另开 task」列进「要用户定」，用户答复前不启动；其余照判因结论直接拆。这样只有会影响用户使用或其规则的拆分才需要用户决定，纯实现拆分由判因结论推进。

## 判因报告

判因报告是 JSON。`diagnosis` 引用各轮报告的阻断项和证据；`actions` 按先后列出一种或几种走法，只能用「拆分」「重想」「问用户」「顶回」，不重复。正式组的报告写在 `group<G>/diagnosis.json`；非正式循环的报告写在含合法 `report-round<N>.md` 的同一目录下。两种位置都由 `check.py` 校验同一份结构与内容。判因子代理写报告前也先检查目标路径与文件：正式组须是 `group<G>/diagnosis.json`，非正式循环须有同目录的合法改测记录，且目标文件不能已存在；不符合就停下回报作者，不写、不覆盖。

```json
{
  "diagnosis": "<这组为什么没过，引用各轮报告的阻断项和证据>",
  "actions": ["<按先后列一种或几种走法，只能用「拆分」「重想」「问用户」「顶回」，不重复>"]
}
```

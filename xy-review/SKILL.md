# 对抗审查

## 派审查

派审前作者先自审。默认派主审和剃刀，研究只派主审。两者并行、互不知情、均非作者且只读；主审审铁律 1、2 和仓库规范，剃刀只审铁律 3、别的不看，以免淡化。各给本文件、`xy-iron-law`、`xy-repo-rules`，并说明角色和报告路径。

每件事由主审、剃刀各开一会话并续用（resume）：同组下一轮及 spec 通过后的代码终审都续用；组未过并判因后，下一组新开两会话。同审多个对象时，这一对只审一个，其余各开一对。

其他 skill（如 `xy-cleanup`）可直接用本 skill 定义的主审、剃刀角色和派法；对象专用的报告格式与校验由调用方提供。

派审说明只列审查对象、契约目录（读 `quotes/` 全部原话；`links.md` 标「自动：」的机器输入不用读）、相关原话编号与原文、已审 spec、已有东西的位置（仓库、依赖、skill 目录）。短回答（如只答「1」）须连同原始题干、所选选项原文和原件位置给出。不得写范围结论或把范围当作「背景」事实；作者的范围判断要进送审 spec。spec 待审增量标「待审增量」，与代码同轮交两位审查者。续审说明只写增量：本轮审什么（`submitted` 位置）、上次审后改动、各意见的处理、报告路径；首次已给的规矩、原话、spec、位置不重给。报告不必重列读过的全部原话：检查器无法证明确实读过，重复列清单只增手续。

同一对象每轮写入 `<对象目录>/group<G>/round<R>/`，从 `group1/round1/` 起；G 从 1 起，R 仅限 1、2、3。主审报告名为 `review-main.json`，剃刀为 `review-razor.json`。改完在同组下一轮再审，不复用旧轮、不另起组。

每轮目录放一份以 `submitted` 开头的文件，说明该版如何取得：有不可变版本（如提交号加路径、提交范围）就写引用，否则存原文。审查者审此版本；判因者从各轮的 `submitted` 取历史版本，核对旧意见当时是否属实。

## 审 spec 和代码

审 spec 时，主审按第一性原理查拆分是否充分：不拆理由是否成立、适合独立验收的部分是否被合并、协调成本是否低于拆分收益、拆分是否切断必须共享的上下文或隐含决策。剃刀查是否拆得过细：各部分是否适合独立验收、协调成本是否低于拆分收益。

审代码时，主审按 `superpowers:requesting-code-review` 派主审式审查者，说明本轮确切提交范围并要求只读、不改工作树；剃刀式审查者按本 skill 的剃刀角色审同一范围。两份报告都通过才进入下一步。

## 审

被审仓有 `repo-map/features.json` 时，主审读清单，说明改动归属或是否要新增功能，并运行 `python3 <xy-repo-map skill目录>/repo_map.py check --repo <仓绝对路径>`；失败即为阻断项。主审逐条核对新增或改动功能的理由出处：`why.source` 为「原话」时，`quote` 必须在 `from` 指向的用户原话或用户规范中逐字可见；为「确认」时，`from` 指向的回答必须有该确认。剃刀把新增功能当实体审。

写报告前核对目标路径、文件名。路径不符 `<对象目录>/group<G>/round<R>/`，或主审/剃刀报告名不符 `review-main.json`/`review-razor.json`，就停下告作者、不写：作者手里的本文件可能是旧版，审查者读的是现行版，此项由审查者把关。目标已存在也停下告作者、不覆盖。

任务是找问题，不是确认无问题；只读，不改对象或工作树。作者的报告、提交说明、注释不作证据，只看对象（读文件、跑命令、看 diff）。上游仅用户原话和已审 spec；契约判据、派审说明、处理记录、裁定及其他会话的话都不是上游。其他会话转述的原话回原件核实，其建议不算上游。引用已审 spec 条文时须同时贴其用户原话编号与原文，不能以条文代原文。代码包括注释；文档（README、runbook、TODO 等）须与代码互核。

短回答须回读原始题干、所选选项和回答原件核对；spec 或派审说明的转录不能代替原件。

三条铁律：

1. 第一性原理：从用户原话追本质（真正要什么、修错根源），不抄 spec 或作者说法。审 spec、待审增量时也审其依据的原话：是否正确、合理、互相矛盾、有无更好办法；问题记入 `quote_problems` 交用户定，偏离仍按原话判。原话要求是否必要、复杂度和代价是否相称归剃刀。再查对象是否从根源下手：未满足上游要求、做成别的、未改错处而在别处加东西收拾后果，都是偏离。以已审 spec 为准；对象做了 spec 未写的事，无论用户原话是否提及，主审都记入「偏离」并标「spec 外」。主审还查整体结构：是否该重构或抽象，有无按同一原话用更少、更清楚的做法；有则记「偏离」。
2. 难误用：考虑对象的用法。正确用法是否最省事？错误用法是被设计挡住、当场报错，还是靠文档、命名、约定、缺省值撑着？能写进设计却靠后者撑着就是问题。
3. 奥卡姆剃刀：按检查句审，新东西须过三问。①要求：它服务定下的要求——用户原话、功能清单，或派方/作者从原话延伸并挂上原话、写清证据的要求；问句、设想不算。带条件且把判断交代理的回答（如「你先判断是否应该这么做」），代理判要做就算作者发起：写明证据，并过后两问；若改用户可见行为、用法或用户自己的规则（如装全局 hook），先附建议列入「要用户定」。只为它服务、离开它就无用的部分也列「要用户定」。②做到：真达到要求目的，不能只做到一部分或换成别的；「尽量」「看能不能」等未定程度的要求，写明做到哪一步；原本要省的手工步骤仍在即属部分完成，列「要用户定」。③代价：先写收益——防住之事发生过几次及出处，或发生机制、频率及其依据和假设、单次损失；都说不出就写「没有依据」。再写代价：新增行数、运行位置和频率、维护者。与最小做法比：什么都不做或只改一句说明能做到几成。收益无依据或明显不抵代价，不算配得上，列「要用户定」并写清双方。三问都写进留下清单。无定下要求支撑的列删除；只做到一部分、代价不配或条件无法判断的列「要用户定」，写能做到哪步及代价。同一东西只进一张清单；列入删除或「要用户定」的，不再列入留下。范围含对象及其替代的旧东西，不限文件。旧东西若能从真在用的入口追到（全局 CLAUDE.md 引入、settings.json 安装的 hook、SKILL.md 或 CI 执行的命令、已装的 systemd 单元、对外发布的接口），或有已知用户原话要求它，就可留下；不必为旧东西另找原话。测试和 README 不独立作理由，跟随被测、被写的东西：东西删了，测试和文档一起删；既无在用入口也无用户原话，且确定没人用的列删除，不确定的列「要用户定」。单位是能单独拿掉而其余仍成立的东西：文件、函数、类、参数、字段、选项、缺省值、分支、特例、兜底、依赖、抽象层、测试用例、文档的节和句子；spec、流程文档则逐条要求、组件、步骤。从大到小审：有理由的留下，拿不准的问用户，再审组成；说不出理由就删整个实体，不再往下拆。留下的每样再查仓库、依赖、已有 skill 是否有现成的；有就删新的、改用旧的。同一件事只留一个。此条优先于第 2 条：防误用先删掉可误用的东西，再加检查；想加的东西也要过这一问。

原话说明要求，不自动证明实现必要。审 spec 和待审增量时，也审其依据的原话：所要求的东西是否必要、复杂度和代价是否相称、少做能否达到目的；问题记入剃刀的 `quote_problems`，交用户定。

标「待审增量」的 spec 条目不是上游。主审核它源自哪条用户原话、如何推导；剃刀重点查转述扩写（如「数据无损」扩成「字节无损」）。增量条目被删，其实现代码也不能通过。

合入研究产出时，研究阶段需要它不构成保留理由。

逐条检查 `xy-repo-rules` 七条。

## 报告

每份报告单独存为符合模板的 JSON；键英文、值中文。主审每项问题含 `problem`、`evidence`（文件和行号，或命令及输出）；依据放入 `quote`：`source` 写契约原话编号、原件路径、spec 中派方或作者发起的证据（spec 路径和条目），或 `xy-iron-law`/`xy-repo-rules` 条号；`text` 逐字引来源。无发现时 `items` 为空，`checked` 写对照内容。涉及增量的项以「增量」开头，主审写在 `problem`，剃刀写在 `entity`。主审 `verdict` 仅可为「通过」「改了就过」「不通过」；所有问题清单均空才可「通过」，另两种必须有发现。`<本 skill 目录>` 指本 SKILL.md 所在目录：由 Skill 工具加载时是 Claude Code 给出的 Base directory，由 CLAUDE.md 引入时是引入路径所在目录。写后运行 `python3 <本 skill 目录>/check.py <报告路径>`，有错就改到通过；最终回复只写 `verdict` 的值。

主审的偏离、`quote_problems`、难误用、仓库规范问题，以及剃刀 `quote_problems` 引用规范条款时，`source` 写 `xy-iron-law 第 N 条` 或 `xy-repo-rules 第 N 条`；`text` 从该条逐字复制连续原文，标点照抄。检查器按来源条号读取规范并核原文，避免把规范说成不支持结论的意思。

主审报告模板：

```json
{
```

剃刀写剃刀报告：

```json
{
  "occams_razor": {
    "keep": [{"entity": "<新东西：实体>", "requirement": "<它服务的定了的要求：用户原话编号加原文、功能清单的条目和原文，或派方、作者发起时挂的原话和写的证据；问句、设想不算，带条件、把判断交给代理的回答算作者发起，写证据>", "achieved": "<它怎样达到这条要求的目的，而不是只做到一部分；要求没定下做到哪一步时，写做到了哪一步，原本要省掉的手工步骤还在不在>", "cost": "<收益：防住的事发生过几次（出处），或按什么机制、多常会发生（依据和假设），一次损失多少；都说不出写「没有依据」；代价：新增行数、在哪里运行、多频繁；和什么都不做或只改一句说明比，配不配>"}],
    "keep_old": [{"entity": "<旧东西：实体>", "reason": "<从哪个真在用的入口追到，或用户原话 N『原文』写着要它；同一文件里和这次改动不相干的旧东西可以合成一项，entity 写各样的名字>"}],
    "delete": {
      "items": [{"entity": "<实体>", "loss": "<删了丢什么>"}],
      "checked": "<对照了什么；没有发现时 items 为空>"
    },
    "ask_user": {
      "items": [{"entity": "<实体>", "now": "<现在多大>", "change_to": "<改成什么>", "saving": "<能省多少>"}],
      "checked": "<对照了什么；没有拿不准的项时 items 为空>"
    },
    "quote_problems": {
      "items": [{"problem": "<这条原话要的东西哪里不必要、复杂度和代价配不上，或少做一些也能达到目的；逐条>", "evidence": "<文件和行号、命令和输出，或能说明必要性、复杂度、代价与更小做法的依据>", "quote": {"source": "<被审原话的契约编号或原件路径，或规范条款（如 `xy-iron-law 第 3 条`）>", "text": "<被审原话的逐字原文>"}, "suggestion": "<建议用户怎么定，理由>"}],
      "checked": "<审了哪些原话要的东西必不必要；本轮不审原话时写明为什么>"
    }
  },
  "verdict": "通过 | 改了就过 | 不通过"
}
```

`keep`、`keep_old` 可为空；它们与 `delete.items`、`ask_user.items`、`quote_problems.items` 合计至少一项。剃刀结论只看 `delete.items` 是否为空：空才是「通过」，另两种结论须有删除发现。

## 收到报告后

按 `superpowers:receiving-code-review` 的态度逐条核实报告和证据，成立后再改；意见站不住就附理由、证据顶回。先跑同一脚本，报错退回重写。两份报告都处理完再继续；谁写谁改，审查者不改。

主审标「spec 外」的内容：把来源用户原话及推导写进 spec 作待审增量。若原话未直接要求、属作者延伸，另写证据，由剃刀按奥卡姆剃刀审必要性；通过才保留。若改用户可见行为、用法或用户自己的规则，先附建议交用户定，同意后才留；给不出来源原话就删。待审增量及改后的代码按上述规则派审、审查。新增或收紧要求一律走待审增量。

逐项照删删除清单；留下项理由站不住也删，除非可追到真在用的入口或已知用户原话。「改了就过」：修改并核验证据，无待审增量即可继续，不再复审。改动超出原意见的部分按「spec 外」处理；主审建议新增的东西先按铁律 3 审。「不通过」则回到产出步骤修改，在同组下一轮复审。审查意见有误就凭证据顶回；建议另开 task 的列入「要用户定」，不顶回。主审、剃刀 `quote_problems` 若站得住，当场询问并等答复；否则顶回。最终汇报列删除、顶回、待定、派方或作者从原话延伸的要求，以及代码、测试、文档净增减行数；除 `quote_problems` 外，待定只在末尾询问。若本轮有「不通过」报告，作者在 `round<R>/handling.md` 记录每条意见的处理和对象改动，供判因。

一组最多 3 轮；第 3 轮仍「不通过」即没过，不得开 `round4`。作者先派新开的、非作者且只读的判因子代理，提供本文件、`xy-iron-law`、`xy-repo-rules`、三轮的 `submitted`、报告和 `handling.md`、对象当前版及用户原话，让它判断失败原因并写入 `group<G>/diagnosis.json`。

非正式轮次的改—测循环（如用对照测试改一处、运行一次并看结果），每次记录在同一目录的 `report-round<N>.md`（N 从 1 起，可不连续，只看最大 N）。写后运行 `python3 <本 skill 目录>/audit.py <这个文件夹>`，如写报告后跑 check.py；最大 N 达 3 且同目录没有 `diagnosis.json` 时会报错，此时停下并按上文派判因代理，材料改为该目录全部 `report-round<N>.md`、对象当前版、用户原话，结果写入该目录 `diagnosis.json`。判因文件写完后运行 `python3 <本 skill 目录>/check.py <这个文件夹>/diagnosis.json` 校验结构与内容。

判因按四类原因选走法：

- 太大：对象超出用户原话即属过度设计（原话要求不难却三轮未过时先怀疑此项），重想并按原话的最少做法重做；若原话确实要求这么多、每轮又在不同部分发现新真问题，就拆成彼此独立的小对象，各从 `group1/round1` 起审并行推进。
- 同类反复：同类意见反复被驳回，回到根因重想做法。
- 需求分歧：意见与用户原话冲突或两份报告矛盾，问用户。
- 审查有误：意见站不住或只是挑刺，顶回。

多类原因并存时，按先后列出各走法，作者逐一完成。作者按判因结论执行；不同意则在处理记录写证据顶回，如顶回审查意见。判为「拆分」时，新 task 若影响用户可见行为、用法或其规则，按「另开 task」列入「要用户定」，答复前不启动；其余照结论直接拆。因此只有影响用户使用或规则的拆分须用户决定，纯实现拆分按判因推进。

## 判因报告

判因报告为 JSON。`diagnosis` 引各轮报告的阻断项和证据；`actions` 按顺序列一种或几种走法，只能用「拆分」「重想」「问用户」「顶回」，不可重复。正式组报告写 `group<G>/diagnosis.json`；非正式循环写在含合法 `report-round<N>.md` 的同目录。两处均由 `check.py` 校验同一结构与内容。判因子代理写前核对路径和文件：正式组须为 `group<G>/diagnosis.json`；非正式循环须有同目录合法改测记录；目标不得已存在。否则停下告作者，不写、不覆盖。

```json
{
  "diagnosis": "<这组为什么没过，引用各轮报告的阻断项和证据>",
  "actions": ["<按先后列一种或几种走法，只能用「拆分」「重想」「问用户」「顶回」，不重复>"]
}
```
